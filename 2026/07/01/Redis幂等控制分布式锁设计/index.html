一、核心认知：锁解决并发，幂等解决重复

设计一个同时实现幂等控制和分布式锁的方案之前，先明确两者的分工：

能力 解决的问题 失效后果
分布式锁 同一时刻只有一个线程执行临界区 并发写入、数据错乱
幂等控制 同一个请求无论执行多少次，结果一致 重复扣款、重复下单

关键认知：分布式锁提供互斥，幂等标记提供最终正确性保证。即使锁”泄露”（异常过期），幂等层也必须兜底。

二、锁的正确性（Safety）

2.1 原子性加锁

必须使用单条 SET key value NX PX 命令，不能用 SETNX + EXPIRE 两步操作。

为什么两步操作危险：

  • SETNX 成功 → 服务 crash / 网络断开
  • EXPIRE 没执行 → 锁永不过期 → 死锁

3.3 幂等标记的 TTL 设计

幂等标记不能设太短，也不能太长：

场景 建议 TTL 原因
支付回调 7 天以上 支付渠道可能延迟回调，需要足够长窗口去重

定时任务 任务周期 × 2 防止同一任务被多次触发

原则：TTL ≥ 业务最大重试窗口 × 2，同时评估 Redis 内存成本。

五、时钟与网络问题

5.1 Redlock 争议

Redis 作者提出的 Redlock 算法（N 个独立 Redis 实例，过半加锁成功才算成功）：

Martin Kleppmann 的经典分析指出：GC 暂停、时钟跳跃可能导致锁互斥性被破坏。

务实建议：对于绝大多数场景，单实例 Redis + 合理的 TTL + 业务层幂等 已经足够。只有在锁的正确性是硬性要求（如金融扣款）时，才考虑 Redlock 或换用 ZooKeeper/etcd。

5.2 时钟漂移

不要依赖 Redis 的 TTL 做精确时间控制。锁的 TTL 应该理解为”允许的最大执行时间”，而不是”精确的执行时间”。

5.3 Redis 主从切换的锁丢失

缓解方案：

  • 如果锁丢失后果严重 → 用 Redlock 或 ZooKeeper
  • 如果锁丢失只是”降低并发度”而非”数据错误” → 幂等层兜底即可
  • 等待 min-replicas-to-write 确认后再认为加锁成功（增加延迟换安全性）

六、生产落地 Checklist

6.1 锁层面

检查项 说明
✅ 加锁原子性 使用 SET NX PX 单命令，不用 SETNX + EXPIRE
✅ 解锁校验 owner Lua 脚本比较 value，防止误删他人锁
✅ 锁超时兜底 合理设置 TTL，防止死锁
✅ Watch Dog 长任务需要自动续期，短任务不需要（避免复杂度）
✅ 锁粒度 尽量细粒度（如单订单锁），避免大粒度的全局锁
✅ 获取超时 加锁操作本身设超时，别让获取锁阻塞整个请求链路

6.2 幂等层面

检查项 说明
✅ 幂等键唯一性 业务唯一键（订单号、请求 ID），不是随机的
✅ TTL 合理 覆盖最大重试窗口，但不过长浪费内存
✅ 幂等结果可解析 返回的业务结果应该是结构化数据，调用方能正确反序列化
✅ 幂等标记原子写入 用 Lua 脚本做”检查 + 标记”，防止并发写入
✅ 幂等失败策略 标记写入失败时，是回滚业务、还是重试、还是告警

6.3 组合层面

检查项 说明
✅ Double Check 加锁后再查一次幂等标记
✅ 锁失败策略 自旋重试 or 快速失败 or 异步排队
✅ 最终一致性 即使锁泄露，幂等层必须兜底
✅ 监控告警 锁等待时间、持锁时间、幂等命中率、锁获取失败率

七、常见坑与避坑指南

7.1 坑：锁被”其他人”释放

现象：A 的锁被 B 释放了，导致 C 拿到了锁。

根因：解锁时没校验 owner。

修复：Lua 脚本 GET + 比较 + DEL 原子执行。

7.2 坑：锁超时后业务还在跑

现象：锁 30s 过期，业务跑了 60s。

根因：没有续期机制。

修复：加 Watch Dog 自动续期，同时增加锁 TTL 到合理值。

7.3 坑：幂等标记丢失导致重复执行

现象：幂等标记 TTL 过短，业务重试时标记已过期。

根因：TTL 小于最大重试窗口。

修复：TTL 至少覆盖最大重试窗口 × 2。

7.4 坑：Redis 挂了导致所有请求失败

现象：Redis 不可用 → 加锁失败 → 所有业务请求被拒。

根因：锁成了单点故障。

修复方案（按优先级）：

  1. Redis 高可用（Sentinel / Cluster）
  2. 降级策略：Redis 不可用时允许”无锁执行”（依赖幂等层兜底）
  3. 本地缓存 + 租约模式

7.5 坑：可重入锁的滥用

现象：同一个线程内多次加同一把锁，用可重入计数。

问题：增加了复杂度和 bug 概率。大部分业务场景不需要可重入。

建议：先确认是否真的需要可重入。如果方法 A 调用方法 B，两者都需要锁，通常可以重构为”外层加锁，内层不加”。

八、面试回答版

8.1 短版（1 分钟）

设计 Redis 幂等控制分布式锁，核心关注 5 点：

  1. 加锁原子性：SET NX PX 单命令，防止死锁
  2. 解锁安全：Lua 脚本校验 owner，防止误删
  3. Watch Dog 续期：防止业务超时导致锁提前释放
  4. 幂等键设计：业务唯一键 + 足够的 TTL，Double Check 模式
  5. 兜底思维：锁提供互斥，幂等提供最终正确性——锁泄露了，幂等层必须兜底

8.2 长版（3 分钟）

如果让我设计一个 Redis 幂等控制分布式锁方案，我会从锁的正确性、幂等设计、两者组合三个维度考虑：

第一，锁的正确性：加锁必须用 SET NX PX 单条命令保证原子性；解锁必须用 Lua 脚本校验锁的持有者，防止 A 的锁超时后被 B 获取、A 又把 B 的锁误删；如果业务执行时间可能超过锁 TTL，需要 Watch Dog 后台协程自动续期，续期间隔一般设为 TTL 的 1/3。

第二，幂等控制：幂等键要用业务唯一标识（如订单号、请求 ID），而不是随机值；幂等标记的 TTL 要覆盖业务的最大重试窗口；写入幂等标记时用 Lua 原子操作，完成”检查 → 标记 → 返回”三步原子执行。

第三，锁与幂等的组合：推荐 Double Check 模式——先无锁查幂等标记（快速返回），再获取分布式锁，获取锁后再查一次幂等标记，最后执行业务并写标记。这样能防止并发窗口期的重复执行。

第四，边界条件：Redlock 在 GC 暂停或时钟跳跃下不完全安全，一般业务用单实例 Redis 就够，硬性安全需求考虑 ZooKeeper。Redis 主从切换可能丢锁，也得靠幂等层兜底。监控上至少覆盖持锁时长、锁等待时长、幂等命中率。

总结

设计 Redis 幂等控制分布式锁，一句话原则：

锁保并发互斥，幂等保最终正确。锁可以丢，幂等不能漏。

具体落地时，抓住 4 个核心动作：

  1. SET NX PX 原子加锁
  2. Lua 校验 owner 再解锁
  3. Watch Dog 自动续期
  4. Double Check 幂等兜底

再加上合理的 TTL 设计、监控告警、降级策略，就是一套生产可用的方案。
