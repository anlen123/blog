分库分表基因法详解——从原理到实战

基因法是分库分表架构中一种经典的路由策略。它的核心思想极其巧妙：在数据写入时，将分片键的信息”编码”进业务 ID 中，使得后续通过业务 ID 查询时，无需跨库就能直接定位目标分片。 本质是”信息前置”——把路由所需的信息提前写入数据本身。

一、问题背景：为什么要用基因法？

1.1 一个具体的场景

1.2 基因法的本质

一句话概括：将 user_id 的路由信息编码到 order_id 内部，使 order_id 本身就携带分片位置。

就像每个人的身份证号包含了出生地信息一样——不需要查表就能知道籍贯。

四、基因位数的确定

4.1 计算公式

实战建议：预留 1-2 个额外 bit，例如当前 32 库用 5 bit，但预留到 7 bit（支持未来扩展到 128 库），把预留位填 0。

4.2 基因碰撞

基因法本身不会产生碰撞——同基因值的数据理论上都在同一个分片。

真正需要注意的是 ID 生成器本身的唯一性：基因法只负责路由，不负责唯一性。如果你用基因法改造后的 ID 生成器，需要保证时间戳 + 序列号部分的唯一性不受基因位侵占的影响。

五、核心优势与代价

5.1 优势

优势 说明
O(1) 精准路由 无需全库扫描，一次取模 / 位运算直接定位
零额外存储 基因编码在 ID 内部，不需要额外的路由表
零额外查询 不需要查路由表 / 缓存，ID 自带路由信息
极低计算开销 位运算仅需 1 个 CPU 周期
无单点故障 不依赖外部路由服务，每个 ID 自包含路由

5.2 代价与限制

代价 说明 缓解方案
分片数固定 扩容后旧 ID 的基因指向错误分片 渐进式路由兼容（见第七章）
ID 膨胀 基因占用 bit 位，挤压了其他字段 预留足够 bit 宽度
仅解等值查询 范围查询、IN 查询仍需多库 结合 ES/ClickHouse 等
单分片键 只能编码一个分片键的路由 多维度用查询索引表互补
编排复杂度 ID 生成器需感知分片数 从配置中心读取分片数

6.2 各方案详细分析

路由表方案：

  • 优点：分片数灵活变化
  • 缺点：多一次查询，路由表本身也是单点/需要分片，数据一致性需额外维护

  • 路由表：用存储换取灵活性，1 次额外查询

九、常见面试追问

Q1：基因法的 ID 会不会重复？

不会。基因法只替换了 ID 的某几个 bit，只要 ID 生成器的其他部分（时间戳 + 序列号）保证唯一，整体 ID 就是唯一的。基因位的变化对应不同用户，不影响唯一性。

Q2：如果 user_id 跨分片迁移怎么办？

基因法假设 user_id 到分片的映射是稳定的。如果 user_id 迁移了分片（比如数据再均衡），所有该用户的 order_id 中的基因都会指向老分片。解决方案：

  • 不迁移用户，只做分片级别的新增（加库）
  • 或者迁移后保留旧分片作为路由兜底（先查新分片，miss 再查旧分片）

Q3：B+Tree 索引在基因法 ID 上的表现如何？

基因位于 ID 低位，会使 ID 在多个分片间交错分布而非连续递增：

影响：

  • 写入：每个分片的 ID 仍是递增的，对 B+Tree 插入友好 ✅
  • 跨库排序：全局时序被打乱，需要额外的时间戳排序 ❌
  • 解决办法：如果必须全局排序，保留原始时间戳字段，或用基因放高位而非低位的设计

Q4：基因放高位还是低位？

位置 优点 缺点
低位 取模/位运算直接得到基因，解码极快 同一分片内 ID 不连续（跳增）
高位 同一分片 ID 连续，利于局部性 需要额外位移提取基因

推荐低位：性能优先，且 B+Tree 对递增写入已足够友好。

十、总结

基因法是一种以空间（ID 位宽）换时间（查询延迟） 的经典分布式路由策略：

维度 结论
核心思想 将分片键取模结果编码进业务 ID
数学保证 (A × N + B) % N = B，取模恒等性
最佳搭档 雪花算法 + 位运算编码，生产黄金组合
适用查询 等值查询（WHERE id = ?）、IN 查询的一部分
不适用查询 纯范围查询、模糊查询、多维度组合查询
扩容策略 预留基因位 + 渐进迁移

一句话记忆：基因法就是让你的 ID “记住”自己属于哪个分片——就像身份证号告诉你籍贯一样。
