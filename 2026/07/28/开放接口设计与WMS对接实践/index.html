一、开放接口设计五大要点

开放接口和内部接口有本质区别——调用方不是你团队的，他们不会按照你的节奏走，超时必重试，报错看不懂就找你。

1.1 鉴权：谁在调我？

开放接口第一个问题永远是：调用方是谁，有没有权限？ 详细方案见第二章。

1.2 幂等：同一个请求别处理两次

调用方超时后会重试，你必须保证同一条请求只生效一次。

1.3 错误码规范：让调用方能程序化处理

调用方最怕看到 {"code": 500, "message": "系统异常"}——他们不知道是参数错了还是你崩了，只能找你。

二、鉴权方案详解

开放接口的鉴权，核心就一个问题：如何在无状态的 HTTP 请求中，确认调用方身份且防止被伪造？

2.1 四种主流方案对比

方案 复杂度 安全性 适用场景 核心原理
AK/SK + HMAC ⭐⭐⭐ ⭐⭐⭐⭐ 系统间调用、WMS 对接 对称签名，服务端用相同算法算一遍比对
JWT ⭐⭐ ⭐⭐⭐ BFF 层、用户态 API 服务端签发，客户端携带，无状态验证
OAuth 2.0 ⭐⭐⭐⭐ ⭐⭐⭐⭐ 第三方授权登录 授权码模式，不暴露用户密码
mTLS ⭐⭐ ⭐⭐⭐⭐⭐ 金融级安全、专线 双向证书校验，传输层加密

2.2 AK/SK + HMAC 签名（WMS 场景首选）

这是 WMS / 供应链对接最常用的方案，因为调用方是固定系统，不是浏览器用户。

原理

签名流程

签名内容包含什么？

至少包含：

  • AccessKey：标识是谁
  • Timestamp：防重放过期请求
  • Nonce：一次性随机数，结合 Timestamp 防重放
  • RequestBody：防中间人篡改请求体

建议也签入：

  • HTTP Method + Path：防止请求被重放到其他接口
  • Content-Type：防止类型混淆攻击

为什么 WMS 场景优先选 AK/SK？

  • 调用方是程序而非用户，不需要 OAuth 的授权页面跳转
  • 仓库 IP 固定，可额外加 IP 白名单
  • 无状态验证，不依赖 Session/Token 刷新
  • 仓库端技术栈各异（Java、.NET、甚至用脚本调），HMAC 实现通用

2.3 JWT（适合带用户态的 API）

JWT 的核心是服务端签发令牌，客户端携带，服务端无状态验证。

JWT 结构：

JWT 的坑：

坑 说明 对策
无法主动失效 签发后到过期前一直有效 配合 Redis 黑名单，或设短过期 + refresh token
不要存敏感信息 Payload 只 base64，非加密 只放 userId，不放密码/手机号
算法降级攻击 攻击者改 alg: "none" 服务端固定算法，忽略 JWT 头声明的 alg
密钥泄露 SecretKey 泄露后所有 Token 可伪造 定期轮换密钥

2.4 OAuth 2.0（第三方授权场景）

如果业务需要允许外部应用以用户名义访问数据（比如让第三方 ERP 读取你 WMS 的库存数据），用 OAuth 2.0 授权码模式。

四种授权模式：

模式 适用场景 安全性
授权码（Authorization Code） 有服务端的第三方应用 ⭐⭐⭐⭐
客户端凭证（Client Credentials） 系统间调用，无用户参与 ⭐⭐⭐
密码模式（Password） 高度信任的应用（已不推荐） ⭐⭐
隐式模式（Implicit） 纯前端 SPA（已废弃） ⭐

WMS 场景一般用 Client Credentials 模式就够了——没有用户参与，就是系统 A 调系统 B。

2.5 mTLS（金融级安全）

如果对接的是对安全性要求极高的场景（支付、银行），可以走 mTLS（双向 TLS）：

  • 普通 HTTPS：客户端验证服务端证书（单向）
  • mTLS：双方都出示证书，互相验证

优点： 传输层安全，应用层不用管签名逻辑
缺点： 证书管理成本高，WMS 小仓可能搞不定

2.6 鉴权方案选型决策树

三、WMS 对接专项

3.1 先理解 WMS 系统的特点

特点 影响 设计对策
仓库网络不稳定 超时、断连家常便饭 重试 + 异步回调双通道
单据明细行多 一张入库单几百 SKU 分页查询 + 批量接口
状态机极其复杂 单据有十几个状态 状态映射文档双方对齐签字
仓库作业有延迟 下发 ≠ 立刻执行 “指令-确认”两步模式
多仓多货主 数据隔离必须到位 每个接口必须带 warehouseCode

3.2 异步流程设计（最关键）

WMS 对接的第一大坑：同步接口等不到结果。

你下发一张入库单，仓库 2 小时后才拣货完成。如果靠同步接口轮询，两边的连接都扛不住。

正确做法：指令下发 + 回调确认 双通道

回调接口的三个铁律：

  1. 必须幂等：WMS 可能会重复回调，你的回调接口必须做幂等
  2. 必须快速响应：收到回调立刻返回 200，业务逻辑异步处理
  3. 必须有重试：WMS 回调可能失败，要求对方做重试（至少 3 次，指数退避）

3.3 状态机对齐

WMS 对接第二大坑：双方对”已完成”理解不同。

你的”已完成” = 入库上架完成，库存已增加
WMS 的”已完成” = 收货完成，还没上架

对策：

落地手段：

  • 状态映射表写进对接文档，双方签字确认
  • 做一个状态转换层：你的服务用内部枚举，跟 WMS 交互时做翻译
  • 每个状态变更都走回调，不靠轮询猜状态

3.4 库存同步三层保障

层级 策略 频率 作用
L1：下单前校验 实时查询 WMS 库存 每次下单 防止超卖
L2：变更增量同步 WMS 回调推送变更 实时 保持库存时效性
L3：全量对账 定时全量拉取对比 每天凌晨 兜底发现差异

3.5 异常处理三板斧

WMS 对接的异常处理比正常流程更重要。

核心原则：

  • 超时 ≠ 失败：先查一下对方是否已处理
  • 业务异常不重试：重试没用，直接告警
  • 连接失败可重试：但要指数退避，别把对方打崩

3.6 一个真实踩坑案例

之前对接过一个三方仓，他们的回调经常丢，导致入库单一直卡在”已下发”状态，库存对不齐。

复盘： 原因出在 WMS 那边回调只发一次，不重试。网络一抖动就丢了。

解决：

  1. 加了一个定时巡检任务：超过 2 小时没完成状态的单据，主动调 WMS 查询接口拉状态
  2. 给 WMS 方提了要求：回调加上重试机制，3 次指数退避
  3. 对账任务从每天一次改为每 4 小时一次，缩小差异窗口

教训： 回调通道必须有兜底，永远不要假设对方一定回调成功。

五、面试回答版

面试官：你们做开放接口，还有对接 WMS 系统，应该注意什么？

建议回答结构：

第一步：先讲你对问题的拆分（体现思维框架）

“开放接口设计和 WMS 对接，我觉得可以拆成三个层面来看：

  • 安全层：谁可以调、怎么防伪造、怎么防滥用
  • 可用性层：怎么保证幂等、怎么处理异常、怎么做容错
  • 业务对齐层：WMS 的状态机、库存怎么同步、异常怎么兜底”

第二步：讲鉴权方案选型

“鉴权这块，系统间调用我优先选 AK/SK + HMAC 签名方案。请求方用 SecretKey 对’AccessKey + Timestamp + Nonce + Body’做 HMAC-SHA256 签名，服务端用相同算法重算比对。Timestamp 防重放、Nonce 防同一时间窗口内重复、Body 参与签名防中间人篡改。WMS 场景因为仓库 IP 固定，还会加一层 IP 白名单。”

第三步：讲幂等设计

“幂等是开放接口的命门。调用方超时一定会重试，我的设计是用 requestId 做 Redis 去重，处理结果也缓存起来，重复请求直接返回原结果。数据库加唯一索引作为并发下的最终兜底。回调接口也必须幂等，用 eventId 去重。”

第四步：讲 WMS 对接的核心难点（差异化亮点）

“WMS 对接比普通 API 复杂，因为有三个特殊点：

第一，仓库网络不稳定。不能只靠同步接口，要设计’下发指令 + 回调确认’双通道。回调必须有重试机制，同时我方轮询查询作为兜底。

第二，状态机对齐。WMS 有十几个状态，和我们的语义不完全一致。我们建立了一个状态映射表，文档化了 6 个关键状态的对应关系，双方签字确认。代码层面做了一个转换层，内部用我们的枚举，发请求时翻译成 WMS 的状态码。

第三，库存同步。用三层保障：下单前实时查询防超卖、变更增量同步保持时效、全量对账兜底发现差异。上次对账发现过 500 多 SKU 有差异，最后跟踪到是回调丢失导致的。”

第五步：收尾，体现全局观

“总结下来，开放接口和 WMS 对接的核心就八个字：安全第一、兜底为王。鉴权防住坏人，幂等防住重复，回调加主动查询双重兜底，对账任务保证数据最终一致。”

本文覆盖了开放接口设计、鉴权方案选型和 WMS 对接的核心实践。其中 AK/SK + HMAC 签名是系统间调用最常用的方案，WMS 对接的核心难点在于异步流程设计和状态机对齐。
