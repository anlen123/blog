MVCC 底层原理详解

一、什么是 MVCC？

MVCC（Multi-Version Concurrency Control，多版本并发控制） 是一种并发控制机制，它通过维护数据的多个版本来实现高效的并发读写，核心思想是 “读不阻塞写，写不阻塞读”。

不同于传统的锁机制（读锁/写锁互斥），MVCC 让每个事务看到的是数据的一致性快照（Snapshot），而不是实时数据。这样就避免了大量读写冲突。

二、为什么需要 MVCC？

2.1 没有 MVCC 的世界——锁的困境

假设一个最简单的并发场景：

时间 事务 A（读） 事务 B（写）
T1 开始读 users 表
T2 读取中… 开始更新 users 表
T3 读到脏数据 ❌ 更新中…

没有并发控制，可能读到脏读、不可重复读、幻读等问题。

2.2 纯锁方案的问题

纯锁方案下，读写互相阻塞，高并发场景吞吐量极低。

2.3 MVCC 的方案

MVCC 的精妙之处：读写互不阻塞，只有写写冲突需要处理。

三、MVCC 核心三要素

以 MySQL InnoDB 为具体例子，MVCC 由三个核心机制构成：

3.1 隐藏字段（Hidden Columns）

InnoDB 在每一行数据后面都悄悄加了三个隐藏字段：

字段 大小 含义
DB_TRX_ID 6字节 最后修改该行的事务ID
DB_ROLL_PTR 7字节 回滚指针，指向 Undo Log 中的旧版本
DB_ROW_ID 6字节 隐式自增ID（无主键时使用）

3.2 Undo Log（回滚日志）——版本链

每次修改数据，InnoDB 会把旧版本记录到 Undo Log，然后用 DB_ROLL_PTR 串联成版本链。

六、当前读 vs 快照读

MVCC 只作用于快照读（Snapshot Read）：

类型 语句 使用MVCC？
快照读 SELECT * FROM t WHERE id=1 ✅ 使用 MVCC
当前读 SELECT ... FOR UPDATE ❌ 加锁读最新版
当前读 SELECT ... LOCK IN SHARE MODE ❌ 加锁读最新版
当前读 UPDATE / DELETE / INSERT ❌ 总是读最新版

九、MVCC 的优缺点总结

优点 ✅

优点 说明
读写不冲突 读操作不需要获取锁，写操作也不阻塞读
高并发 大量读+少量写场景下吞吐量极高
一致性快照 RR 级别下事务内数据一致，不会出现不可重复读
无锁读 普通 SELECT 完全无锁，性能极佳

缺点 ❌

缺点 说明
额外存储 Undo Log 占用磁盘空间
版本链过长 频繁更新或长事务导致版本链很长，影响查询性能
不是真正的 Serializable MVCC 本身不解决写偏斜（Write Skew）
内存开销 维护 ReadView 和版本链需要额外内存

十、PostgreSQL 的 MVCC（对比 InnoDB）

PostgreSQL 的实现思路类似，但细节不同：

特性 MySQL InnoDB PostgreSQL
版本存储 Undo Log（分离） 数据页内（堆中）
清理机制 Purge线程（后台） VACUUM（定期清理死元组）
回滚段 有专用回滚段 无回滚段，直接标记
事务ID回卷 不敏感 需要 FREEZE 防止回卷
优点 回滚快 版本查找快（在同一页）
缺点 版本链可能跨页 表膨胀，需要 VACUUM
