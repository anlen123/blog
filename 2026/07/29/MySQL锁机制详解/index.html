MySQL 锁机制详解

MySQL InnoDB 的锁机制是理解事务隔离、MVCC、死锁和并发性能的基础。本文从底层原理出发，系统讲透 InnoDB 的各种锁。

一、锁的分类全景

二、行锁（Record Lock）

2.1 基本概念

行锁锁定的是索引记录，不是数据行本身。如果某条 SQL 没走索引，行锁会退化为表锁！

2.2 行锁的两种模式

锁类型 简称 互斥关系 加锁语句
共享锁 S 锁 S 与 S 兼容，S 与 X 互斥 SELECT ... LOCK IN SHARE MODE
排他锁 X 锁 X 与任何锁互斥 SELECT ... FOR UPDATE / UPDATE / DELETE / INSERT

2.3 行锁加在索引上

关键原则：InnoDB 的行锁是加在索引上的。如果没走索引，行锁退化为表锁！

2.4 两阶段锁协议

InnoDB 的行锁在事务提交时才释放，不是语句执行完就释放。这是防止并发写冲突的基础。

三、间隙锁（Gap Lock）

3.1 解决的问题：幻读

间隙锁是 InnoDB 在 RR（可重复读） 级别下的独特能力，用于防止幻读（Phantom Read）。

了解幻读的完整背景，参考：事务隔离性的原理

特点 说明
只在 RR 级别 RC 级别没有间隙锁
只阻止 INSERT 不阻止 UPDATE/DELETE
S 锁和 X 锁的 Gap Lock 不互斥 间隙锁之间总是兼容的
唯一索引等值查询不会加 Gap Lock 唯一索引已经保证无幻读

四、临键锁（Next-Key Lock）

4.1 概念

Next-Key Lock = Record Lock + Gap Lock，锁定一个索引记录及其之前的间隙。

这是 InnoDB 默认的行锁算法。

五、意向锁（Intention Lock）

5.1 为什么需要意向锁

疑问：InnoDB 要给某行加 X 锁，怎么判断表级是否已有 S 锁？

  • 没有意向锁：需要遍历所有行检查 → 太慢
  • 有意向锁：表级 mark 一下即可 → O(1)

5.2 IS 锁与 IX 锁

锁类型 含义 获取方式
IS（意向共享锁） 事务打算给某些行加 S 锁 SELECT ... LOCK IN SHARE MODE 时自动加
IX（意向排他锁） 事务打算给某些行加 X 锁 SELECT ... FOR UPDATE 时自动加

5.3 表级锁兼容矩阵

IS IX S X
IS ✅ ✅ ✅ ❌
IX ✅ ✅ ❌ ❌
S ✅ ❌ ✅ ❌
X ❌ ❌ ❌ ❌

意向锁之间总是兼容的（IS/IX），因为不同行之间的锁不冲突。

八、锁与 MVCC 的关系

锁和 MVCC 是 InnoDB 并发控制的两大支柱：

机制 读操作 写操作 解决的问题
MVCC 快照读（无锁） 写 Undo Log 读不阻塞写
锁 当前读（加锁） 阻止并发写 写不丢失

九、面试高频题

Q1：InnoDB 在 RR 级别下如何解决幻读？

通过 Next-Key Lock（行锁 + 间隙锁）。间隙锁锁住记录之间的空隙，阻止其他事务 INSERT 新数据，从而防止范围查询时出现幻行。这也是 InnoDB 优于标准 RR 的关键。

Q2：SELECT … FOR UPDATE 和 LOCK IN SHARE MODE 的区别？

FOR UPDATE LOCK IN SHARE MODE
锁类型 X 锁（排他） S 锁（共享）
其他事务读 ✅ 可以（快照读） ✅ 可以
其他事务写 ❌ 阻塞 ❌ 阻塞
其他事务加 S 锁 ❌ 阻塞 ✅ 可以

Q3：间隙锁会造成什么问题？

间隙锁的主要副作用是可能导致更多的死锁。因为间隙锁之间虽然兼容，但间隙锁和 INSERT 操作会冲突。例如：

Q4：什么情况下行锁会升级为表锁？

  1. SQL 没有命中索引，做全表扫描
  2. 使用了 LOCK TABLES 显式加表锁
  3. 对 MySQL 原生不支持行锁的引擎（如 MyISAM）

Q5：如何预防死锁？

  1. 统一加锁顺序：所有事务按相同顺序访问资源
  2. 缩短事务，尽快提交
  3. 尽量用主键/唯一索引更新，减少锁范围
  4. RC 隔离级别替代 RR：避免间隙锁（但要注意不可重复读）
  5. 应用层捕获死锁并重试

总结

一句话：InnoDB 的行锁加在索引上，不命中索引就退化成表锁；RR 级别下默认使用 Next-Key Lock 防止幻读；间隙锁虽然解决幻读但也增加了死锁风险。
