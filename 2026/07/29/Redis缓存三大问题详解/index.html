Redis 缓存三大问题详解——穿透、击穿、雪崩

缓存穿透、缓存击穿、缓存雪崩是 Redis 面试中必问的三板斧。本文从定义、原因、方案到代码，一次性讲透。

一、三个问题一句话区分

二、缓存穿透（Cache Penetration）

2.1 什么情况

用户请求的数据缓存和数据库中都不存在。比如请求 id=-1 的商品，每次请求都穿透缓存直击数据库。

原因：

  • 恶意攻击：用不存在的数据疯狂查询
  • 业务 bug：请求了不应该存在的 ID
  • 爬虫遍历：遍历 ID 范围扫描

2.2 解决方案

方案一：布隆过滤器（Bloom Filter）⭐ 推荐

在缓存之前加一层布隆过滤器，判断 key 是否可能存在。

方案二：缓存空值

把”数据不存在”也缓存起来，设置较短的过期时间。

注意：大量不存在的 key 会撑爆 Redis 内存，所以过期时间要短，且最好配合布隆过滤器。

2.3 方案对比

方案 优点 缺点 推荐度
布隆过滤器 内存小，精度可控 有误判率，不能删除 ⭐⭐⭐⭐⭐
缓存空值 实现简单 大量 key 浪费内存 ⭐⭐⭐
参数校验 无额外成本 只能挡基础攻击 ⭐⭐⭐⭐

最佳实践：参数校验 + 布隆过滤器 + 缓存空值兜底，三层防护。

三、缓存击穿（Cache Breakdown）

3.1 什么情况

一个热点 key 在过期瞬间，大量并发请求同时打到数据库。

3.2 解决方案

方案一：互斥锁（Mutex Lock）⭐ 最常用

第一个请求去查 DB 并加锁，其他请求等待锁释放后直接读缓存。

方案二：逻辑过期（不设物理过期）

缓存不设置过期时间，而是在 value 中存储”逻辑过期时间”。后台异步更新。

方案三：永不过期

对于特别核心的热点数据（如秒杀商品库存），干脆不设过期时间，通过双写 + 更新通知来更新。

3.3 方案对比

方案 优点 缺点
互斥锁 简单可靠，一致性强 可能短暂阻塞
逻辑过期 高可用，不阻塞 短暂数据不一致
永不过期 最简单 需要保证 DB 和缓存一致性

推荐：核心热点数据用逻辑过期 + 互斥锁组合，普通数据用互斥锁。

四、缓存雪崩（Cache Avalanche）

4.1 什么情况

大量缓存 key 在同一时间集中过期，或者 Redis 宕机，所有请求直接打到 DB。

4.2 解决方案

方案一：过期时间加随机值（防止同时过期）⭐

原理：让 key 的过期时间分散开，避免集中过期。

六、三个问题对比总结

缓存穿透 缓存击穿 缓存雪崩
现象 请求不存在的 key 一个热点 key 过期 大量 key 同时过期
打击面 每次都不命中 过期瞬间集中 全面冲击
数据不存在? ✅ 是（不存在） ❌ 否（存在但过期） ❌ 否（同时过期）
核心方案 布隆过滤器 + 空值缓存 互斥锁 + 逻辑过期 随机 TTL + 多级缓存
严重程度 中 高 极高

七、面试回答模板

面试官：”说说缓存穿透、击穿、雪崩的区别和处理方式”

穿透是请求既不命中缓存也不命中数据库，用布隆过滤器和缓存空值解决；击穿是一个热点 key 过期瞬间大量并发打到 DB，用互斥锁或逻辑过期解决；雪崩是大量 key 同时过期或 Redis 宕机，用随机过期时间、多级缓存、限流熔断解决。

三者严重程度递增：雪崩 > 击穿 > 穿透。穿透是”数据本来就不存在”，击穿是”热点消失了一瞬间”，雪崩是”整个缓存层坍塌”。

生产上建议的组合：穿透层用布隆过滤器 + 参数校验；击穿用互斥锁；雪崩用随机过期 + 本地缓存 + Redis 高可用。
