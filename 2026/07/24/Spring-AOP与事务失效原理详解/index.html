Spring AOP 与事务失效原理详解

发表于2026-07-24|更新于2026-07-28|后端

一、Spring AOP 的底层运行原理

1. 代理模式

Spring AOP 基于动态代理实现，有两种代理方式：

代理类型 适用条件 实现
JDK 动态代理 目标类实现了接口 java.lang.reflect.Proxy
CGLIB 代理 目标类没有实现接口（或强制使用 CGLIB） 字节码增强，生成目标类的子类

Spring Boot 2.x 开始默认使用 CGLIB 代理（spring.aop.proxy-target-class=true）。

2. 核心组件

关键组件：

  • Aspect：切面类，包含通知（Advice）和切点（Pointcut）
  • JoinPoint：程序执行的连接点（方法调用）
  • Advisor = Pointcut + Advice 的组合体
  • AopProxy：代理对象（JDK 或 CGLIB 生成的代理）
  • MethodInterceptor：方法拦截器链，ReflectiveMethodInvocation.proceed() 驱动链式调用

二、Spring 事务管理原理

1. 事务本质也是一个切面

@Transactional 本质上就是一个 AOP Advisor（BeanFactoryTransactionAttributeSourceAdvisor），它的 Advice 是 TransactionInterceptor。

2. 事务切面与自定义切面的执行顺序

当同一个 Bean 上同时存在事务切面和自定义切面时，默认顺序是不确定的。可以通过 @Order 或实现 Ordered 接口来控制。

三、事务失效的 8 大场景及根本原因

场景 1：自调用（最常见 🔥）

原因：调用 this.innerMethod() 时直接通过目标对象引用调用，完全绕过了代理对象。AOP 只能拦截外部穿过代理的调用。

为什么代理是关键：

  • 调用者 → 代理对象 → 事务拦截器 → 目标方法 ✅
  • 目标方法内 → this.otherMethod() → 目标方法 ❌ 没有代理

解决方案：

场景 2：非 public 方法

原因：

  • JDK 动态代理：只能代理接口中声明的 public 方法
  • CGLIB 代理：通过继承生成子类，不能重写 private/final/static 方法
  • Spring 的 AbstractFallbackTransactionAttributeSource 默认要求方法是 public 的

场景 3：异常被吞掉

原因：事务回滚的触发条件是 TransactionInterceptor 捕获到异常。如果异常在目标方法内部被 catch 了，invocation.proceed() 正常返回，事务管理器就会提交事务。

补充：@Transactional 默认只对 RuntimeException 和 Error 回滚，受检异常不会触发回滚，除非显式指定：

场景 4：数据库引擎不支持事务

原因：MyISAM 引擎不支持事务。@Transactional 的代码能正常执行，但事务操作会被 MySQL 静默忽略，数据会直接写入磁盘。

场景 5：多线程环境

原因：事务上下文通过 TransactionSynchronizationManager 绑定在 ThreadLocal 上，每个线程持有独立的事务连接。新线程无法拿到当前线程的事务。

场景 6：传播行为配置不当

事务传播行为（Propagation）决定了一个事务方法被另一个事务方法调用时，事务边界如何界定。Spring 定义了 7 种传播行为，面试高频。

6.2 7 种传播行为完整解析

① REQUIRED（默认）—— 有则加入，无则新建
调用方有事务？ methodA 行为
有 加入调用方事务，同生共死
没有 自己创建一个新事务

图解：

② REQUIRES_NEW —— 总是独立开新事务
调用方有事务？ sendLog 行为
有 挂起调用方事务，自己新建独立事务
没有 自己创建新事务

核心特性：互不影响。 调用方回滚，不影响 REQUIRES_NEW 已经提交的数据。

典型场景： 扣款失败了要回滚，但操作日志无论如何都要记录下来。

③ NESTED —— 嵌套事务（Savepoint 机制）

NESTED vs REQUIRES_NEW 的核心区别：

维度 NESTED REQUIRES_NEW
数据库连接 共享外层连接 独立新连接
回滚影响 只回滚到 savepoint 完全独立，互不影响
外层提交 嵌套事务的数据随外层一起提交 各自独立提交
实现机制 JDBC Savepoint 获取新 Connection
依赖 JDBC 3.0+ Savepoint 支持 无特殊要求

典型场景： 批量处理，每条记录可以独立失败，但不影响整批。

④ SUPPORTS —— 有就加入，没有就算

典型场景： 纯查询方法。被事务方法调用时能享受到事务隔离级别的保障，单独调用时也不报错。

⑤ NOT_SUPPORTED —— 强制非事务运行

为什么要挂起？ 如果外层事务持有行锁或表锁，NOT_SUPPORTED 里的操作可以”跳出”锁等待，避免长时间占用连接。

⑥ NEVER —— 有事务就报错

典型场景： 清除缓存等操作，开发阶段防止被误包在事务里。

⑦ MANDATORY —— 强制要求有事务

典型场景： 数据库写操作必须带事务，单独调用时立刻报错，防止裸写。

6.3 7 种传播行为一览

传播行为 调用方有事务 调用方没事务 典型场景
REQUIRED 加入 新建 默认选择，绝大部份业务
REQUIRES_NEW 挂起 + 新建 新建 日志、审计（无论如何要落库）
NESTED 嵌套 savepoint 退化为 REQUIRED 批量处理、允许部分失败
SUPPORTS 加入 非事务运行 纯查询方法
NOT_SUPPORTED 挂起 + 非事务 非事务运行 发邮件/短信等耗时非事务操作
NEVER 抛异常 非事务运行 强制非事务场景
MANDATORY 加入 抛异常 强制要求调用方提供事务

6.5 传播行为与隔离级别的配合

传播行为定义了”事务边界”，隔离级别定义了”事务内的读行为”。两者经常搭配使用：

隔离级别 解决的问题 搭配传播行为
READ_UNCOMMITTED 无 几乎不用
READ_COMMITTED 脏读 REQUIRED / REQUIRES_NEW
REPEATABLE_READ（MySQL 默认） 脏读 + 不可重复读 REQUIRED
SERIALIZABLE 脏读 + 不可重复读 + 幻读 对一致性要求极高的场景

四、总结

事务失效分类

所有 @Transactional 失效都可以归结为以下三类：

类别 根因 典型场景
代理未生效 调用绕过了代理对象 自调用、private/final 方法、静态方法
异常未传播 事务拦截器没收到异常信号 try-catch 吞异常、错误的 rollbackFor
基础设施问题 事务管理的物理基础不存在 非事务引擎、多线程、错误的事务管理器

判断核心

一个 @Transactional 方法是否真的在事务中，取决于：

  1. 调用是否经过代理 — 必须通过 Spring 容器管理的代理对象调用
  2. 代理上的事务拦截器是否正确开启和结束事务 — 异常能否传播到拦截器
  3. 底层设施是否正确 — 数据库引擎、事务管理器、线程上下文

记忆口诀

代理要经过、异常要抛出、引擎要支持、线程要对上。

排查优先级

  1. ✅ 先确认调用链是否经过了 Spring 的代理对象（占 80% 失效场景）
  2. ✅ 再检查异常是否传播到事务拦截器
  3. ✅ 最后排查数据库引擎、多线程等基础设施问题

代理机制是 Spring 事务的唯一入口，绕过了代理就等于绕过了事务。
