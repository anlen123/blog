Skill 命中率保证策略

发表于2026-07-24|更新于2026-07-24|AI
|浏览量:

一、命中率的瓶颈在哪里？

Skill 的触发依赖 LLM 阅读 skill 描述 → 判断是否匹配用户意图 这个过程。问题出在：

问题 说明
描述冲突 两个 skill 的描述都覆盖了同一个关键词（比如 pdf 和 docx 都可能匹配”处理文件”）
描述模糊 “当用户需要创建文档时使用”——到底是指什么文档？
上下文窗口竞争 skill 列表在 system prompt 里，数量越多，每个 skill 分到的”注意力”越少
LLM 的贪心匹配 模型倾向于选择第一个”看起来相关”的 skill，而不是最精确的那个

二、四大核心策略

1. 描述场景而非能力（最关键）

这是最容易被忽视的。很多 skill 描述写成了能力说明书：

核心区别： 能力描述需要模型做一次语义推理（”合并 PDF” ⊆ “处理 PDF” 吗？），场景描述只需要做一次模式匹配（用户说的话里有没有这些字面片段）。LLM 在语义推理上会出错，但在字面/近字面匹配上准确得多。

原则：

  • 明确列出触发词（用户会怎么说话）
  • 区分度优先于覆盖面——宁可漏掉边缘场景，也不要和其他 skill 撞车

2. 建立 Tree（层级 Skill 体系）

利用目录级 scope 天然形成树状结构：

Tree 的好处：

  • 每个节点只需要和自己的兄弟节点区分，不需要和全局所有 skill 竞争
  • 模型先路由到子树，再在子树内精确匹配——两步路由，每步的候选集都很小
  • 目录 scope 是物理隔离，apps/web:deploy 和 apps/api:deploy 永远不会同时出现在候选列表里

3. 表明不适用场景（负向描述）

负向描述不是”建议”，是必须品。它帮模型做减法——把不相关的 skill 从候选集里直接踢出去：

为什么负向描述比正向更关键： 正向描述划定了 skill 的边界，负向描述修补了边界上的漏洞。两个 skill 撞车位置往往是边缘地带——恰好是负向描述能解决的地方。

4. 召回 + 重排（两阶段架构）

这是最工程化的方案。单阶段匹配做不到高精度，两阶段把问题拆开：

对比：

维度 单阶段 两阶段
候选集大小 N 个全部 K 个（K=3~5）
每个候选的注意力 1/N 1/K（大得多）
区分难度 从 N 个里选 1 个 从 K 个里确认最对的
负向描述的作用 被稀释 集中在候选对比上

三、辅助手段

用 skill-creator 做基准测试

  • Eval 测试：用一组用户输入测试 skill 是否正确触发
  • 方差分析：多次运行看触发稳定性
  • 描述优化：对照测试结果调优描述

控制 Skill 数量

不是所有 workflow 都值得做成 skill：

  • 高频 + 固定流程 → 适合做成 skill
  • 低频 / 一次性 → 用指令或直接描述即可
  • 变体太多 → 不适合，LLM 很难判断该不该触发

四、可操作的检查清单

添加新 skill 时，过一遍：

  1. ☐ 描述里有没有用户会怎么说话的场景触发词？（而非能力说明）
  2. ☐ 有没有写清楚什么情况下不要触发？（负向排除）
  3. ☐ 在 Tree 里的位置是否合理？兄弟节点之间有没有冲突？
  4. ☐ 拿 10 条真实用户输入测试，命中率 > 90%？
  5. ☐ 这个 skill 的使用频率值得占用 prompt 空间吗？

五、总结

Skill 命中率的保证 = 写好场景触发词（recall）+ 写好排除条件（负向过滤）+ 用 Tree 缩小搜索空间 + 召回重排两阶段架构 + 用 skill-creator 做定量测试。

最终的公式：

在 Claude Code 当前框架下，前三个手段已经能做到 90%+ 的命中率。两阶段 recall+rerank 是进一步提升到 95%+ 的理想方向。
