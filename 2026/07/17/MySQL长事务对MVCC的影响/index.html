MySQL 长事务对 MVCC 的影响

这是面试高频题，也是线上故障的常见根源。要理解长事务的危害，必须先清楚 MVCC 的几个核心组件。

一、MVCC 核心组件速览

InnoDB 的 MVCC（多版本并发控制） 通过维护同一行数据的多个版本，实现读写不阻塞。关键组件：

组件 作用
Undo Log（回滚日志） 记录行数据的旧版本，用于事务回滚和构造一致性读的快照
Read View（读视图） 事务启动时记录当前活跃事务列表，决定哪些数据版本对本次查询可见
Purge Thread（清理线程） 异步清除不再被任何事务需要的旧版本数据

二、长事务的 6 大影响

1. Undo Log 堆积（最严重）

这是长事务最致命的后果：

后果：

  • Undo 表空间（innodb_undo_*）持续膨胀，可能导致磁盘写满
  • 即使长事务最终提交，已膨胀的空间也不会自动回收

2. Purge Thread 被”卡住”

  • trx_rseg_history_len（undo 历史链表长度）飙升至几百万甚至上千万
  • Purge 线程虽然还在工作，但能清理的只是比长事务 Read View 更老的数据（几乎没有）
  • 历史链表越长，每次有事务提交时查找”最老活跃 Read View”的开销越大

3. 查询性能退化

退化类型 原因
全表扫描变慢 主键 B+Tree 中标记删除的行无法物理删除，叶子节点膨胀
二级索引回表变慢 索引中指向的旧版本主键记录堆积，回表时遍历版本链更长
Buffer Pool 污染 大量 undo 页频繁换入换出，挤走真正的热数据

4. 表空间膨胀（磁盘）

  • 被标记删除的行不能物理清理，ibd 文件持续增长
  • Undo 表空间不可逆地膨胀
  • 即使长事务最终提交，释放的空间也不会还给操作系统（需要 OPTIMIZE TABLE 或重建表）

5. 读取”过期”数据

五、应对策略

策略 操作 说明
预防 innodb_undo_log_truncate = ON 启用 undo 表空间自动截断
预防 SET SESSION max_execution_time = 30000 单条 SQL 最长执行 30 秒
预防 innodb_lock_wait_timeout = 10 锁等待超时 10 秒自动放弃
检测 定时查询 INNODB_TRX，告警运行超过 60 秒的事务 Prometheus + Grafana 或简单 cron
止损 KILL <connection_id> 杀掉长事务，让 purge 恢复
事后 innodb_purge_threads = 4 增加 purge 并行度加速清理
事后 OPTIMIZE TABLE xxx 或 ALTER TABLE xxx ENGINE=InnoDB 重建表回收空间

六、线上排查口诀

七、总结

长事务对 MVCC 的核心危害是阻止 undo log 被 purge——一个事务拖得越久，它身后堆积的”历史版本垃圾”就越多，最终导致：

  1. Undo 表空间膨胀 → 磁盘告警
  2. History list 暴涨 → Purge 线程空转
  3. 查询变慢 → 主键 B+Tree 膨胀、回表版本链变长
  4. 锁等待链 → 连接池打满 → 服务不可用

线上只要出现一条持续数小时未提交的事务，就足以拖垮整个实例。 预防的核心是：设置合理的超时参数 + 监控活跃事务时长 + 及时发现和 kill。
