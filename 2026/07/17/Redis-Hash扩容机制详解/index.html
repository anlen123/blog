Redis Hash 扩容机制详解（1000 万数据场景）

Redis Hash 底层用字典（dict） 存储，1000 万条数据要经历 20 多次扩容。如果一次性搬完，主线程会卡住数秒——这对 Redis 单线程模型来说是致命的。Redis 的解决方案是渐进式 rehash。

一、底层数据结构

关键设计：ht[0] 和 ht[1] 两个 table 并存。平时只用 ht[0]，rehash 时 ht[1] 是扩容后的新 table，ht[0] 中的数据逐步迁移过去。

二、扩容触发条件

扩容有两个判断条件（且需 dict_can_resize = 1）：

条件 规则 设计意图
负载因子 ≥ 1 used / size >= 1，且无 BGSAVE / BGREWRITEAOF 避免写时复制导致内存翻倍
负载因子 > 5 used / size > dict_force_resize_ratio = 5 情况紧急，强制执行，无视 BGSAVE

三、核心机制：渐进式 Rehash

Redis 绝对不会一次性迁移所有数据，而是”化整为零”。

六、优化建议（对应 1000 万级 Hash）

建议 说明
避免大量删除 删到不足 10% 会触发缩容，之后再加回来又扩容——反复 rehash 浪费 CPU
管道写入 批量写入用 PIPELINE，加速写入的同时也加速 rehash
配置保护 activerehashing yes（默认开启），定时器主动加速 rehash
分片思想（推荐） 1000 万的大 Hash，拆成 100 个小 Hash，各存 10 万

分片方案（最佳实践）

分片的好处：

  • 单个 Hash 的 dict 更小，rehash 成本更低
  • 避免了单个大 key 成为热点
  • 删除一个分片的数据不会影响其他分片
  • Redis Cluster 下可以分散到不同节点

八、与 Java HashMap 的对比

维度 Redis dict Java HashMap
扩容方式 渐进式 rehash，分步迁移 一次性 resize，全部 rehash
阻塞影响 每次请求只阻塞 1 个 bucket 扩容瞬间 STW（尤其 JDK 7 头插法死循环）
并发 单线程，天然无并发问题 JDK 7 有死循环 bug，JDK 8 改用尾插法
缩容 支持（负载因子 < 0.1） 不支持（只扩容不缩容）
bucket 数 始终 2^n 始终 2^n

九、总结

Redis Hash 扩容的核心设计哲学是化整为零：

  1. 两个 hash table 并存（ht[0] + ht[1]），数据逐步从旧表迁移到新表
  2. 每次操作只搬一点点（1 个 bucket），绝不阻塞主线程
  3. 三个触发点：请求触发 + 定时器触发 + 主动查询触发，多管齐下
  4. 1000 万数据扩容：全过程中单次请求的额外开销只是一个 bucket 的迁移，用户无感知

对于大 Hash，业务分片是最佳实践——将一个大 key 拆成多个小 key，既降低了单次 rehash 的规模，又避免了单个大 key 成为热点或慢操作源。
