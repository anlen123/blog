Spring 三级缓存为什么必须是三级——循环依赖与 AOP 的渐进推导

Spring 三级缓存为什么必须是三级

“Spring 用三级缓存解决循环依赖”——这句话人人会背，但很少有人能说清：为什么必须三级？一级、二级分别解决了什么问题、又卡在什么问题？ 本文从零开始渐进推导，把三级缓存的必要性彻底讲透。

相关知识闭环：Spring Bean 生命周期详解 · Spring AOP 与事务失效原理详解

一、结论先行

方案 解决循环依赖 并发拿不到半成品 AOP 代理一致 代价
只有一级缓存 表面解决 ✗ ✗（B 拿 raw，全局是 proxy） 无
一级 + 二级 ✓ ✓ ✗（早期引用是 raw，无增强） 半成品隔离
一级 + 二级 + 三级 ✓ ✓ ✓（按需提前代理且只代理一次） 多一层 ObjectFactory

三级缓存的本质：把”是否提前暴露、暴露成 raw 还是 proxy”的决策，延迟到”真正发生循环依赖的那一刻”，由 getEarlyBeanReference 的 BeanPostProcessor 链决定。一级管成品、二级管”已暴露的早期引用”、三级管”可暴露的工厂”。

二、前提：问题发生在哪个时间点

回顾 Bean 生命周期中的关键顺序：

  • 循环依赖发生在实例化和属性填充之间；
  • AOP 代理在初始化之后（postProcessAfterInitialization）才生成。

核心矛盾：

A 必须在”还没初始化”时就把自己交给 B（否则 B 创建不下去），但 A 的最终形态——AOP 代理——要到初始化之后才产生。

三级缓存要解决的就是”提前暴露的对象 vs 最终形态的对象“如何保持一致。

三、方案一：只用一级缓存（singletonObjects）

做法：实例化后直接把半成品 A 放进 singletonObjects，B 创建时从里面拿。

3.1 解决的问题

循环依赖”表面上”通了——B 能拿到 A 的引用，A→B→A 的链路能走完。

3.2 无法解决的问题

① 并发拿到生命周期不一样的对象

另一个线程 T2 恰好在 A 属性填充/初始化之前调用 getBean("A")，直接从一级缓存拿到半成品 A——属性是 null、初始化方法没执行。getBean 的语义被破坏：它应该永远返回完整可用的 Bean。

② AOP 代理不一致（致命）

A 初始化完成后，postProcessAfterInitialization 生成代理，此时把代理放进一级缓存（覆盖 raw A）。但 B 手里拿的已经是原始对象：

B 调用 A 的 @Transactional 方法 → 没走代理 → 事务失效。同一个 bean 在系统里出现两个实例（raw + proxy），互相矛盾。

所以纯一级缓存在 Spring 里根本不存在——singletonObjects 只放成品，这是它的语义底线。

四、方案二：一级 + 二级缓存（earlySingletonObjects）

做法：一级缓存只放成品；半成品放进二级缓存 earlySingletonObjects。getBean 先查一级，查不到且该 bean 正在创建中（isSingletonCurrentlyInCreation），就从二级拿。

4.1 解决的问题

① 一级缓存语义变干净

singletonObjects 永远只放完整 Bean，并发下 getBean 不会再拿到半成品（非循环依赖场景）。

② 并发拿到同一个早期引用

多个线程同时 getBean 正在创建的 A，都从二级缓存拿到同一个 raw A 实例，引用一致，不会各拿各的、也不会重复创建。

4.2 无法解决的问题：AOP 动态代理

二级缓存里存的是原始对象（实例化后、初始化前的形态）。A 的代理要在 postProcessAfterInitialization（初始化之后）才创建——太晚了，B 早就拿着 raw A 了。

那能不能补救：实例化后立即创建代理再放二级缓存？走不通，有三个原因：

问题 说明
性能浪费 绝大多数 Bean 根本不参与循环依赖，白白提前包一层代理
双重代理 提前包了一层，初始化后 postProcessAfterInitialization 再包一层 → 代理套代理
语义破坏 代理创建依赖 BeanPostProcessor 链和 Advisor 匹配，在初始化前强行代理，增强时机不对（依赖初始化状态的 Advisor 会拿到错误结果）

结论：

不能”对所有 Bean 提前代理”，只能”延迟到真正发生循环依赖的那一刻再决定是否代理”——这就是三级缓存存在的意义。

问题 解法

六、补充：构造器注入的循环依赖为什么解决不了

三级缓存的工厂是在实例化之后才注册的，而构造器循环依赖发生在实例化阶段——此时 Bean 还没 new 出来，无物可暴露，只能抛 BeanCurrentlyInCreationException：

这也是为什么 Spring 官方建议循环依赖用 setter/字段注入，以及为什么 @Lazy 可以绕过构造器循环依赖（延迟注入代理，不立即触发创建）。

七、面试回答版

面试官：Spring 为什么用三级缓存解决循环依赖？用两级行不行？

建议回答结构：

“循环依赖发生在实例化之后、属性填充之时，而 AOP 代理是在初始化之后才生成的，这就产生了’提前暴露的对象 vs 最终形态的对象’如何保持一致的问题。

如果只用一级缓存，实例化后直接把半成品放进去，有两个问题：一是并发下 getBean 会拿到没初始化完的半成品，破坏 getBean 语义；二是 A 初始化后生成 AOP 代理放进一级缓存，但 B 手里拿到的还是原始对象，@Transactional 这些增强在 B 这边全部失效。

所以一级缓存只放成品，加一个二级缓存放早期引用，解决并发下引用一致的问题。但二级缓存存的是原始对象，AOP 代理创建得太晚，B 拿到的还是没有增强的 raw 对象。

如果改成实例化后立刻对所有 Bean 创建代理，又存在性能浪费、双重代理、增强时机错误的问题。所以需要三级缓存：实例化后先放一个 ObjectFactory，只有真正发生循环依赖时才调用它，通过 getEarlyBeanReference 链按需提前创建代理，结果缓存到二级缓存保证只创建一次。这样 B 拿到的早期引用和最终存入一级缓存的是同一个代理对象，AOP 和循环依赖就都解决了。”

总结

一句话记忆：

一级管成品、二级管”已暴露的早期引用”、三级管”可暴露的工厂”；工厂按需触发，触发时由 getEarlyBeanReference 决定暴露 raw 还是 proxy，且只暴露一次。

Spring 用三级缓存不是炫技，而是把”是否提前暴露、暴露成什么形态”的决策权交还给了 BeanPostProcessor 链——这也是 Spring 整个框架”扩展点优先”设计哲学的缩影。
