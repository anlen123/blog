一、什么是分布式事务

1.1 定义

分布式事务是指事务的参与者、支持事务的服务器、资源服务器以及事务管理器分别位于分布式系统的不同节点之上，需要保证这些操作要么全部成功、要么全部失败。

本地事务（如单库单表的 @Transactional）依赖数据库自身的 ACID 能力，而分布式事务要跨多个数据库、多个服务，数据库的本地事务无法保证全局一致性，因此需要额外的协调机制。

1.2 典型产生场景

场景 例子
跨库事务 订单库与库存库分属不同数据库，下单要同时扣库存
微服务调用 订单服务调用库存服务、支付服务、积分服务
分库分表 数据分散在多个分片中，一次业务操作涉及多个分片
多系统异构 调用第三方系统（支付、短信、物流），无法控制其内部事务

1.3 常见业务案例：下单扣库存

任何一个环节失败，都需要回滚其他环节，这就是分布式事务要解决的问题。

二、理论基础：CAP 与 BASE

2.1 CAP 定理

CAP 定理（Eric Brewer 提出）指出：一个分布式系统最多只能同时满足以下三个特性中的两个：

特性 含义
C（Consistency）一致性 所有节点在同一时刻看到的数据是一致的
A（Availability）可用性 系统在任意时刻都能响应请求（不保证返回最新数据）
P（Partition tolerance）分区容错性 网络分区发生时，系统仍能继续运行

网络分区（P）在分布式环境下不可避免，所以实际是在 CP 和 AP 之间做取舍：

  • CP 系统：放弃可用性，保证一致性。如 ZooKeeper、etcd（选主期间不可用）。
  • AP 系统：放弃强一致性，保证可用性，通过最终一致性收敛。如 Eureka、大部分微服务业务系统。

面试追问：CAP 中的 C 和 ACID 中的 C 一样吗？

不一样。ACID 中的 C 是事务内的一致性约束（约束不被破坏），CAP 中的 C 是多副本之间的一致性（副本间数据相同）。ACID 的 C 关注单机数据合法，CAP 的 C 关注分布式副本收敛。

2.2 BASE 理论

BASE 是 CAP 中 AP 方案的延伸，由 eBay 架构师 Dan Pritchett 提出：

缩写 含义 说明
BA（Basically Available）基本可用 允许部分功能降级 如双十一期间部分服务限流降级
S（Soft state）软状态 允许中间状态 数据副本之间允许存在短暂不一致
E（Eventually consistent）最终一致 经过一段时间后达到一致 通过消息、重试、对账等手段收敛

核心思想：放弃强一致性，接受”最终一致”，用”异步 + 重试 + 对账”来兜底。

2.3 强一致 vs 最终一致

  • 强一致（CP 路线）：2PC、3PC、XA、Seata AT 模式的某些环节。适合对一致性要求极高的场景（如转账）。
  • 最终一致（AP 路线）：TCC、消息事务、SAGA、最大努力通知。适合大多数互联网业务（如订单、积分）。

面试高频问题：为什么互联网公司很少用强一致的 2PC/XA？
因为 XA 需要数据库原生支持（Oracle、MySQL 5.7+ 都支持 XA），且采用同步阻塞协议，协调者单点、参与者阻塞、性能差，在并发量大的互联网场景下不适用。

三、2PC 两阶段提交

3.1 角色

  • 协调者（Coordinator）：事务管理器，负责发起和决策。
  • 参与者（Participant）：资源管理器，如各数据库、各服务。

3.2 流程

第一阶段：准备（Prepare / Vote）

第二阶段：提交（Commit / Abort）

3.3 经典实现：XA 协议

  • XA 是 X/Open 组织定义的分布式事务规范，由数据库原生支持。
  • 角色：AP（应用）、TM（事务管理器）、RM（资源管理器，数据库）。
  • Java 中对应 JTA（Java Transaction API），实现如 Atomikos、Narayana。

3.4 缺点（面试重点）

问题 说明
同步阻塞 Prepare 之后参与者资源被锁定，期间不能做其他事
单点问题 协调者宕机，整个事务悬挂，参与者无法决定提交还是回滚
数据不一致 第二阶段 Commit 广播时部分参与者宕机，会出现部分提交部分未提交
性能差 多轮网络通信 + 长锁，吞吐量低

2PC 无法解决”Commit 阶段网络中断”导致的脑裂问题——这也是 3PC 引入超时机制的原因。

四、3PC 三阶段提交

4.1 改进点

3PC 在 2PC 基础上引入超时机制，并在两阶段之间增加一个 CanCommit 询问阶段：

阶段 动作
1. CanCommit 协调者询问参与者”能否提交”，参与者只做可行性检查，不执行事务
2. PreCommit 参与者执行事务写日志但不提交，返回结果
3. DoCommit 协调者根据 PreCommit 结果决定 Commit 或 Abort

关键改进：

  1. 参与者引入超时，长时间收不到协调者指令时自动提交（避免无限阻塞）。
  2. CanCommit 阶段提前过滤掉无法提交的参与者，减少无谓的资源占用。

4.2 缺点

  • 3PC 依然存在数据不一致的可能：参与者超时自动提交，但此时协调者已决定回滚，就会不一致。
  • 实现复杂，实际落地极少。面试中更多是考察”你是否理解它相对 2PC 改进了什么”。

五、TCC 补偿事务

5.1 概念

TCC（Try-Confirm-Cancel）是业务层面的分布式事务方案，把一次业务操作拆成三个阶段，由业务方自己实现，不依赖数据库 XA：

阶段 动作 说明
Try 预留资源 冻结库存、冻结金额、生成待支付订单
Confirm 确认执行业务 真正扣减库存、扣款、订单生效；要求幂等
Cancel 取消、释放资源 解冻库存、退款、订单作废；要求幂等

5.2 代码示例（扣减库存）

5.3 优缺点

优点：

  • 性能好：Try 阶段只加短暂业务锁，不像 2PC 全程锁资源。
  • 灵活：不依赖数据库 XA，任何存储都能用。

缺点：

  • 侵入性强：每个业务都要写 Try/Confirm/Cancel 三套逻辑，开发成本高。
  • 空回滚、幂等、悬挂问题需要额外处理（见下）。

5.4 三个经典坑（面试高频）

问题 场景 解法
空回滚 Try 未执行（网络超时/服务未收到请求），Cancel 却执行了 Cancel 前先查事务记录，Try 未成功则 Cancel 直接返回成功
幂等 Confirm/Cancel 可能被重试多次 用事务状态表（Try 成功记一条记录，带唯一事务 ID）+ 状态机判断
悬挂 Try 请求超时后 Cancel 先执行完，Try 的请求才到达，导致资源被永久冻结 Try 执行前查事务记录，若 Cancel 已执行则 Try 直接丢弃（”空执行”）

六、本地消息表

6.1 思路

由 eBay 提出，核心思想：事务与消息同库落盘，再异步投递。

6.2 流程

6.3 关键点

  • 业务表与消息表在同一个本地事务里写入，保证”业务成功则消息一定存在”。
  • 投递失败靠定时轮询重发兜底，天然具备”至少一次投递”语义。
  • 消费方必须幂等（因为可能重复投递）。

6.4 优缺点

优点：实现简单，不依赖 MQ 的高级特性，可靠性高（消息不会丢）。
缺点：消息表和业务耦合在同一库，库压力大；需要自己写轮询任务；没有消息确认/重试的完整闭环（要自己实现）。

面试常问：本地消息表和事务消息的区别？
本地消息表是”业务方自己写消息表 + 自己轮询”；事务消息是 MQ 中间件（如 RocketMQ）原生支持”半消息 + 回查”机制，把消息表的逻辑内聚到了 Broker 里，业务方只需实现一个回查接口。

八、最大努力通知

8.1 概念

最大努力通知：发起方在完成本地事务后发送消息通知，接收方处理失败则按退避策略反复重试（如 1s、5s、10s、30s…递增），直到成功或达到最大次数；若最终仍失败，则进入人工对账/补偿流程。

8.2 典型场景

  • 支付结果通知：支付宝、微信支付回调商户系统。
  • 第三方对接：WMS 出库结果通知、短信/邮件发送结果确认。

8.3 流程

8.4 特点

优点 缺点
实现最简单，双方解耦 一致性最弱：只保证”尽力通知”，不保证对方一定成功
配合查询/对账接口可落地 需要接收方提供查询接口做最终兜底

面试要点：最大努力通知不保证最终一致性一定达成，它是”概率上尽力 + 对账兜底”。适合对一致性要求不高的场景。

十、Seata 分布式事务框架

10.1 什么是 Seata

Seata（Simple Extensible Autonomous Transaction Architecture）是阿里巴巴开源的分布式事务框架，也是目前国内最主流的方案。它把一次分布式事务抽象为三个角色：

角色 英文 职责
事务协调器 TC（Transaction Coordinator） 维护全局事务状态，负责全局提交/回滚（独立部署）
事务管理器 TM（Transaction Manager） 开启/提交/回滚全局事务（业务方）
资源管理器 RM（Resource Manager） 管理分支事务，向 TC 注册并报告状态（业务方数据源代理）

10.2 四种模式对比（面试必背）

模式 原理 一致性 侵入性 性能 适用场景
AT 基于数据源代理 + 全局锁 + undo_log 自动回滚 最终一致 低（近似无侵入） 中 大多数 CRUD 业务，最常用
TCC 业务方实现 Try/Confirm/Cancel 最终一致 高 高 强隔离、高性能场景
SAGA 状态机编排 + 补偿 最终一致 中 高 长事务、业务流程
XA 基于数据库 XA 协议 强一致 低 低 一致性要求极高的存量系统

10.3 AT 模式核心原理（面试重点）

AT 模式是 Seata 的招牌，它做到”对业务代码几乎无侵入“，靠三个机制：

① 一阶段：业务 SQL + 生成 undo_log（同一本地事务）

② 二阶段提交：异步删除 undo_log（因为一阶段已经提交了本地事务，全局提交很快）

③ 二阶段回滚：用 undo_log 反向补偿

④ 全局写锁：一阶段执行业务 SQL 时会获取全局锁（记录在 TC 的全局锁表中），防止其他全局事务并发修改同一行导致回滚时覆盖脏数据。

10.4 AT 模式使用示例

只要库存服务、账户服务的数据库配置了 Seata 数据源代理，业务代码不需要任何改动，这就是 AT 模式的”无侵入”。

10.5 Seata 部署架构

TC 需要注册中心（Nacos/Eureka）和配置中心，Seata Server 与业务服务之间通过长连接通信。

10.6 面试常见追问

Q：AT 模式和 TCC 模式怎么选？
A：AT 无侵入、开发成本低，但一阶段要拿全局写锁，并发写同一行时性能差；TCC 需要写三套代码，但 Try 阶段业务锁短、性能好。简单业务用 AT，高并发强隔离场景用 TCC。

Q：AT 模式什么时候会脏写？
A：一阶段本地事务已提交、全局事务未提交时，其他本地事务（非 Seata 管理的）修改了同一行数据，回滚时 afterImage 校验不通过，需要人工介入。解决：业务上避免”非 Seata 事务”并发写同一行，或使用全局锁表保证串行。

十一、各方案对比与选型

11.1 总览表

方案 一致性 侵入性 性能 实现复杂度 典型场景
2PC / XA 强一致 低（数据库支持） 低 中 银行、金融核心（存量）
3PC 弱于 2PC 低 中 高 基本无落地
TCC 最终一致 高 高 高 高并发强隔离（如秒杀扣库存）
本地消息表 最终一致 中 中 中 无事务消息 MQ 的老系统
事务消息 最终一致 中 高 中 RocketMQ 生态（订单、积分）
最大努力通知 最终一致（最弱） 低 高 低 支付回调、第三方对接
SAGA 最终一致 中 高 中高 长事务、多步骤流程
Seata AT 最终一致 极低 中 低（框架集成） 微服务常规业务，首选
Seata TCC 最终一致 高 高 高 Seata 生态的高性能场景

11.2 选型建议（面试话术）

  1. 能不用分布式事务就不用：优先考虑本地事务 + 异步解耦、事务边界重设计（如”先扣款后发货”拆成两段）。
  2. 需要强一致且并发低：XA（数据库原生支持）。
  3. 常规微服务业务：首选 Seata AT（无侵入、社区成熟）。
  4. 高并发 + 核心资金链路：TCC（自己控制资源锁粒度）。
  5. 异步解耦场景：RocketMQ 事务消息（订单创建 + 发消息）。
  6. 长流程、跨系统：SAGA。
  7. 对账兜底：任何方案都要配合对账 + 人工补偿，保证最终一致。

十二、面试高频问题清单

基础理论类

  1. 什么是分布式事务？为什么本地事务解决不了？
    本地事务的 ACID 只对单库有效，跨库/跨服务无法保证原子性，需要全局协调。

  2. CAP 是什么？为什么只能三选二？
    网络分区不可避免，P 必须满足；分区时要么保一致放弃可用（CP），要么保可用放弃强一致（AP）。

  3. BASE 理论讲的是什么？
    基本可用 + 软状态 + 最终一致，是 AP 路线的落地指导。

  4. 强一致和最终一致分别有哪些方案？
    强一致：2PC/XA/3PC；最终一致：TCC、本地消息表、事务消息、SAGA、最大努力通知。

方案原理类

  1. 2PC 的两个阶段分别做什么？有什么致命缺点？
    准备阶段（执行不提交 + 投票）、提交阶段（广播提交/回滚）。缺点：同步阻塞、协调者单点、脑裂不一致。

  2. 3PC 相对 2PC 改进了什么？
    增加 CanCommit 预检阶段 + 参与者超时机制，减少阻塞窗口，但依然不能保证绝对一致。

  3. TCC 是什么？Try/Confirm/Cancel 分别做什么？
    预留 → 确认 → 取消，业务层补偿，要求每个操作幂等。

  4. TCC 的空回滚、幂等、悬挂怎么处理？
    事务状态表 + 唯一事务 ID + 状态机校验，Try 前查状态、Cancel 前查状态、防重入。

  5. 本地消息表的原理是什么？有什么缺点？
    业务与消息同库同事务写入，定时轮询投递。缺点：库耦合、要自己写轮询与重试。

  6. RocketMQ 事务消息的原理？半消息是什么？回查机制怎么工作？
    半消息对消费者不可见；本地事务执行后 Commit/Rollback；超时由 Broker 回查 Producer 的本地事务状态。

  7. 最大努力通知和可靠消息最终一致有什么区别？
    事务消息/本地消息表保证”消息一定投递”；最大努力通知只”尽力投递 + 重试 + 对账兜底”，不保证成功。

  8. SAGA 是什么？编排和协调两种模式的区别？
    子事务 + 补偿；编排靠事件驱动（轻量），协调靠中央引擎（可控性强）。

Seata 类

  1. Seata 的 TC/TM/RM 分别是什么角色？
    TC 协调器（独立部署）、TM 全局事务管理、RM 分支事务资源管理。

  2. Seata AT 模式原理？为什么对业务无侵入？
    数据源代理自动记录 beforeImage/afterImage 到 undo_log，与业务 SQL 同事务；回滚时反向补偿；全局写锁防脏写。

  3. Seata 四种模式的区别与选型？
    AT（无侵入常用）/ TCC（高性能强隔离）/ SAGA（长事务）/ XA（强一致）。

  4. AT 模式的全局锁是什么？什么时候释放？
    一阶段执行业务 SQL 前获取全局锁，二阶段全局提交/回滚完成后释放，避免并发全局事务交叉修改。

实战类

  1. 你们项目里分布式事务是怎么做的？为什么这么选？
    建议回答：先讲业务场景 → 对比 2PC/TCC/消息 的取舍 → 说明选择了 Seata AT 或事务消息 → 讲落地的对账/幂等/重试细节。

  2. 分布式事务里如何保证幂等？
    唯一业务主键 + 唯一索引、状态机字段、Redis setnx 防重、MQ 消息去重表。

  3. 消息重复消费怎么办？
    消费方幂等：唯一键查重、状态机判断、Redis 去重。

  4. 最终一致性方案里，对账系统怎么设计？
    定时任务扫描”本地已成功但对方状态未知”的记录 → 调用查询接口核对 → 差异记录人工处理或自动补偿。

总结

分布式事务的面试考察主线非常清晰：

记住一条主线：互联网业务 90% 的场景用”最终一致”就够了，面试时能把每个方案的原理、优缺点、适用场景讲清楚，再把 Seata AT 的原理吃透，分布式事务这道题就稳了。
