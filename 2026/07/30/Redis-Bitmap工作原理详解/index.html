Redis Bitmap 工作原理详解

面试常问：“Redis Bitmap 是什么？底层怎么存的？为什么省内存？BITCOUNT 怎么实现？”

一句话先记住本质：

Bitmap 不是独立的数据类型，本质是 String（SDS），只是把它当”位数组”用——每个 bit（0/1）就是一个状态位，1 个用户只占 1 位，8 个用户才 1 字节。

1.2 位寻址计算（核心原理）

关键：Redis 采用大端位序（MSB first）——每个字节内，最左边（最高位）是 bit 0：

offset 字节索引 位索引 位置
0 0 7 第 1 字节最高位
7 0 0 第 1 字节最低位
8 1 7 第 2 字节最高位
100 12 3 第 13 字节第 4 位

二、自动扩容机制（稀疏特性）

  • 设置一个超出当前长度的 offset，Redis 自动用 \0（零字节）填充中间部分，再写目标位。
  • SETBIT 依然是 O(1)，与 offset 大小无关。
  • 注意：GETBIT 越界不报错，返回 0。

⚠️ 坑：大 offset 会产生大 key。虽然中间全是 0，但字符串长度就是 offset/8，内存照样占。用户 ID 是 10 亿级别时，一个 bitmap 就是 125MB，要评估是否适合。

三、内存计算（为什么省内存）

场景 传统存储（每用户 8 字节） Bitmap 节省
1 亿用户签到 800MB 12.5MB 64 倍
10 亿用户活跃统计 8GB 125MB 64 倍

本质：1 个用户只占 1 个 bit，8 个用户才 1 字节。

四、命令详解

命令 作用 复杂度 说明
SETBIT key offset v 设置某位 O(1) 返回该位原值
GETBIT key offset 读取某位 O(1) 越界返回 0
BITCOUNT key [start end] 统计 1 的个数 O(N) 底层查表 + SWAR
BITPOS key bit 找第一个 1/0 的位置 O(N)
BITOP AND/OR/XOR/NOT dest k1 k2 位运算 O(N) 多 bitmap 合并，求留存/交集
BITFIELD key GET/SET/INCRBY 批量操作位域 O(N) 支持 u8/i16 等类型、溢出控制 WRAP/SAT/FAIL

示例：统计 7 月连续签到 7 天的用户

七、面试高频点清单

  1. Bitmap 是什么类型？ String，不是独立类型；最大 512MB → 最多 2^32 位（约 42.9 亿位）。
  2. 位序是什么？ 大端（MSB），bit = 7 - (offset % 8)。
  3. 为什么省内存？ 1 位 1 个状态，8 用户 1 字节，比传统存储省几十倍。
  4. SETBIT 大 offset 会怎样？ 自动补零扩容，O(1)，但会产生大 key，内存按 offset/8 算。
  5. GETBIT 越界？ 返回 0 不报错。
  6. BITCOUNT 怎么实现？ 查表法 + SWAR，O(N) 按字节处理。
  7. 和 HyperLogLog 的区别？ Bitmap 精确计数（1 用户 1 位）；HLL 近似计数（12KB 存上亿基数，误差 ~0.81%）。百万以内用 Bitmap，亿级去重用 HLL。

总结

三句话记住：

  1. Bitmap = String 的位视图：字节数组 + 大端位序，byte = offset >> 3，bit = 7 - (offset & 7)。
  2. 省内存靠”1 位 1 状态”：8 用户 1 字节，比传统存储省 64 倍；代价是稀疏大 offset 会撑大 key。
  3. BITCOUNT 快靠查表 + SWAR：按字节处理而非按位处理，亿级位图毫秒级统计。
