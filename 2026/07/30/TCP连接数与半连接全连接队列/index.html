服务器能撑多少 TCP 连接？半连接与全连接队列内存解析

面试高频双连问：“一台服务器最多能建立多少 TCP 连接？””半连接队列和全连接队列，哪个阶段最占内存？”

本文分两部分讲透：先看连接数的决定因素（木桶效应），再看握手两个队列的内存真相。

相关知识闭环：Java 分布式事务详解 · gRPC 与 Thrift 序列化机制详解

一、服务器能承载多少 TCP 连接？

1.1 先给结论：取决于”短板”

木桶效应：哪个先到极限，连接数就卡在哪。逐项看：

① 文件描述符（FD）限制——最先撞的墙

Linux 一切皆文件，每个 TCP 连接占一个 fd：

限制 位置 默认值 调法
进程级 ulimit -n 1024 调到 100w（ulimit -n 1000000，systemd 里配 LimitNOFILE）
系统级 fs.file-max 由内存决定 /proc/sys/fs/file-max
硬上限 fs.nr_open 1048576 单进程 fd 上限

为什么默认只有 1024？ 早期防止进程耗尽系统资源的安全策略。生产环境第一步就是调大它——这是撑高连接数的起点。

② 内存——真正的瓶颈

每个连接的内核开销：

项目 大小（约）
struct sock（内核连接结构） ~2KB
fd / file 结构 ~1KB
收发缓冲区 4KB ~ 数百 KB（内核自动调节）

粗算：百万连接 ≈ 3~5GB 内核内存。C1M（单机百万连接）必须大内存机器 + 内核调优。

用户态模型同样致命：

模型 每连接成本 上限
BIO（一连接一线程） 1 个线程（~1MB 栈） 1w 连接就撑爆
epoll / NIO（事件驱动） 几乎为零（空闲连接） C10K 轻松，C1M 可期

epoll 是 C10K → C1M 的分水岭，面试常考。

③ 端口/四元组——服务端其实不受 65535 限制

一个 TCP 连接由四元组唯一确定：(源IP, 源端口, 目的IP, 目的端口)。

  • 服务端被动 accept：固定监听一个端口，连接数上限 = 客户端 IP × 客户端端口组合 → 理论上亿级，不受 65535 限制。
  • 客户端主动连接：源端口只有 65535 个（ip_local_port_range），单机主动连接上限约 6.5w，且被 TIME_WAIT 雪上加霜（2MSL 内端口不能复用，用 tcp_tw_reuse、调小 tcp_fin_timeout 缓解）。

面试题：“服务端为什么能接受超过 65535 个连接？” 因为被动接受方不受源端口限制，瓶颈在四元组组合数。

④ CPU 与带宽

  • 活跃连接才消耗 CPU 和带宽：握手/挥手、协议处理、业务逻辑。
  • 空闲长连接 CPU 占用 ≈ 0，但心跳保活（TCP keepalive / 业务心跳）会占资源。
  • 带宽是”活跃连接数”的瓶颈，不是”总连接数”的瓶颈——1w 个连接不发数据，带宽 0 占用。

⑤ 内核参数一览

参数 作用 说明
net.core.somaxconn 全连接队列上限 默认 4096，突发连接会溢出
net.ipv4.tcp_max_syn_backlog 半连接队列上限 默认 1024，防 SYN Flood
net.ipv4.tcp_syncookies SYN Cookie 开关 默认 1，半连接队列满时兜底
net.ipv4.ip_local_port_range 客户端源端口范围 客户端连接数上限
net.ipv4.tcp_fin_timeout TIME_WAIT 时长 默认 60s

1.2 实际量级（心里有个数）

量级 含义 需要什么
C10K 万级连接 epoll 即可，轻松
C100K 十万级 调大 fd + 足够内存
C1M 百万级 大内存 + 内核调优 + 压测，生产一般靠多机集群

确定方法：不是算出来的，是压测 + 监控出来的——用 ss -s 看连接数、free 看内存、cat /proc/sys/fs/file-nr 看 fd 水位，逐步加压找拐点。

二、半连接队列 vs 全连接队列，哪个最占内存？

2.1 两个队列在握手流程中的位置

半连接队列（SYN Queue） 全连接队列（Accept Queue）
存放时机 收到 SYN、发出 SYN+ACK 后 收到 ACK、三次握手完成后
连接状态 SYN_RECV（未完成握手） ESTABLISHED（已握手，等 accept）
上限参数 tcp_max_syn_backlog（默认 1024） somaxconn（默认 4096）+ listen backlog
满了怎么办 丢 SYN / 启用 SYN Cookie 丢 ACK（客户端重传）或 tcp_abort_on_overflow 直接发 RST

2.2 哪个最占内存？——分两个视角答（面试加分点）

视角一：看队列”条目”本身 → 半连接队列重得多

半连接队列条目 全连接队列条目
内容 tcp_request_sock（~300B）+ sk_buff 报文副本（保留 SYN 报文用于重传 SYN+ACK） 指针 / request_sock（轻量）
单个条目 约 1~2KB 几十字节

为什么半连接条目必须带报文副本？ 因为客户端 ACK 可能丢失，服务器要重传 SYN+ACK，就必须留着原始 SYN 的上下文——这就是它”重”的根源。

视角二：看连接”全生命周期” → ESTABLISHED 连接最占内存

真正的内存大头不在队列里，而在建立完成的连接上：struct sock（~2KB）+ 收发缓冲区（KB 级 ~ MB 级），连接存活多久就占多久。百万连接的机器，内存基本都花在这里。

结论一句话：

半连接队列是”最危险”的（条目重、易被打满）；ESTABLISHED 连接是”最占内存”的（sock + 缓冲区，量大且持久）。

2.4 面试话术模板

“半连接队列存的是 SYN_RECV 状态的未完成连接，每个条目包含 request_sock 和 SYN 报文副本（用于重传 SYN+ACK），单条目内存重，所以它既是资源瓶颈也是 SYN Flood 的攻击目标，满了靠 SYN Cookie 兜底；全连接队列存的是已完成握手、等待 accept 的连接，条目轻，满了丢 ACK 让客户端重传。但如果看整个连接生命周期，最占内存的是 ESTABLISHED 的完整连接——sock 结构加收发缓冲区，连接越多、活得越久，内存消耗越大。”

总结

三句话记住：

  1. 连接数 = 木桶效应：fd、内存、CPU、带宽、内核参数，谁先到极限谁说了算；服务端被动接受不受 65535 限制，真正的瓶颈是内存和 epoll 模型。
  2. 半连接队列最危险：条目带报文副本（1~2KB），是 SYN Flood 的攻击面，靠 SYN Cookie 兜底。
  3. ESTABLISHED 最占内存：完整 sock + 收发缓冲区，量大且持久，百万连接的机器内存大头全在这。
