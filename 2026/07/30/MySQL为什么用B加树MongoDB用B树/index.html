为什么 MySQL 用 B+ 树，MongoDB 用 B 树？

数据库面试高频题：“为什么 MySQL 用 B+ 树做索引，而 MongoDB 用 B 树？”

一句话先记住本质：

磁盘 IO 是数据库最大的瓶颈，树的高度 = 查询的 IO 次数。B 树和 B+ 树的区别，本质是”为了树更矮、查询更快，牺牲了什么”。而最终选择哪种结构，取决于数据模型和访问模式。

相关知识闭环：MySQL 锁机制详解 · MVCC 底层原理详解 · Redis Bitmap 工作原理详解

一、共同前提：为什么数据库都要”树形索引”

磁盘 IO 是最慢的环节（比内存慢几个数量级），所以索引设计的第一目标就是减少 IO 次数：

B 树/B+ 树都是多路平衡查找树：一个节点存多个 key，把树高压到 34 层，查询只要 34 次 IO。

两者的结构差异：

二、MySQL（InnoDB）为什么选 B+ 树

① 树更矮 → IO 更少（最核心）

InnoDB 默认页大小 16KB，B+ 树非叶子节点只存 key + 指针（约 14 字节/条），一页能装 约 1170 个 key：

3 层 B+ 树撑起 2000 万行，4 层能到 25 亿行——查询最多 3~4 次 IO。

如果换成 B 树：非叶子节点要连数据一起存（假设一行 1KB），一页只能装 16 个 key，树高指数级膨胀，同样千万行要 5~6 层 → IO 次数翻倍。

一句话：B+ 树用”非叶子不存数据”换来了更大的扇出（fanout），树更矮，查询更快。

② 范围查询/排序高效（SQL 的特性需求）

SQL 大量使用 >、<、BETWEEN、ORDER BY、GROUP BY：

叶子链表是 B+ 树为”范围查询”量身定做的，这正是关系型数据库最频繁的操作。

③ 查询性能稳定

B 树 B+ 树
数据位置 可能在第 1 层，也可能在第 5 层 全部在叶子
查询耗时 1~5 次 IO 不等，不可预估 每次都走完整棵树，IO 次数相同

B+ 树任何查询耗时都稳定，对数据库优化器友好。

④ 与 InnoDB 聚簇索引天然契合

  • InnoDB 主键索引（聚簇索引）叶子存整行数据，二级索引叶子存主键值（回表）；
  • 数据全部沉到叶子 + 叶子有序链表 → 按主键顺序扫描就是物理顺序；
  • MVCC 版本链挂在行上，也集中在叶子层，方便事务控制。

三、MongoDB 为什么用 B 树？（含现实修正）

传统面试答案（设计动机）

动机 说明
数据模型不同 MongoDB 存 BSON 文档（可变长、字段不固定），文档是整体，一次查询就要”整份”数据；B 树非叶子节点也能带数据，命中上层节点就直接拿到文档，少一次寻道
访问模式不同 MongoDB 高频操作是单文档点查（按 _id/唯一索引），范围扫描需求远低于关系型 SQL，叶子链表的优势发挥不出来
文档可变长 文档频繁更新导致页分裂/移动，B 树节点紧凑、写放大相对小（早期 MMAPv1 引擎的设计）

⚠️ 现实修正（面试加分，区分度所在）

MongoDB 3.2+ 默认的 WiredTiger 存储引擎，底层用的其实也是 B+ 树（索引和集合存储都是 btree，叶子页同样有序、支持顺序扫描），还支持可选 LSM 树（日志结构合并树，写入更快）。

“MongoDB 用 B 树”是早期 MMAPv1 时代的说法，也是面试题的简化版。严谨的结论是：真正决定索引结构的不是”B 还是 B+”，而是数据模型和访问模式——MySQL 的行模型 + 范围查询需求选 B+；MongoDB 的文档模型 + 点查需求，最终 WiredTiger 也收敛到了 B+ 结构。

四、一张表对比

维度 MySQL InnoDB MongoDB
数据模型 关系型行，列固定 BSON 文档，可变长
主要访问模式 范围查询、排序、聚合 点查 _id、条件查询
非叶子节点 只存 key（扇出大，树矮） 早期 B 树可存数据（少一次寻道）
叶子链表 有（双向链表，范围查询利器） 早期没有；WiredTiger 也有
页大小 16KB 固定 4KB~32KB 可变页
树高 34 层存千万亿级 类似
现状 B+ 树 WiredTiger：B+ 树变体 / LSM

五、面试话术

“两者都是为了降低树高、减少磁盘 IO。MySQL 选 B+ 树，是因为：① 非叶子只存 key，扇出大，树更矮，千万行只要 3 层；② SQL 高频范围查询，叶子链表能顺序扫描；③ 所有数据在叶子，查询 IO 稳定；④ 契合聚簇索引设计。MongoDB 早期用 B 树，是因为文档型数据以整条文档为单位、以点查为主，B 树节点带数据命中即得、少一次寻道。但要注意，现在 MongoDB 默认的 WiredTiger 引擎底层也是 B+ 树结构，所以这个面试题真正的考点是：索引结构取决于数据模型和访问模式。”

总结

三句话记住：

  1. 共同目标：树越矮，IO 越少，所以都要多路平衡树。
  2. B+ 树强在范围查询：非叶子只存 key（扇出大、树矮）+ 叶子链表（顺序扫描），完美匹配关系型 SQL。
  3. B 树强在点查顺带拿数据：节点带数据命中即得，匹配文档型点查；而现代 MongoDB 的 WiredTiger 其实也用 B+ 结构——结构服务于数据模型与访问模式。
