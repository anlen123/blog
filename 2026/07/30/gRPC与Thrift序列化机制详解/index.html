gRPC 与 Thrift 序列化机制详解

RPC 框架的面试必问题：“gRPC 用什么序列化？Thrift 呢？它们有什么异同？”

一句话先记住结论：

gRPC 默认用 Protobuf 序列化（可插拔）；Thrift 自带三种协议（Binary/Compact/JSON）。两者的核心编码思路一模一样：变长整数 + 字段编号直跳，所以又快又小。

本文用”打包快递”的思路，把编码原理讲到看得懂、记得住。

一、先搞懂：序列化在 RPC 里是干什么的

一次远程调用，本质是”把数据变成字节流传过去，再变回来“：

序列化方案的好坏，就看三个指标：

指标 含义 类比
体积小 字节流越短，传输越快 快递越轻，运费越省
解析快 反序列化不费 CPU 拆箱越快，效率越高
兼容好 字段增删不影响老服务 箱子换包装，收货人不变

JSON 是”人 readable 但胖、慢”，而 gRPC 和 Thrift 选择的是”二进制、紧凑、快“的路线。

二、gRPC 的序列化：Protobuf

2.1 整体定位

  • gRPC 是 RPC 框架（基于 HTTP/2 传输），序列化是可插拔的，但默认、最常用的就是 Protobuf。
  • 分工：.proto 文件里同时定义 service（远程方法）和 message（数据结构），用 protoc 生成各语言代码。

2.2 Protobuf 编码核心：四板斧

第一板斧：Tag（快递单上的”货架号 + 格子号”）

每个字段编码 = Tag + Value，其中：

wire_type 含义 对应类型
0 Varint 变长整数 int32/int64/bool/enum
1 64-bit 定长 fixed64/double
2 长度前缀 string/bytes/嵌套 message/数组
5 32-bit 定长 fixed32/float

关键理解：字段在编码里没有名字，只有编号。

就像快递柜：取件码是”3 号柜 7 号格“，而不是”用户姓名的包裹”。解析时按编号直接跳过去拿，不用匹配字符串——这就是 Protobuf 快的根本原因。

第二板斧：Varint（变长整数，小数字只占 1 字节）

普通 int32 固定占 4 字节，但业务里大部分数字都很小（id=1、count=5）。Varint 的做法：

类比：像停车位编号，小数字写一个字符，大数字才多写几个字符。小整数是绝大多数，所以整体省一半以上空间。

第三板斧：ZigZag（负数的”隐身术”）

int32 的负数在计算机里符号位全 1，用 Varint 编码会膨胀成 10 字节。Protobuf 的解法是先把负数映射成正数再编码：

类比：负数像”欠条”，直接把欠条改成”存款单”的格式再入账。所以协议里负数类型要用 sint32/sint64（自动 ZigZag），别用 int32。

第四板斧：Length-delimited（字符串/嵌套消息）

2.3 兼容性：为什么字段编号不能改

  • 编码里只有编号，所以字段名随便改（不影响线上兼容）；
  • 编号一旦发布不能改，新增字段安全（老程序遇到未知编号直接跳过），删除字段要”留号不复用”。

类比：编号是”契约”，名字是”昵称”。昵称随便换，契约不能撕。

2.4 小结

优点 缺点
二进制紧凑，比 JSON 小 3~10 倍 不可读，排查问题要工具转码
按编号直跳，解析快 改字段要重新生成代码
跨语言、前后兼容 需要 .proto 文件才能看懂报文

三、Thrift 的序列化机制

3.1 整体定位

Thrift 是 Facebook 开源的一体化 RPC 框架：IDL（.thrift）、代码生成、传输层、协议层、服务端栈全都有。序列化协议是可选的多种，这是它和 gRPC 最大的不同。

3.2 三种协议

① TBinaryProtocol（默认二进制）

与 Protobuf 的关键差异：Thrift 把”类型”和”字段 ID”分开编码（各占字节），而 Protobuf 把两者合并进一个变长 Tag。所以 Binary 协议比 Protobuf 略胖。

② TCompactProtocol（紧凑二进制，≈ Protobuf）

三个压缩手段：

手段 说明
Varint 整数变长编码（和 Protobuf 同款）
ZigZag 负数映射（和 Protobuf 同款）
字段 ID delta 合并 字段 ID 与上一个字段做差值，差值 + 类型合并在 1 字节里（高 4 位类型、低 4 位差值，超出再扩展）

额外细节：bool 值直接编码进类型（BOOL_TRUE/BOOL_FALSE），字符串长度用 Varint。

效果：Compact 体积约为 Binary 的一半，与 Protobuf 相当。

③ TJSONProtocol（JSON 文本）

字段编码成 {"1": {"i32": 100}} 这种带类型的 JSON。优点是可读、可跨语言调试；缺点是体积和性能最差，一般只用于调试和 Web 场景。

3.3 传输层配合（TTransport）

传输 说明
TSocket 原始 TCP
TFramedTransport 帧传输：每条消息前加 4 字节长度头，服务端按帧读取
TZlibTransport 先 zlib 压缩再传输，配合 Binary/Compact 进一步瘦身

3.4 兼容性

和 Protobuf 一样的规矩：字段 ID 唯一且不可改，新增字段老客户端自动忽略，删除字段 ID 保留。区别是 Thrift 支持 optional/required 标记（proto3 已去掉 required）。

四、一张表对比

维度 gRPC + Protobuf Thrift
默认序列化 Protobuf（可插拔 Codec） Binary / Compact / JSON 自选
IDL 文件 .proto .thrift
编码核心 Tag(编号+类型合并) + Varint + ZigZag Binary：类型与 ID 分离；Compact：delta 合并 + Varint + ZigZag
体积 紧凑 Binary 略大，Compact 与 Protobuf 相当
传输层 HTTP/2（多路复用、流式、双向流） TCP/HTTP，可配帧传输、压缩
生态 Google 系，云原生标配（K8s、etcd、Istio） Facebook 系，传统微服务框架
一句话特点 序列化只是拼图一角，强在 HTTP/2 生态 一体化框架，协议/传输/服务端全自研

选型直觉：云原生、对外 API、需要流式通信 → gRPC；老系统内部服务、想要一把梭的完整框架 → Thrift。

五、面试高频题

  1. gRPC 默认用什么序列化？能换吗？ Protobuf；可以，Codec 可插拔（如 JSON codec）。
  2. Protobuf 为什么比 JSON 快？ 二进制 + 按编号直跳（不匹配字段名）+ Varint 紧凑。
  3. Varint 的原理？ 每字节 7 位数据 + 1 位继续位，小整数 1 字节。
  4. 负数怎么优化？ 用 sint32/sint64，ZigZag 映射避免 10 字节膨胀。
  5. Proto 改字段名/编号的规则？ 名字随便改；编号是契约不能改；新增安全、删除留号。
  6. Thrift 有哪几种协议？ Binary（默认）/ Compact（紧凑）/ JSON（可读），配合 FramedTransport、Zlib 压缩。
  7. Compact 比 Binary 紧凑在哪？ Varint + ZigZag + 字段 ID delta 与类型合并 + bool 内嵌类型。
  8. Protobuf 和 Thrift 怎么选？ 云原生/流式选 gRPC；一体化老框架选 Thrift；性能两者同级。

总结

三句话记住本篇文章：

  1. 它们是一家人：都是”IDL 定义 + 代码生成 + 二进制紧凑编码”，核心都是 Varint + ZigZag + 字段编号直跳。
  2. 唯一实质差异：gRPC 的 Protobuf 把”编号+类型”合并进一个 Tag（更省），Thrift 默认 Binary 分开编码（略胖），但 Compact 协议追平。
  3. 面试答法：先讲共性编码原理（这才能显出深度），再对比协议差异和选型场景。
