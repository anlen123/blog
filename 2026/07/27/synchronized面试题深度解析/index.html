synchronized面试题深度解析

发表于2026-07-27|更新于2026-07-28|后端
|浏览量:

synchronized 面试题，按 基础概念 → 使用方式 → 底层原理 → 锁升级 → Monitor 源码 → 优化 → wait/notify → 对比 Lock → DCL 单例 → 高级场景 → 参数调优 → 口述提纲 全链路整理，涵盖源码级深度分析。

一、基础概念

1. 什么是 synchronized？它解决了什么问题？

synchronized 是 Java 提供的一种内置锁机制（也叫监视器锁 / Monitor Lock），用于解决多线程并发访问共享资源时的线程安全问题。

它能保证：

  • 原子性：同一时刻只有一个线程执行被保护的代码块
  • 可见性：一个线程释放锁前对共享变量的修改，对后续获取锁的线程立即可见
  • 有序性：禁止指令重排（但不能完全杜绝重排，需配合 volatile）

2. synchronized 的三大特性分别是怎么保证的？

特性 保证方式
原子性 通过监视器锁的互斥机制，同一时刻只有一个线程能持有锁
可见性 JMM 规定：线程解锁前必须将工作内存中的共享变量刷新到主内存；线程加锁前必须清空工作内存，重新从主内存读取
有序性 通过”一个变量在同一时刻只允许一条线程对其进行 lock 操作”的规则来限制指令重排

3. synchronized 是可重入锁吗？为什么？

是可重入锁。 同一个线程在已经持有一个锁的情况下，可以再次获取同一个锁而不会被阻塞。

实现原理：每个监视器对象内部维护一个重入计数器：

  • 线程首次获取锁，计数器 = 1
  • 同一线程再次进入同步块，计数器 +1
  • 退出同步块时，计数器 -1
  • 计数器归零时，锁完全释放

如果没有可重入性，子类调用父类的同步方法就会死锁。

二、使用方式

4. synchronized 的三种使用方式及其锁对象分别是什么？

使用方式 锁对象 示例
修饰实例方法 当前实例对象 this public synchronized void method() {}
修饰静态方法 当前类的 Class 对象 public static synchronized void method() {}
修饰代码块 括号中指定的对象 synchronized(obj) {}

5. 实例方法锁和静态方法锁互相影响吗？

不互相影响。 因为它们锁的是不同的对象：

  • 实例方法锁的是 this（实例对象）
  • 静态方法锁的是 ClassName.class（Class 对象）

两个线程一个执行实例同步方法、一个执行静态同步方法，不会互斥。

6. synchronized 修饰代码块时，锁对象怎么选？

关键原则：

  1. 锁对象用 final 修饰，防止引用被修改导致锁失效
  2. 避免用字符串常量和包装类作为锁对象
  3. 尽量缩小同步代码块的范围，提高并发性能

8. Monitor（监视器）是什么？它如何工作？

Monitor 是操作系统级别的同步原语，每个 Java 对象都可以关联一个 Monitor。

Monitor 的核心结构：

Monitor 工作流程：

  1. 线程尝试获取锁 → 进入 Monitor 的 EntryList
  2. 获取锁成功 → 成为 Owner
  3. 调用 wait() → 释放锁，进入 WaitSet，状态变为 WAITING
  4. 被 notify()/notifyAll() 唤醒 → 从 WaitSet 移到 EntryList，重新竞争锁
  5. 执行完同步块 → 释放锁，Owner 置空，唤醒 EntryList 中的线程竞争

四、锁升级机制（重点中的重点）

10. 什么是锁升级？为什么需要锁升级？

JDK 1.6 之前，synchronized 直接使用重量级锁（操作系统的互斥量），每次加锁都需要用户态到内核态的切换，开销非常大。

但实际应用中，大多数情况下锁竞争并不激烈，甚至很多锁始终只在一个线程中使用。为了优化这种”高开销应对低竞争”的不匹配，JDK 1.6 引入了锁升级机制：

11. 偏向锁是什么？它是怎么加的？

偏向锁（Biased Locking） 的核心思想是：大多数情况下锁不仅不存在多线程竞争，而且总是由同一个线程多次获取。

加锁过程：

  1. 检查 Mark Word 的偏向锁标志是否为 1，锁标志位是否为 01
  2. 如果是可偏向状态（标志位 101），检查 Mark Word 中存储的 Thread ID 是否为空
  3. 如果为空 → CAS 将当前线程 ID 写入 Mark Word
    • 成功 → 获得偏向锁，继续执行
    • 失败 → 说明有竞争，撤销偏向锁，升级为轻量级锁
  4. 如果 Thread ID 等于当前线程 → 直接执行（无需任何 CAS 操作）
  5. 如果 Thread ID 不等于当前线程 → CAS 尝试替换 Thread ID
    • 成功 → 获得偏向锁
    • 失败 → 撤销偏向锁，升级为轻量级锁

13. 什么是自旋锁？自旋锁有什么优缺点？

自旋锁是轻量级锁竞争失败时的一种等待策略：线程不立即阻塞，而是执行一段空循环（自旋） 等待锁释放。

优点：

  • 避免线程阻塞/唤醒带来的用户态-内核态切换（阻塞/唤醒是重量级操作，通常需要 30,000~50,000 个时钟周期）
  • 锁很快释放时，自旋等待的代价远小于线程切换

缺点：

  • 自旋消耗 CPU 时间（空循环也是用 CPU 的）
  • 锁长时间不释放，自旋就是浪费 CPU

自旋的进化：

版本 策略
JDK 1.4 引入 默认关闭，需 -XX:+UseSpinning 开启
JDK 1.6 默认开启 固定自旋次数（10次）
JDK 1.7+ 自适应自旋：根据上一次自旋的结果动态调整

自适应自旋的决策逻辑：如果上次自旋成功获取了锁 → 这次更愿意自旋，时间更长；如果上次自旋失败 → 这次少自旋，甚至直接阻塞。

14. 重量级锁是什么？什么时候升级到重量级锁？

当锁竞争真正激烈（多个线程同时争抢，CAS 频繁失败）时，JVM 将锁升级为重量级锁。

升级条件：

  • 轻量级锁状态下，CAS 自旋失败达到一定次数（JDK 6 后由自适应自旋决定）
  • 或者等待线程数达到阈值（第三个线程同时竞争时通常直接膨胀）

重量级锁的实现：依赖操作系统的互斥量（Mutex），未获取到锁的线程进入 Monitor 的 EntryList，状态变为 BLOCKED。锁释放时，操作系统负责唤醒等待线程。

性能开销最大的地方：用户态到内核态的切换。每次阻塞（pthread_mutex_lock）和唤醒（pthread_mutex_unlock）都是系统调用，需要用户态↔内核态切换。

六、JVM 对 synchronized 的优化

19. 除了锁升级，JVM 还有哪些优化？

优化手段 说明
锁粗化（Lock Coarsening） 如果 JVM 检测到一连串对同一个锁的反复加锁/解锁，会把锁的范围扩大到整个操作序列之外

七、wait / notify / notifyAll

22. wait()、notify()、notifyAll() 和 synchronized 的关系？

这三个方法属于 Object 类，必须在 synchronized 块中调用，否则抛 IllegalMonitorStateException。

API 作用
wait() 释放当前持有的锁，线程进入 Monitor 的 WaitSet 等待，状态变为 WAITING
wait(long timeout) 同上，但超时后自动唤醒
notify() 唤醒 WaitSet 中随机一个等待线程
notifyAll() 唤醒 WaitSet 中所有等待线程

23. 为什么 wait() 要放在 while 循环里而不是 if 里？

核心原因：防止虚假唤醒（Spurious Wakeup）。

虚假唤醒：线程可能在没有被 notify/notifyAll、也没有超时中断的情况下被唤醒。这是操作系统层面的现象（POSIX 标准允许），Java 必须兼容。

总结：用 while 而不是 if，确保被唤醒后条件仍然满足才继续执行。

24. sleep() 和 wait() 的区别？

对比维度 sleep() wait()
所属类 Thread 类的静态方法 Object 类的实例方法
锁释放 不释放锁 释放锁
调用位置 任意位置 必须在 synchronized 块中
唤醒方式 睡眠时间到或 interrupt() wait 时间到或 notify()/notifyAll()
线程状态 TIMED_WAITING WAITING / TIMED_WAITING

25. 为什么 wait/notify 定义在 Object 类而不是 Thread 类？

  1. 锁是对象级别的，不是线程级别的。每个 Java 对象都可以作为锁，wait/notify 操作的是对象的监视器，所以定义在 Object 中更合理。
  2. 一个线程可能持有多把锁，等待和唤醒必须明确是哪个对象的监视器。如果定义在 Thread 上，就无法区分。
  3. 如果定义在 Thread 中，线程 A 调用 threadB.wait() 会让线程 A 等待，但实际需要的是让线程 A 在某个锁对象上等待，语义不符合。

八、synchronized vs Lock

26. synchronized 和 ReentrantLock 的区别？

对比维度 synchronized ReentrantLock
实现层面 JVM 内置，关键字级别 JDK 提供的 API，Java 类

29. 什么时候该用 synchronized，什么时候该用 Lock？

场景 推荐
简单同步需求、代码块固定 synchronized
需要尝试获取锁（tryLock） ReentrantLock
需要可中断的锁获取 ReentrantLock
需要公平锁 ReentrantLock
需要多个条件队列 ReentrantLock + Condition
需要读写分离 ReentrantReadWriteLock

总结：能用 synchronized 解决的优先用 synchronized（代码简洁、不易出错），有特殊需求时再用 Lock。

九、synchronized 的内存语义

30. synchronized 如何保证可见性？

JMM（Java Memory Model）关于 synchronized 的规定：

  1. 线程解锁前，必须把工作内存中的共享变量刷新回主内存。
  2. 线程加锁前，必须清空工作内存中的共享变量，强制从主内存重新读取。

十三、高频面试追问

42. synchronized 锁住的是对象还是代码？

锁住的是对象。 synchronized 修饰的代码块和方法本身并不重要——真正起作用的是锁对象。

多个线程如果用的是同一个锁对象，它们就会互斥；如果用的是不同锁对象，就不会互斥。

43. 两个线程同时访问同一个对象的两个不同的 synchronized 方法，会互斥吗？

会互斥。 因为实例同步方法都锁的是 this（同一个对象），一个线程进入 methodA() 后，另一个线程无法进入 methodB()。

44. 锁升级后还能降级吗？

不能。 HotSpot JVM 中的锁升级是单向不可逆的（偏向锁 → 轻量级锁 → 重量级锁）。唯一的例外是 JVM 的 STW（Stop-The-World）期间，比如 GC 或偏向锁批量撤销时，可能发生降级，但这属于 JVM 内部的特殊行为，用户代码层面看不到降级。

45. 偏向锁为什么在 JDK 15 后被废弃？

  1. 现代应用多用线程池，锁的持有者频繁变化，偏向锁的撤销成本 > 收益
  2. 偏向锁的撤销需要在安全点（Safepoint）执行，所有线程停下来，开销大
  3. 高并发场景下，偏向锁给的是负优化
  4. 维护偏向锁逻辑也给 JVM 代码带来了相当大的复杂度

46. synchronized 和 volatile 的区别？

对比维度 synchronized volatile
本质 锁机制 轻量级同步机制（内存屏障）
原子性 保证 不保证（如 i++ 不是原子的）
可见性 保证 保证
有序性 保证（部分） 保证（禁止指令重排）
性能开销 较大 较小
适用场景 多线程对共享变量的复合操作 一写多读场景（状态标志位）

47. 一个对象有两把锁吗？

严格说一个对象关联着一个 Monitor，但有两种作用域：

问题 一句话答案
synchronized 是什么 Java 内置互斥锁，保证原子性、可见性、有序性
锁的是代码还是对象 对象，每个对象关联一个 Monitor
底层怎么实现 对象头 Mark Word + Monitor + monitorenter/monitorexit 指令
锁升级过程 无锁 → 偏向锁 → 轻量级锁(CAS) → 重量级锁(Mutex)
锁可降级吗 不可以（HotSpot 实现中）
是可重入的吗 是，Monitor 内部有重入计数器
Monitor 几个队列 3 个：CXQ（FILO 入队）→ EntryList（FIFO 出队）→ WaitSet（wait/notify）
wait 为什么要用 while 防止虚假唤醒
和 Lock 的区别 synchronized 自动释放、不可中断、非公平、JVM 层面
DCL 为什么加 volatile 防止 new 对象时的指令重排导致半初始化
静态方法 vs 实例方法 锁对象不同（Class vs this），不互斥
偏向锁为什么被弃用 线程池场景下撤销成本太高，得不偿失
什么时候膨胀到重量级 自旋超限 / 第三个线程竞争 / CAS 频繁失败
