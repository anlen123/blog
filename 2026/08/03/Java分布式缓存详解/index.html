一、缓存分层架构：为什么需要分布式缓存

1.1 缓存为什么快

  • 内存访问纳秒级，磁盘访问毫秒级，差了 3~4 个数量级。
  • 数据存在内存里，省去磁盘 IO + 网络 + SQL 解析执行的开销。
  • 数据库 80% 的请求其实都是读同一批热点数据，缓存把它们挡在 DB 之外。

1.2 完整缓存分层

一个成熟系统的缓存是分层的，越靠上越快、越靠下越全：

1.3 为什么不能只用本地缓存？

问题 说明
数据不一致 每台机器各存一份，用户轮询到不同机器看到不同数据
内存有限 单机内存撑不起大数据量，无法横向扩展
无法集中管理 过期、淘汰、预热都要逐台配置，运维成本高
缓存命中率低 流量分散到 N 台机器，每台的”热点”都变小了

所以生产环境核心数据用 Redis 分布式缓存：所有机器共享同一份缓存，天然一致、可扩展、可统一治理。本地缓存只做最后一道兜底（如 Redis 挂了用 Caffeine 挡一阵）。

二、缓存选型：Redis vs Memcached

2.1 对比表

维度 Redis Memcached
数据结构 丰富：String/Hash/List/Set/ZSet/Bitmap/HyperLogLog 只有 String（KV）
持久化 RDB + AOF 无（纯内存，重启丢光）
集群 官方 Cluster（分片 + 高可用）、哨兵 客户端分片，无官方高可用
分布式锁 SET NX EX + Lua，生态完善（Redisson） 不支持
事务 MULTI/EXEC 乐观锁事务 不支持
多线程 6.0+ 支持 IO 多线程（命令执行仍单线程） 多线程
典型场景 缓存 + 计数器 + 分布式锁 + 消息队列 + 排行榜 纯 KV 缓存

2.2 结论

面试话术：Memcached 只是”KV 缓存”，而 Redis 是”数据结构服务器”。现代项目基本都用 Redis——一个中间件同时解决缓存、分布式锁、计数器、排行榜、限流、延迟队列等需求，Memcached 已逐步边缘化。

三、Redis 高可用架构演进

3.1 演进路线（面试必背）

3.2 三种架构要点

① 主从复制

  • 写主读从，分摊读压力。
  • 异步复制：主库写成功即返回，从库可能短暂落后 → 读从库可能读到旧数据（主从延迟问题）。
  • 主库宕机需要人工/脚本切换，有段时间不可用。

② 哨兵模式（Sentinel）

  • 主库宕机 → 哨兵通过 Raft 协议选主 → 从库提升为新主 → 客户端感知新地址。
  • 解决高可用，但存储容量仍受单机限制（所有数据在主上）。

③ Redis Cluster（生产首选）

  • 分片：数据打散到多个节点，容量横向扩展（3 主起步，可扩到 1000+ 节点）。
  • 高可用：每个主节点配从节点，主挂自动提升从节点。
  • 去中心化：Gossip 协议通信，客户端请求任意节点，MOVED 重定向到正确节点。

面试追问：Cluster 模式有什么限制？

  • 不支持多 Key 操作（除非这些 Key 在同一个槽，可用 hash tag {user:1001} 强制同槽）。
  • 不支持跨槽事务。
  • 批量操作（mget 跨节点）需要客户端分片处理。

四、缓存穿透：查”不存在”的数据

4.1 定义

请求查询缓存和数据库都不存在的数据（如恶意构造的 id = -1），缓存永远 miss，每次请求都穿透到数据库：

4.2 解决方案

① 缓存空值（最简单，推荐）

缺点：大量不存在的 key 会占缓存空间 → 配合较短 TTL + 对非法 key（如负数、超长）直接参数校验拦截。

② 布隆过滤器（Bloom Filter，防批量攻击）

  • 判断”不存在”绝对准确（无假阴性），判断”存在”可能误判（假阳性）→ 正好用来拦截非法 key。
  • 使用姿势：项目启动时把所有合法 ID 预加载进布隆过滤器（或用缓存 key 集合构建），请求先过布隆，不在直接拒绝。

面试追问：布隆过滤器有什么缺点？

  • 有误判率（假阳性），可通过增大 bit 数组和 hash 函数数量降低。
  • 不支持删除（一个 key 的位置可能被其他 key 共享，删了会误伤）→ 用计数布隆过滤器（每个位置是计数器）解决。
  • 数据量变化后难以扩容。

五、缓存击穿：热点 Key 过期瞬间

5.1 定义

某个热点 Key（如秒杀商品、热搜榜）在过期的一瞬间，大量请求同时 miss，全部打到数据库：

与穿透的区别：穿透是”查不存在的数据”，击穿是”查存在的热点数据，但恰好在过期瞬间”。

5.2 解决方案

① 互斥锁（Mutex）—— 只放一个线程重建缓存

优点：实现简单，保证只有一个请求打 DB；缺点：有锁竞争，极端情况可能短暂阻塞。

② 逻辑过期（推荐高并发场景）—— 缓存永不过期，异步刷新

优点：读请求永远有数据可返回，不会阻塞，适合秒杀等超高热场景；缺点：有短暂的不一致窗口，且数据是”惰性”刷新的。

选型：追求一致性用互斥锁；追求极致可用性（秒杀）用逻辑过期。

六、缓存雪崩：大量 Key 同时失效

6.1 定义

两种情况：

情况 例子 后果
大量 Key 同时过期 所有商品都设了 0 点过期 0 点一到，全部 miss 打 DB
Redis 整体宕机 集群故障 / 误操作 flushall 所有请求穿透到 DB

6.2 解决方案

面试话术：雪崩的根因是”同时失效“，所以核心解法是”错峰“（随机 TTL）；而 Redis 宕机要靠多级缓存 + 高可用 + 限流降级组合拳，任何一个单点措施都不够。

七、缓存与数据库一致性

这是缓存面试的最深水区，核心问题是：

缓存是”最终一致”的，而数据库是”强一致”的，两者之间怎么做读写，才能把不一致窗口压到最小？

7.1 标准方案：Cache Aside（旁路缓存）

关键设计：为什么更新 DB 后要”删缓存”而不是”更新缓存”？

对比 删缓存 更新缓存
并发安全 删了下次读重新加载，天然正确 并发写时后写的可能覆盖先写的，产生脏数据
成本 一次 DEL 极轻量 每次写都额外写一次缓存，浪费
热点冷数据 删掉冷数据 = 自然淘汰 更新冷数据 = 浪费内存

结论：Cache Aside 写入路径 = 先更库，再删缓存。这是业界公认的标准做法。

7.2 错误示范：先删缓存、再更新库

窗口期：①删缓存 ~ ③更新DB 之间任何读请求都会把旧值写回缓存，且缓存此后一直返回旧值（除非再次过期）。这个错误的脏数据窗口很长，务必避免。

7.3 标准做法仍有极小概率不一致

窗口期：①更新DB ~ ③删缓存 之间，读请求返回旧值。这个窗口很短（毫秒级），且第二次读就正常了，所以是”可接受的最终一致”。

7.4 加强版：延迟双删（Double Delete）

注意：如果用了主从架构，③ 的 sleep 还要覆盖”从库同步延迟”（读请求可能从落后从库读到旧值），一般取 500ms~1s；延迟时间难以精确把控是它的缺点。

7.5 终极方案：订阅 binlog 异步删缓存（Canal）

为什么它最可靠？

注意：binlog 是异步消费的，中间仍有短暂不一致（毫秒~秒级），所以：

  • 适合”允许秒级不一致”的业务（商品详情、用户信息）。
  • 最终一致性 = Canal 删缓存 + 缓存 TTL 兜底（即使漏删，TTL 也会兜住）。

7.6 一致性方案总结

方案 不一致窗口 实现成本 适用
Cache Aside（更库+删缓存） 毫秒级 低 大多数业务，默认选择
延迟双删 极小 低 写多读少、对一致性稍敏感
Canal binlog 订阅 秒级（异步） 中 大规模系统、多系统数据同步
缓存 TTL 兜底 永远兜底收敛 0 所有方案都必加

面试总结一句话：写路径”先更库再删缓存”，读路径”miss 就回填”，一致性要求高加”延迟双删”，大规模系统上”Canal 订阅 binlog”，最后无论哪个方案都必须靠 TTL 兜底——缓存最终会过期，保证数据最终收敛。

八、缓存淘汰策略

8.1 经典算法

策略 思想 缺点
LRU（Least Recently Used） 淘汰最久没被访问的 偶发批量扫描会误淘汰热点
LFU（Least Frequently Used） 淘汰访问频率最低的 新数据频率低容易被淘汰（加衰减/时间窗解决）
FIFO 淘汰最早进来的 不考虑访问，效果差
TTL 淘汰最快过期的 需要 Key 带过期时间
随机 随机淘汰 命中率差

8.2 Redis 的 maxmemory-policy（8 种）

策略 说明
noeviction 内存满拒绝写请求（默认，生产会报错）
allkeys-lru 所有 Key 中近似 LRU（生产常用）
volatile-lru 仅对设了过期时间的 Key 近似 LRU
allkeys-lfu 所有 Key 近似 LFU（生产常用）
volatile-lfu 仅对设了过期时间的 Key 近似 LFU
allkeys-random 所有 Key 随机淘汰
volatile-random 仅对设了过期时间的 Key 随机淘汰
volatile-ttl 淘汰剩余 TTL 最短的

8.3 面试加分点：Redis 的 LRU 是”近似 LRU”

  • Redis 出于性能考虑不会维护全局双向链表精确 LRU，而是采样：内存满时随机采样 5 个 Key（maxmemory-samples），淘汰其中最久没访问的。
  • 采样数越大越接近真实 LRU，但 CPU 开销越大。
  • 若业务有”全量扫描”（如遍历所有 Key 做批量操作），会让大量冷 Key 的 LRU 时间被刷新，污染 LRU → 这种情况更适合 LFU。

9.5 RedLock 及其争议（面试加分项）

RedLock：加锁时向多个独立 Redis 节点（如 5 个）同时尝试加锁，超过半数成功才算加锁成功，释放时向全部节点释放——用于解决”主从切换导致锁丢失”。

争议（知道双方观点即可）：

观点 代表人物 核心论点
反对 Martin Kleppmann（《DDIA》作者） ① 客户端 GC 停顿：锁过期后持有者还在跑，另一个客户端拿到锁并发执行；② Redis 的时钟跳跃/过期淘汰会让锁提前失效；③ 分布式锁应该用带 fencing token（单调递增令牌）的方案，让资源侧校验
支持 antirez（Redis 作者） ① GC 停顿问题对任何分布式锁都存在，RedLock 至少能容忍单点故障；② 只要客户端在过期前完成任务、时间源可控，RedLock 是可用的

面试话术：生产上绝大多数场景单节点 Redis + 看门狗就够用；如果要求更高的容错性（如金融场景），方案是 RedLock 或引入带 fencing token 的数据库锁（如 ZooKeeper 顺序节点）。同时要认识到：分布式锁的最终安全边界在资源侧（如数据库行锁、版本号校验），应用层锁只是第一道防线。

十、大 Key 与热 Key 问题

10.1 大 Key（Big Key）

定义：单个 Key 的 value 过大（如一个 Hash 存几十万字段、String 存 10MB+ 内容）。

危害：

  • 读写耗时高：阻塞 Redis 单线程，拖慢其他命令。
  • 内存不均：集群下数据倾斜，单个节点内存爆掉。
  • 删除阻塞：DEL 大 Key 同步阻塞（Redis 4.0+ 用 UNLINK 异步删除）。
  • 网络流量大：大 value 序列化/传输耗带宽。

解决：

  • 拆分：Hash 拆成多个小 Hash（如按 user:{id}:field_{i}），大 String 分片存储。
  • 压缩：value 压缩（gzip/序列化优化）。
  • 定期扫描：redis-cli --bigkeys 找出大 Key 治理。

10.2 热 Key（Hot Key）

定义：某个 Key 被超高频率访问（如双十一的爆款商品、明星八卦热搜）。

危害：单分片流量打满，拖慢整个集群；Redis 单线程处理该 Key 时其他请求排队。

解决：

  • 本地缓存 + 热点 Key 限流：热点 Key 在应用本地缓存一份（Caffeine），挡住大部分流量。
  • 多副本读写分离：热点 Key 复制 N 份（hot:1~`hot:N`），请求 hash 分散到不同副本/节点。
  • 监控 + 动态识别：Redis 4.0+ 的 hotkeys 参数（需要开启 LFU）或客户端统计。

十一、面试模拟题与参考答案

基础类

1. 缓存为什么要分层？Redis 挂了一定要立刻恢复吗？
缓存分层是为了”逐层兜底”：CDN/本地缓存挡静态和热点，Redis 挡共享数据，DB 是最后防线。Redis 挂了不慌的前提是有多级缓存 + 限流降级，本地缓存（Caffeine）能顶住几分钟。

2. Redis 和 Memcached 怎么选？
见第二章：Redis 数据结构丰富、支持持久化/集群/分布式锁，Memcached 仅 KV 且无高可用。现代项目选 Redis。

3. Redis 主从、哨兵、Cluster 的区别？
主从解决读写分离（人工切换）；哨兵解决自动故障转移（容量仍受限）；Cluster 解决容量横向扩展（分片 + 高可用）。

三大问题类

4. 缓存穿透、击穿、雪崩分别是什么？怎么解决？（必考，按表答）

问题 场景 核心解法
穿透 查不存在的数据 缓存空值 / 布隆过滤器 / 参数校验
击穿 热点 Key 过期瞬间 互斥锁 / 逻辑过期
雪崩 大量 Key 同时过期或 Redis 宕机 随机 TTL / 永不过期 / 多级缓存 / 高可用 / 限流降级

5. 布隆过滤器为什么能防穿透？误判怎么办？
判断”不存在”绝对准（无假阴性），拦截非法 key；”存在”可能有假阳性，但只会多放行一个请求进缓存层，无害。误判率通过 bit 数组大小和 hash 数量控制。

6. 热点 Key 用互斥锁还是逻辑过期？
互斥锁保证强一致但极端情况有阻塞；逻辑过期保证读永远可用但有短暂脏读。秒杀等超高并发选逻辑过期，一般业务选互斥锁。

一致性类（最难点）

7. 先更新数据库还是先删缓存？为什么？
先更库再删缓存（Cache Aside）。先删缓存再更库，中间窗口所有读都会把旧值回填缓存，脏数据窗口长且不易自愈。

8. 为什么是”删缓存”而不是”更新缓存”？
删除是懒加载，并发下天然正确；更新缓存并发写可能互相覆盖产生脏数据，且冷数据写入浪费内存。

9. 延迟双删为什么还要”延迟”？
为了让并发读把旧值回填进缓存的窗口过去，第二次删除清掉脏缓存；主从架构下还要覆盖从库同步延迟。

10. 用 Canal 订阅 binlog 删缓存，中间不一致多久？怎么兜底？
binlog 解析、MQ 投递、消费都是异步的，不一致窗口毫秒~秒级。兜底：缓存 TTL 一定比业务可接受不一致时间短，保证最终收敛。

11. 缓存和数据库的一致性，能保证强一致吗？
不能，缓存本质是最终一致。要么接受”删缓存后短暂读旧值/读不到”，要么不用缓存（一致性要求极高且写密集的场景）。

分布式锁类

12. 手写一个 Redis 分布式锁，注意哪些点？
① SET NX EX 原子加锁；② value 用 UUID 标识；③ Lua 脚本原子比对+删除防误删；④ 设合理过期时间防死锁；⑤ 业务时间不确定时用 Redisson 看门狗续期；⑥ 业务上配合幂等/乐观锁做兜底。

13. Redisson 看门狗原理？
加锁未指定 leaseTime 时默认 30s，后台定时每 10s（30s/3）执行 Lua 续期；解锁或宕机后停止，锁自动过期。

14. RedLock 的争议是什么？
GC 停顿和时钟跳跃可能让锁提前失效，导致两个客户端同时持有锁；反对者主张用 fencing token 在资源侧校验，支持者认为 RedLock 至少解决了单点问题。生产中多数场景单节点 + 看门狗足够。

实战类

15. 你们项目缓存怎么设计的？Redis 挂了怎么办？
参考话术：读多写少的核心数据（商品、用户）走 Cache Aside；热点数据本地缓存 + 逻辑过期；Redis 集群主从 + 哨兵保证高可用；降级方案是本地缓存 + 限流 + 返回旧值，DB 加读写分离扛压；同时有大 Key/热 Key 治理和监控告警。

总结

分布式缓存的面试考察主线：

记住三条主线：

  1. 性能：缓存挡在 DB 前面，分层越厚，DB 越安全。
  2. 一致性：缓存本质是最终一致，”先更库再删缓存 + TTL 兜底”是底线，延迟双删和 Canal 是加强。
  3. 可靠性：穿透/击穿/雪崩/锁丢失，每一个问题都有一套成熟解法，面试时按”问题 → 场景 → 解法 → 取舍”四步讲，就稳了。
