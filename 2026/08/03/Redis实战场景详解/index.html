Redis 实战场景详解：排行榜/分布式锁/共同好友等经典用法

面试官常问：”你们项目里 Redis 都用来干什么？”——如果只回答”做缓存”，就浪费了 Redis 这张好牌。Redis 的每个数据结构几乎都对应一类经典业务场景：ZSet 做排行榜、Set 做共同好友、Lua 做秒杀防超卖、GEO 做附近的人、HyperLogLog 做 UV、Bitmap 做签到、Stream 做消息队列……

本文按”场景 → 数据结构 → 命令 → 代码 → 坑“的套路，系统梳理 Redis 的经典用法，一篇讲透。

一、总览：数据结构 × 业务场景对照表

先背这张表，面试开场就能”控场”：

数据结构 核心特性 经典场景
String 简单 KV、自增自减、过期 缓存、计数器、Session、分布式锁、分布式 ID
Hash 对象字段、局部更新 购物车、对象缓存、点赞计数
List 双向链表、阻塞读写 轻量消息队列、最新列表、任务流
Set 去重、集合运算（交/并/差） 共同好友、点赞人集合、抽奖、标签

Stream 持久化消息 + 消费者组 + ACK 轻量可靠消息队列

选择口诀：计数用 String，对象用 Hash，去重用 Set，排序用 ZSet，位操作用 Bitmap，统计去重用 HyperLogLog，距离用 GEO，可靠队列用 Stream。

四、分布式锁（场景三）

一句话：多实例并发修改共享资源（库存、余额、任务）时，用 Redis 锁做互斥。

进阶：可重入、自动续期（看门狗）、主从切换锁丢失、RedLock 争议，详见 Java 分布式缓存面试题与知识点详解 §九 和 Redis 幂等控制与分布式锁设计。

面试提醒：分布式锁不是万能的。能不用锁就不用（用乐观锁/幂等设计替代）；锁的最终安全边界在资源侧（数据库行锁、版本号校验）。

六、计数器与限流（String / ZSet / Lua）

6.1 计数器（String INCR）

关键坑：计数器是最终一致的，要定期异步落库（定时任务批量同步/订阅 binlog），防止 Redis 数据丢失导致计数错乱。

6.2 接口限流：三种方案对比

① 固定窗口（最简单）

坑：窗口临界点突刺（59s 和 61s 各放 10 次 = 2 秒内 20 次）。

② 滑动窗口（ZSet，精确）

优点：精确；缺点：每个请求一条 ZSet 记录，内存占用高。

③ 令牌桶（Lua，平滑）

生产上也可以直接用 Redis 官方模块 redis-cell（CL.THROTTLE 一行命令）或网关层（Sentinel 等）限流，Redis 方案适合”应用内精确限流”。

7.2 Lua 原子方案（推荐）

关键设计：

  • 库存预热：活动前把库存 SET stock:sku:1 100。
  • Redis 只挡流量（预扣），真正的订单写 MySQL 走 MQ 异步落库——落库失败（如地址非法）要回补库存（Lua 里 INCR 或对账任务）。
  • 超卖的最后防线：MySQL 乐观锁（UPDATE stock SET count = count-1 WHERE id=? AND count>0）。
  • 为什么用 Lua：多条命令在 Redis 单线程中原子执行，天然无并发问题，比分布式锁性能高一个量级。

九、轻量消息队列（List / Stream）

9.1 List 简单队列

  • 优点：极简单；缺点：无确认机制（BRPOP 取出即删，消费者挂了消息就丢）、无消费者组。

9.2 Stream（Redis 5.0+，正经的可靠队列）

Stream 与 List 的对比（面试点）：

特性 List Stream
消费者组 无 有（XREADGROUP）
消息确认 无（取出即丢） XACK 确认，PENDING 可追查
重复消费 天然不会（取出即删） 可能重复（需幂等）
消息积压 一直堆在内存 可设 MAXLEN 截断
适合 简单任务流 需要可靠消费的轻量场景

9.3 什么时候用 Redis 做 MQ？

一句话：Redis 的 Stream 是”轻量可靠”的折中方案，但替代不了专业 MQ——消息堆积、持久化、回溯、海量分区是专业 MQ 的护城河。

十九、什么场景不该用 Redis

面试官会反过来问：”Redis 这么强，是不是都能用？”——不是：

场景 为什么不能用
强一致 + 可回滚的事务 Redis 事务（MULTI/EXEC）无回滚，持久化有丢失窗口（RDB 间隔丢 / AOF 每秒丢 1s）
资金类账务 最终一致 + 可能丢数据 = 致命；必须 MySQL 事务
复杂关联查询 不支持 SQL、无 Join，数据模型要预设计
大数据量分析报表 全内存，容量贵；离线数仓/HBase 更合适
精确计数且量大 HyperLogLog 有 0.81% 误差，Set 内存贵 → 用 DB
超大 value（>10MB） 阻塞单线程、网络/内存压力大（大 Key 治理见缓存文章）
全文搜索 用 ES
需要消息回溯/海量堆积的 MQ 用 Kafka/RocketMQ

面试一句话：Redis 是”高性能最终一致组件”，不是”数据库”。凡是”必须强一致、必须不丢、必须复杂查询”的数据，都不要放 Redis。

二十、面试模拟题与参考答案

Q1：排行榜怎么实现？分数相同怎么排？
ZSet：ZINCRBY 加分、ZREVRANGE 取榜、ZREVRANK 查名次。同分处理：把时间戳编码进分数（业务分 * 100万 + 时间余数），先到先得；或展示层按”分数 + 时间”二次排序。

Q2：共同好友怎么实现？
双向 Set（following/follower），SINTER 交集。注意大 V 场景集合运算重 → 结果缓存/离线计算；集群下用 hash tag 保证同槽。

Q3：怎么防超卖？
三层：Redis Lua 原子扣减（校验库存 + 扣减 + 一人一单）+ 异步落库回补 + MySQL 乐观锁（WHERE count > 0）兜底。

Q4：限流方案怎么选？
固定窗口（简单，有临界突刺）/ 滑动窗口 ZSet（精确，费内存）/ 令牌桶 Lua（平滑，可突发）。网关级用 Sentinel，应用内精确限流用 Redis。

Q5：Redis 能做消息队列吗？
List 能但不可靠；Stream（5.0+）支持消费者组、ACK、PENDING 恢复，轻量场景够用；要求不丢消息、高吞吐、回溯选 Kafka/RocketMQ。

Q6：UV 统计用 Set 还是 HyperLogLog？
UV 量大用 HyperLogLog（12KB 管亿级，误差 0.81%）；要精确或数据量小用 Set。

Q7：签到怎么存？怎么算连续签到？
Bitmap：一个用户一个月一个 Key，SETBIT 标记，BITFIELD 一次取出当月位串，客户端从今天位往低位数连续的 1。

Q8：Redis 做分布式锁注意什么？
SET NX EX 原子加锁 + UUID 标识 + Lua 原子解锁；锁过期业务没完用 Redisson 看门狗续期；主从切换丢锁用 RedLock（有争议）或 ZooKeeper；最终靠业务幂等兜底。

Q9：GEO 底层是什么？
ZSet，经纬度 geohash 编码成 52 位整数做 score，所以支持 ZREM 删除。

Q10：点赞数存 Redis，怎么和 DB 一致？
Redis 扛实时读写，异步批量落库（定时/计数阈值触发）；以 Redis 明细为准展示，DB 定期对账修正。

Q11：Session 存 Redis 和 JWT 怎么选？
要踢人/统计在线 → Redis Session；要无状态高可用 → JWT；生产常用”JWT + Redis 黑名单/白名单”。

Q12：Redis 宕机了怎么办？（综合）
多级缓存兜底（本地缓存）→ 限流降级 → 恢复后缓存预热；数据不丢靠 RDB + AOF 持久化；高可用靠哨兵/Cluster；核心数据永远以 DB 为准。

总结

Redis 的用法可以浓缩成一张心智图：

三条总原则：

  1. 选型看结构：先想清楚业务要”排序、去重、计数还是范围查询”，再选数据结构——选对了 Redis 一半的坑就避开了。
  2. Redis 是流量层，DB 是事实层：Redis 里的一切最终都要能回落到 DB（异步落库 + 对账 + TTL 兜底）。
  3. 原子性交给 Lua：凡是要”多步操作 + 并发安全”（扣库存、令牌桶、解锁校验），一律 Lua 脚本，别用分布式锁硬撑。
