## 一、先说结论：JVM 调优本质上在调什么

JVM 调优，核心不是“背参数”，而是解决这几类问题：

1. 内存不够
- 频繁 Full GC
- OOM
- 堆外内存爆掉
2. 延迟太高
- GC 停顿时间太长
- 接口 RT 抖动
- 高峰期 STW 明显
3. 吞吐量不够
- CPU 大量耗在 GC 上
- Young GC 太频繁
- 对象创建/回收压力太大

所以 JVM 调优的目标一般就是三类：

- 降低 GC 频率
- 降低 GC 停顿时间
- 提高系统吞吐量

---

## 二、先讲 JVM 内存结构

要理解 GC，先知道 JVM 主要管哪些内存区域。

---

### JVM 运行时内存的大图

Java 程序运行时，主要有这些区域：

### 1. 程序计数器

记录线程当前执行到哪条字节码指令。
这个区域很小，基本不参与 GC。

### 2. Java 虚拟机栈

每个线程都有自己的栈，方法调用时会压栈。
局部变量、方法参数等主要在这里。
栈内存一般线程结束就释放，也不属于 GC 主要处理对象。

### 3. 本地方法栈

给 Native 方法用的，和 GC 关系也不大。

### 4. 堆（Heap）

GC 的主战场。
对象实例几乎都分配在堆里。

### 5. 方法区 / 元空间（Metaspace）

存类信息、常量、静态变量、方法元数据等。
JDK8 以后用 Metaspace 替代了永久代 PermGen。

---

### 堆的分代结构

现代 JVM 通常把堆分成：

- 新生代（Young Generation）
- 老年代（Old Generation）

新生代又通常分为：

- Eden 区
- Survivor From
- Survivor To

示意图：

Heap
├── Young
│   ├── Eden
│   ├── S0
│   └── S1
└── Old

---

## 三、为什么 JVM 要分代回收

核心思想叫：

大部分对象朝生夕死，少量对象长期存活

比如：

- 请求过程中创建的 DTO、临时字符串、Map、List，通常很快就没用了
- 缓存对象、连接池对象、Spring 单例 Bean，生命周期会很长

所以 JVM 采取“分代回收”：

- 新生代：频繁回收，速度快
- 老年代：回收频率低，但更重

这就是 分代回收思想。

---

## 四、垃圾回收机制到底是什么

---

### 什么对象会被当成垃圾

最本质的问题是：

JVM 怎么知道一个对象已经没用了？

有两种常见思路：

#### 1. 引用计数法

对象每被引用一次，计数 +1；引用失效则 -1。
计数为 0 就说明对象可回收。

但 JVM 主流并不用这个方法，因为它解决不了循环引用问题。

---

#### 2. 可达性分析（JVM 实际使用）

JVM 从一组叫 GC Roots 的根对象开始向下找引用链：

- 栈中局部变量引用的对象
- 静态变量引用的对象
- 常量引用的对象
- JNI 引用的对象
- 活跃线程对象等

如果一个对象从 GC Roots 出发不可达，就认为它是垃圾。

---

### 对象回收并不是“立刻删掉”

JVM 不是像 free() 那样手工释放。
而是在某个时机做 GC，把不可达对象占用的内存收回。

---

## 五、垃圾回收算法

GC 的底层并不是一种方法，而是多种算法组合使用。

---

### 1. 标记-清除（Mark-Sweep）

流程

1. 标记哪些对象还活着
2. 清除没标记的对象

优点

- 实现简单

缺点

- 会产生内存碎片
- 清理效率一般

示意：

[存活][垃圾][存活][垃圾][垃圾][存活]
清除后：
[存活][空洞][存活][空洞][空洞][存活]

碎片多了之后，即使总空闲内存够，也可能找不到一块连续大内存分配大对象。

---

### 2. 复制算法（Copying）

流程

把内存分成两块，每次只用一块。
GC 时把存活对象复制到另一块，再一次性清空原区域。

优点

- 没有碎片
- 回收快

缺点

- 需要额外空间
- 如果存活对象多，复制成本高

适用

特别适合 新生代，因为新生代大多数对象都很快死掉，真正活下来的少，复制成本低。

---

### 3. 标记-整理（Mark-Compact）

流程

1. 标记存活对象
2. 不直接清除，而是把存活对象往一端移动
3. 清理边界外的内存

优点

- 没有碎片
- 比单纯标记清除更适合老年代

缺点

- 移动对象有成本
- 停顿时间可能更长

---

### 4. 分代收集算法

这是 JVM 实际采用的总体策略：

- 新生代：一般用 复制算法
- 老年代：一般用 标记清除 或 标记整理
- 不同垃圾收集器有不同实现细节

---

## 六、对象在堆里的生命周期

这个过程很重要。

---

### 1. 对象先进入 Eden

新对象通常先分配在 Eden 区。

---

### 2. Eden 满了会触发 Minor GC / Young GC

JVM 扫描 Eden 和一个 Survivor 区，把还活着的对象复制到另一个 Survivor 区。

---

### 3. 对象年龄增长

对象每熬过一次 Young GC，年龄 +1。

---

### 4. 晋升到老年代

当对象年龄达到阈值（比如 15），或者 Survivor 放不下时，会进入老年代。

---

### 5. 老年代满了可能触发 Full GC / Major GC

这类 GC 更重，停顿通常更长。

---

## 七、什么是 Minor GC、Major GC、Full GC

这几个词很容易混。

---

### 1. Minor GC / Young GC

针对新生代的回收。

特点：

- 发生频率高
- 回收速度快
- 停顿一般较短

---

### 2. Major GC

通常指针对老年代的 GC。
但实际不同收集器和工具里定义可能不完全一致。

---

### 3. Full GC

一般指对整个堆甚至包括方法区/元空间的较重回收。

特点：

- 非常贵
- 停顿长
- 线上最怕频繁 Full GC

所以线上调优最常见目标之一就是：

尽量减少 Full GC

---

## 八、STW 是什么

STW = Stop The World

意思是：

GC 某些阶段执行时，用户线程全部暂停

也就是说：
- 你业务线程不跑了
- 所有请求可能都会卡住
- GC 完了才恢复

为什么很多线上接口 RT 抖动很大？
很多时候根因不是代码慢，而是 GC 停顿。

---

## 九、常见垃圾收集器

这是“垃圾回收机制”里非常重要的部分。

---

### 1. Serial 收集器

单线程收集器，GC 时只有一个线程工作，而且会 STW。

优点

- 简单
- 单核、小内存场景开销低

缺点

- 停顿明显
- 不适合大内存和高并发服务

---

### 2. ParNew / Parallel Scavenge

都是新生代的多线程收集器。

Parallel Scavenge

更关注 吞吐量。

适合：
- 后台计算
- 对停顿不太敏感但希望高吞吐的场景

---

### 3. CMS（Concurrent Mark Sweep）

老年代收集器，目标是低停顿。
它曾经非常经典，但现在已经逐渐退出主流。

过程

- 初始标记（STW）
- 并发标记
- 重新标记（STW）
- 并发清除

优点

- 停顿短

缺点

- 会产生碎片
- 对 CPU 敏感
- 可能出现 Concurrent Mode Failure
- JDK 新版本里已经被淘汰趋势很明显

---

### 4. G1（Garbage First）

现在服务端非常主流的收集器之一。

核心思想

G1 不再简单按连续的新生代/老年代逻辑管理，而是把堆划分成很多小的 Region。

它会优先回收“垃圾最多、收益最高”的 Region，所以叫 Garbage First。

特点

- 面向大堆内存
- 可以预测停顿时间
- 兼顾吞吐量和低停顿
- 支持并发标记
- 减少内存碎片

为什么 G1 常用

因为它相比 CMS 更现代化，适合大部分中大型 Java 服务。

---

### 5. ZGC

JDK 新时代的低延迟收集器。

特点

- 停顿极短，通常可控制在毫秒级甚至更低
- 支持超大堆
- 并发做大部分 GC 工作

适合

- 超低延迟系统
- 大堆内存服务
- 对 STW 极其敏感的场景

不足

- 对 JVM 版本和运行环境有要求
- 某些业务场景未必有必要上这么先进的收集器

---

### 6. Shenandoah

也是低延迟 GC，和 ZGC 思路接近，目标也是尽量降低停顿。

---

## 十、GC 收集器怎么选

可以粗略这么理解：

### 1. 小应用 / 简单任务

- Serial
- Parallel

### 2. 常规线上服务

- G1 是现在最常见的默认优选之一

### 3. 超低延迟、大堆

- ZGC
- Shenandoah

如果没有特别明确需求，现代 Java 服务大多数情况下：

先用 G1，再根据指标决定是否升级到 ZGC

## 十一、JVM 调优到底调哪些东西

调优其实不是乱改参数，而是围绕以下几件事展开。

---

### 1. 堆大小

常见参数：

-Xms4g
-Xmx4g

含义：

- -Xms：初始堆大小
- -Xmx：最大堆大小

一般线上建议：

Xms 和 Xmx 设成一样，避免堆动态扩容带来的额外抖动

---

### 2. 新生代和老年代比例

以前很多人喜欢手动配：

-XX:NewRatio=2
-XX:SurvivorRatio=8

但在 G1 下，很多细粒度分代参数不一定还像老年代收集器时代那样重要。
所以不是所有参数都值得手调。

---

### 3. 元空间大小

-XX:MetaspaceSize=256m
-XX:MaxMetaspaceSize=512m

如果类加载很多，比如：

- 动态代理多
- 热部署
- Groovy / Scala / 字节码增强
- 大量第三方框架

就要关注元空间。

---

### 4. 选择垃圾收集器

例如：

-XX:+UseG1GC

或使用 ZGC：

-XX:+UseZGC

---

### 5. G1 常见调优参数

比如：

-XX:MaxGCPauseMillis=200

意思是希望 GC 停顿目标尽量控制在 200ms 左右。
注意这是目标，不是强保证。

还有：

-XX:InitiatingHeapOccupancyPercent=45

表示堆使用到一定比例时开始并发标记。

---

## 十二、JVM 调优的正确方法

这个部分最重要，因为面试和实战最看重“方法论”。

---

### 1. 第一步：先看现象

你不能一上来就改参数，要先问：

- 是 CPU 高？
- 是内存涨？
- 是 RT 抖？
- 是 Full GC 频繁？
- 是 OOM？
- 是容器被杀？
- 是 Young GC 太频繁？

---

### 2. 第二步：收集指标

重点看这些：

GC 指标

- Young GC 次数
- Young GC 平均停顿
- Full GC 次数
- Full GC 停顿时间
- GC 总耗时占比

堆内存指标

- Eden 使用率
- Survivor 使用率
- Old 区使用率
- 对象晋升速度

系统指标

- CPU 使用率
- Load
- RT/P99
- 吞吐量
- 线程数

---

### 3. 第三步：看 GC 日志

现在一般打开 GC 日志：

JDK9+：

-Xlog:gc*:file=gc.log:time,uptime,level,tags

老版本常见：

-XX:+PrintGCDetails
-XX:+PrintGCDateStamps
-Xloggc:gc.log

GC 日志能看出：

- 哪种 GC 在发生
- 每次回收前后堆大小变化
- 停顿时长
- 是否频繁晋升到老年代
- 是否有 Full GC
- 是否 evacuation failure / promotion failure

---

### 4. 第四步：定位根因

比如常见现象与根因：

现象 1：Young GC 很频繁

可能原因：
- 新生代太小
- 短命对象太多
- 对象创建过于频繁
- 缓冲区设计不合理

---
现象 2：老年代增长很快

可能原因：
- 大对象直接进入老年代
- 长生命周期对象太多
- 缓存泄漏
- 对象晋升过快
- 内存泄漏

---
现象 3：Full GC 频繁

可能原因：
- 老年代不够
- 元空间不够
- 内存泄漏
- 显式 System.gc()
- 晋升失败

---
现象 4：GC 停顿长

可能原因：
- 堆太大
- 老年代对象太多
- 碎片严重
- 收集器不合适
- 引用链太复杂

---

## 十三、常见调优思路

---
场景 1：Young GC 太频繁

可能做法

1. 增大堆 / 新生代
2. 优化代码，减少临时对象
3. 避免无意义对象创建
4. 检查 JSON 序列化、字符串拼接、大量 Map/List 构建

代码层常见问题

比如：

```text
for (...) {
String s = a + b + c;
}
```
大量循环里不断产生临时字符串对象，会增加新生代压力。

---
场景 2：Full GC 太频繁

先看是不是内存泄漏

如果每次 Full GC 后老年代还是降不下来，说明很可能不是“内存不够”，而是“垃圾回不掉”。

这时要用：

- jmap -dump
- MAT（Memory Analyzer Tool）

去看：
- 哪类对象最多
- 谁引用着它们
- 是否缓存没清
- 是否 ThreadLocal 泄漏
- 是否连接对象没释放

---
场景 3：停顿时间太长

调优方向

1. 选择更适合低延迟的收集器（如 G1 / ZGC）
2. 调整堆大小
3. 减少老年代压力
4. 避免巨型对象
5. 优化缓存结构

---
场景 4：容器环境 OOM / 被 Kill

现在很多服务跑在容器里，要特别注意：

- JVM 可见内存不等于容器限制
- 除了堆，还有：
- Metaspace
- Direct Memory
- Thread Stack
- Code Cache
- Native 内存

所以你给堆分 6G，不代表总内存只用 6G。

## 十五、几个典型面试/实战问题

---

### 1. 为什么新生代适合复制算法

因为新生代对象大多朝生夕死，存活对象少，复制成本低，而且没有碎片。

---

### 2. 为什么老年代不适合纯复制算法

因为老年代对象存活率高，如果每次都大量复制，成本太高。

---

### 3. 为什么 Full GC 可怕

因为它往往涉及整个堆甚至更多区域，STW 时间长，对线上 RT 和吞吐影响大。

---

### 4. CMS 和 G1 的区别

简单说：

- CMS：以低停顿为目标，但会有碎片
- G1：Region 化管理，可预测停顿，更现代，适合大堆

---

### 5. 什么叫内存泄漏

Java 有 GC，不代表不会泄漏。
只要对象本来应该释放，但仍然被引用链持有，就是内存泄漏。

典型如：
- 静态集合不断放数据
- 缓存无上限
- ThreadLocal 未清理
- 监听器/回调未注销

---

## 十六、一个实际调优案例思路

假设线上出现：

- 接口 RT 抖动严重
- CPU 正常
- 但每隔几分钟有 1~2 秒卡顿

排查思路：

第一步：看监控

发现 Full GC 次数高，停顿 1.5s

第二步：看 GC 日志

发现老年代快满时频繁 Full GC

第三步：看堆 dump

发现某个本地缓存 Map 一直增长，没有淘汰机制

第四步：处理

1. 给缓存加容量上限 / 过期策略
2. 临时增大堆避免立刻打爆
3. 观察 Full GC 是否下降
4. 评估是否切换 G1 / 调整停顿目标

这个例子说明：

JVM 调优很多时候最后会落到“代码和对象生命周期设计”上，不只是改启动参数。

---

## 十七、JVM 调优的一些经验原则

---

### 1. 不要迷信参数

参数调优只能缓解，不能治好内存泄漏。

---

### 2. 先看业务对象生命周期

很多 GC 问题，根本原因是：
- 创建对象太猛
- 缓存太大
- 对象引用链没释放

---

### 3. Full GC 频繁优先查根因

不要只想着“把堆调大”。
堆调大只是延后爆炸时间。

---

### 4. 调优要基于监控和日志

没有数据支撑的调优基本都是玄学。

---

### 5. 现代服务优先考虑 G1

如果没有特殊理由，G1 通常是比较稳的起点。

---

### 6. 超低延迟场景再考虑 ZGC

不是所有项目都需要 ZGC，别为了新而新。

---

## 十八、如果你面试时怎么回答

你可以这样组织：

---
简版回答模板

### 1. 垃圾回收机制

- JVM 通过可达性分析判断对象是否存活
- 堆一般分新生代和老年代
- 新生代对象大多朝生夕死，适合复制算法
- 老年代对象存活率高，常用标记清除/标记整理
- GC 分为 Young GC、Full GC 等
- GC 过程中会有 STW，停顿会影响业务 RT

### 2. 常见收集器

- Serial、Parallel、CMS、G1、ZGC
- 目前服务端常见优先选 G1
- 低延迟大堆场景可考虑 ZGC

### 3. JVM 调优

- 目标是降低 GC 频率、降低停顿、提高吞吐
- 核心手段包括调整堆大小、选择合适 GC、分析 GC 日志、排查内存泄漏
- 调优必须结合监控、GC 日志、heap dump，而不是盲调参数

一句话理解：

- 垃圾回收机制解决的是：哪些对象该回收、怎么回收、什么时候回收
- JVM 调优解决的是：让 GC 更少打扰业务、让内存更稳定、让吞吐和延迟更符合目标

所以真正重要的是这个链路：

对象创建行为
→ 堆内存分布
→ GC 触发频率
→ 停顿时间
→ RT / 吞吐 / 稳定性

---
总结

- JVM GC 的核心是 可达性分析 + 分代回收。
- 新生代一般用 复制算法，老年代一般用 标记清除/标记整理。
- GC 会带来 STW，所以线上最关注 Young GC 频率、Full GC 次数、GC 停顿时间。
- 常见收集器里，现代 Java 服务通常优先考虑 G1，超低延迟场景可考虑 ZGC。
- JVM 调优不是单纯调参数，而是结合 监控、GC 日志、heap dump、对象生命周期设计 去定位和解决问题。

指数退避，英文一般叫 Exponential Backoff，是做重试时非常常见的一种策略。

它的核心思想是：

第一次失败后先等一小会儿再重试；
如果还失败，就等更久；
再失败，就等得更更久。
等待时间按“指数级”增长。

---

## 一、为什么需要指数退避

假设一个服务调用第三方接口失败了。

如果你立刻不停重试，会有几个问题：

1. 把对方压得更死
- 对方本来就已经异常了
- 你还疯狂补刀式重试
- 整个系统更难恢复
2. 自己也被拖垮
- 线程、连接、CPU 都被重试占住
- 形成“重试风暴”
3. 瞬时故障本来能恢复，却被放大成雪崩
- 比如网络抖动 1 秒
- 如果 1 秒内你发了 1000 次重试，问题就更严重了

所以要让重试“有节奏”，不要上来猛冲。
这就是指数退避存在的意义。

---

## 二、什么叫“指数”

所谓指数，就是等待时间不是线性增加，而是像这样增长：

第1次重试：1秒
第2次重试：2秒
第3次重试：4秒
第4次重试：8秒
第5次重试：16秒

它通常符合一个公式：

等待时间 = base * 2^n

比如：

- base = 1s
- n = 0,1,2,3...

那就是：

- 1s
- 2s
- 4s
- 8s
- 16s

这就是“指数退避”。

---

## 三、为什么叫“退避”

“退避”你可以理解成：

遇到失败，不是硬顶，而是先后退一下，给系统恢复时间。

所以它的本质不是“慢”，而是：

- 降低冲击
- 给恢复窗口
- 避免重试放大故障

---

## 四、一个生活化例子

假设你给朋友打电话，对方没接：

- 不是每 0.1 秒打一遍
- 而是：
- 1 分钟后再打
- 2 分钟后再打
- 4 分钟后再打
- 8 分钟后再打

这样更合理。

如果你每秒打一遍：

- 对方烦
- 线路忙
- 你自己也浪费精力

这就是指数退避的直觉。

---

## 五、在系统里一般怎么用

指数退避经常用在这些场景：

### 1. 接口调用失败重试

比如：
- 调第三方支付
- 调下游 RPC
- 调数据库代理层
- 调消息投递接口

---

### 2. 网络连接重连

比如：
- WebSocket 断线重连
- MQ 客户端重连
- 服务注册中心重连

---

### 3. 分布式锁竞争失败后重试

比如 Redis 锁没抢到，不要立刻死循环抢。

---

### 4. 限流/429 场景

如果服务器告诉你：
- 请求太多
- 稍后再试

这时就很适合指数退避。

---

## 六、一个简单例子

假设你请求一个接口，最多重试 5 次：

第1次失败 → 等 1 秒
第2次失败 → 等 2 秒
第3次失败 → 等 4 秒
第4次失败 → 等 8 秒
第5次失败 → 等 16 秒
仍失败 → 放弃

这样比“每次都等 1 秒”更稳。

---

## 七、为什么不能只用固定间隔重试

比如固定每次都等 1 秒：

1s, 1s, 1s, 1s, 1s

问题是：

- 故障如果持续时间较长，固定重试仍然很密集
- 大量客户端会在同一时刻重复打过来
- 容易形成脉冲式流量洪峰

而指数退避会逐渐拉开间隔，更平滑。

---

## 八、指数退避通常要加“随机抖动”

这是实战里非常重要的一点。

如果所有客户端都严格按：

1s, 2s, 4s, 8s

那它们还是会在同一时刻一起重试。
这就叫惊群效应或重试雪崩。

所以通常要加一个随机值（jitter，抖动）：

第1次：1s + 随机几十毫秒
第2次：2s + 随机几百毫秒
第3次：4s + 随机一点偏移

比如：

wait = base * 2^n + random(0, 500ms)

这样不同客户端的重试时间就错开了。

---

## 九、常见几种形式

### 1. 纯指数退避

1s, 2s, 4s, 8s, 16s

### 2. 指数退避 + 最大上限

因为不能无限等下去，所以常会设置 cap：

1s, 2s, 4s, 8s, 16s, 30s, 30s, 30s...

公式类似：

wait = min(base * 2^n, maxDelay)

### 3. 指数退避 + 抖动

最推荐的实战版本：

wait = min(base * 2^n, maxDelay) + randomJitter

---

## 十、一个伪代码例子

```text
int retry = 0;
long baseDelay = 1000; // 1秒
long maxDelay = 30000; // 最多30秒
while (retry < 5) {
try {
callService();
break;
} catch (Exception e) {
long delay = Math.min(baseDelay * (1L << retry), maxDelay);
long jitter = ThreadLocalRandom.current().nextLong(200);
Thread.sleep(delay + jitter);
retry++;
}
}
```
意思就是：

- 第 1 次失败等 1 秒左右
- 第 2 次失败等 2 秒左右
- 第 3 次失败等 4 秒左右
- ...
- 但最多不超过 30 秒
- 再加一点随机抖动

---

## 十一、它适合什么场景

指数退避适合：

- 瞬时故障：网络抖动、短暂超时、服务短时不可用
- 需要重试但不能打爆对方
- 多个客户端并发重试
- 下游恢复需要时间

---

## 十二、它不适合什么场景

不是所有失败都该指数退避。

### 1. 参数错误

比如你传参错了，重试 100 次也没用。

### 2. 权限错误

比如 401 / 403，说明没权限，不该盲目重试。

### 3. 业务明确失败

比如“余额不足”“库存不足”，这不是瞬时故障，不能靠重试解决。

所以指数退避通常只用于：

可恢复的临时性失败

---

## 十三、和“普通重试”的区别

普通重试

- 失败就马上重试
- 或固定 1 秒重试一次

指数退避重试

- 每失败一次，等待时间变长
- 更温和
- 更适合故障恢复场景

---

## 十四、你可以怎么记

一句话记忆：

指数退避 = 重试时等待时间按 2 的幂次增长，用来避免失败时疯狂重试把系统压垮。

---
总结

- 指数退避是一种重试策略：失败后不是立刻重试，而是按 1s、2s、4s、8s... 这种指数级增长的间隔去重试。
- 目的不是“拖慢”，而是防止重试风暴、给系统恢复时间、减少雪崩风险。
- 实战中通常会配合：
- 最大等待上限
- 随机抖动（jitter）
- 最大重试次数
- 它适合临时性、可恢复性故障，不适合参数错误、权限错误、业务确定失败这类场景。
