## 一、死锁的四个必要条件（打破任一即可预防）

| 条件 | 说明 |
| --- | --- |
| 互斥 | 资源同一时刻只能被一个线程占用 |
| 占有并等待 | 线程持有资源同时等待其他资源 |
| 不可抢占 | 资源不能被强制剥夺 |
| 循环等待 | 线程间形成环形等待链 |

## 二、预防死锁（开发阶段）

### 1. 固定加锁顺序（打破循环等待）

```java
// ❌ 危险：线程A锁1→锁2，线程B锁2→锁1
synchronized (lockA) {
synchronized (lockB) { ... }
}
// ✅ 安全：所有线程统一按 lockA → lockB 顺序加锁
// 可用锁对象的 System.identityHashCode() 决定顺序
int hashA = System.identityHashCode(lockA);
int hashB = System.identityHashCode(lockB);
Object first  = hashA < hashB ? lockA : lockB;
Object second = hashA < hashB ? lockB : lockA;
synchronized (first) {
synchronized (second) { ... }
}
```

### 2. 使用 tryLock 设置超时（打破不可抢占）

```java
ReentrantLock lockA = new ReentrantLock();
ReentrantLock lockB = new ReentrantLock();
boolean acquiredA = lockA.tryLock(1, TimeUnit.SECONDS);
boolean acquiredB = acquiredA && lockB.tryLock(1, TimeUnit.SECONDS);
try {
if (!acquiredA || !acquiredB) {
// 获取失败，回退重试，避免死锁
return;
}
// 业务逻辑
} finally {
if (acquiredB) lockB.unlock();
if (acquiredA) lockA.unlock();
}
```

### 3. 一次性申请所有资源（打破占有并等待）

```java
// 用统一的资源管理器，原子性地申请全部资源
ResourceManager.acquireAll(resourceA, resourceB, resourceC);
```

### 4. 缩小锁粒度，减少持锁时间

```java
// ❌ 持锁期间做耗时 IO
synchronized (this) {
data = fetchFromRemote(); // 远程调用持锁
process(data);
}
// ✅ 锁外准备，锁内只操作共享状态
Data data = fetchFromRemote();      // 锁外完成
synchronized (this) {
process(data);                   // 锁内只做必要操作
}
```

## 三、数据库死锁（最常见场景）

### 常见原因

- 不同事务以不同顺序更新多行
- 大事务持锁时间过长
- 索引缺失导致全表锁

### 解决方案

```sql
-- 1. 保证多事务操作同一批数据时顺序一致（按主键排序）
UPDATE orders SET status = 1 WHERE id IN (1, 2, 3) ORDER BY id;
-- 2. 缩短事务，尽快提交
BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 1;
COMMIT;  -- 立即提交，不要夹杂其他查询
-- 3. 检测到死锁时重试（MySQL InnoDB 自动回滚其中一方）
-- 应用层捕获 1213 错误码并重试
```

## 四、检测与诊断

### Java 线程死锁检测

获取 JVM 线程 dump，搜索 "deadlock"

```bash
jstack <pid> | grep -A 20 "deadlock"
```

或使用 JConsole / VisualVM 可视化检测。

### 数据库死锁日志

```sql
-- MySQL 查看最近一次死锁详情
SHOW ENGINE INNODB STATUS;
-- 查看当前锁等待
SELECT * FROM information_schema.INNODB_LOCK_WAITS;
```

## 五、解决优先级建议

高频死锁  →  先找循环等待链 → 统一加锁顺序（最有效）
偶发死锁  →  tryLock + 重试 兜底
数据库死锁 → 拆分事务 + 索引优化
架构层    → 考虑无锁设计（CAS/Disruptor）或串行化（单线程队列）
