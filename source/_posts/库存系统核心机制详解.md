## 一、库存扣减链路

整个链路以 **出库审核（auditStockOut）** 为入口，经过 9 个串行阶段完成，全部在同一个数据库事务内。

### 1.1 链路全貌

```text
用户触发出库审核
│
▼
StockOutWriteServiceImpl.auditStockOut()           ← 第1层：出库业务服务
│
├─ 1. 组装 StockOutFormBO（设置 status=DONE）
│
▼
StockOutWriteServiceImpl.saveStockOut4front()      ← 第2层：通用保存入口
│
├─ 2. 前置校验（会计期间、负库存开关、在途管理）
│
├─【事务开始】
│
▼
StockInOutStandardWriteServiceImpl
.executeInOutStandardProcess()                   ← 第3层：标准出入库编排引擎
│
├─ Step 1  listUpdatePair     → 读取 DB 当前状态，组成 before/after 对
├─ Step 2  setUniqueId        → 为每条明细生成唯一幂等 ID
├─ Step 3  arrangeItem        → 按依赖关系排序（防止先出后入成本错误）
│
│  ── 以下对每张单据串行执行 ──
│
├─ Step 4  calcOperationType  → 判断是 AUDIT/ANTI_AUDIT/RECALCULATE
├─ Step 5  checkBizTime       → 校验业务日期在会计期间内
├─ Step 6  calcAmountChange   → 计算数量变化量（Δamount）
├─ Step 7  position()         → 【定位】确定实物批次 → 分配到具体仓库/批次
├─ Step 8  valuation()        → 【计价】从财务批次扣减 → 确定成本金额
├─ Step 9  updatePriceAndMoney→ 将计价结果回写到单据明细的 stock_price/stock_money
├─ Step 10 saveCalcArgs       → 保存本次定位计价参数（供成本重算用）
├─ Step 11 saveStockChange()  → 【核心】实际写库存结存
├─ Step 12 saveItem()         → 持久化出库单主表和明细
│
├─【事务提交】
│
├─ 3. 操作日志记录
├─ 4. 在途占用释放（invokeManageStockOccupyOrRelease）
└─ 5. 注册 ES 索引更新事件
```

### 1.2 最关键的两个阶段：定位 & 计价

#### Step 7 — 定位（Position）：确定从哪个实物批次扣

`StockPositionExecutor.position()` 根据 `StockPositionCodeEnum`（定位策略码）决定怎么把出库量分配到具体的实物批次记录（`stock_physical_batch_detail`）：

| 定位策略 | 说明 |
|---|---|
| 按默认批次（SYSTEM批次） | 没有批次管理时，所有数量归一个系统批次 |
| 按物理批次（FEFO） | 有批次/效期时，按先过期先出顺序分配 |
| 按依赖单据 | 返货入库等，继承来源出库单的批次 |

输出：`List<StockPhysicalBatchChangeBO>`，每条记录说明哪个批次扣多少数量。

#### Step 8 — 计价（Valuation）：确定出库成本金额

`StockValuationExecutor.valuation()` 根据 `StockValuationCodeEnum`（计价策略码），从财务批次（`stock_financial_batch_detail`）按比例扣减成本金额：

```java
// StockValuationStrategy207Impl — 主策略"按比例依次扣减"
outMoney = APMCalculateUtil.calculateNewMoney(
batchAmount,   // 批次当前数量
batchMoney,    // 批次当前金额
outAmount      // 本次出库数量
);
// 即 outMoney = batchMoney × (outAmount / batchAmount)
```

输出：`List<StockFinancialBatchChangeBO>`，每条记录说明哪个财务批次扣多少金额（Δmoney）。

### 1.3 Step 11 — saveStockChange：最终写库存

这是真正扣减库存数据的地方：`SaveStockChangeExecutorImpl.saveStockChange()` → `StockChangeWriteServiceImpl.changeStock()`。

写之前先做两件事：
1. `buildGoodsAllowNegativeMap()` — 查物品档案，每个物品是否允许负库存
2. `doHandleStockCheckNegative()` — 审核/反审核时，对盘点场景做负库存前置处理

写的内容（在同一个事务内，按 `id ORDER` 防死锁）：

```sql
-- ① stock_physical_batch_detail（实物批次结存）
WHERE (id, version) IN (...)                    -- 乐观锁版本号校验
SET amount = #{newAmount}, version = version + 1
-- 如果 WHERE 匹配行数=0 → 并发冲突，回滚
-- ② stock_financial_batch_detail（财务批次结存）
WHERE (id, version) IN (...)                    -- 同上
SET amount = amount + #{delta},
money  = money  + #{delta_money}
-- ③ stock（仓库维度结存）
SET amount      = amount      + #{delta}        -- 原子增量，无需版本号
money       = money       + #{delta_money}
lock_amount = lock_amount + #{delta_lock}
ORDER BY id                                     -- 固定顺序防死锁
-- ④ stock_org（机构维度结存）
SET amount = amount + #{delta}                  -- 同上，原子增量
ORDER BY id
-- ⑤ stock_change_item（变更流水）
INSERT — 记录本次变更的 before/after 快照，供 MQ 下游消费
```

### 1.4 Step 7+11 联动的负库存检查

实物批次这一层做了应用层兜底校验（`validateForPhysicalChangeStockDetail`），在 `doChangePhysicalBatchDetailAndFlow()` 内，写库之前：

```java
// 出库后 afterAmount = beforeAmount + changeAmount（changeAmount 为负数）
// afterAmount - lockAmount < 0 且 不允许负库存 → 抛 LACK_STOCK 异常
if (!allowNegative && isNegative(afterAmount - lockAmount)) {
invalidGoodsIdList.add(goodsId);  // 收集所有不足的物品
}
// 最终抛异常 → 整个事务回滚
throw new BizRuntimeException(ErrorCode.LACK_STOCK, goodsNames);
```

### 1.5 事务外的收尾工作

事务提交成功后，`saveStockOut4front` 还做：

```java
// 1. 在途占用释放
invokeManageStockOccupyOrRelease(hqId, stockOutBOS);
// 出库审核完成 → 删除 stock_occupy_record（amount=0 或 deleteByUniqueKeys）
// 表示这笔货已确认出库，不再是"在途预计出库"
// 2. 操作日志
batchAddOperationLog(...)
// 3. ES 索引注册（事务提交后异步触发）
registerStockInOutESRollBackUpdateEvent(...)
// → 事务提交后通过 TransactionSynchronization.afterCommit() 发 MQ
// → 更新 ES 全文索引，供搜索使用
```

### 1.6 完整流程图

```sql
auditStockOut
│
└── saveStockOut4front (outer transaction)
│
├── [Transaction]
|  |  |  |  |
| --- | --- | --- | --- |
|  | ├── arrange (排序，依赖先算) |  |  |
|  |  |  |  |
|  | ├── position() |  |  |
|  |  | ├── 分配实物批次 (FEFO/系统批次) |  |
|  |  | └── 输出 Δphysical_batch |  |
|  |  |  |  |
|  | ├── valuation() |  |  |
|  |  | ├── 从财务批次比例扣减 |  |
|  |  |  | outMoney = batchMoney × (out/batch) |
|  |  | └── 输出 Δfinancial_batch |  |
|  |  |  |  |
|  | └── saveStockChange() |  |  |
|  | ├── 负库存前置处理 |  |  |
|  | ├── UPDATE stock_physical_batch_detail (乐观锁) |  |  |
|  | ├── UPDATE stock_financial_batch_detail (乐观锁) |  |  |
|  | ├── UPDATE stock   (原子增量 + ORDER BY id) |  |  |
|  | ├── UPDATE stock_org (原子增量 + ORDER BY id) |  |  |
|  | └── INSERT stock_change_item (变更流水) |  |  |
└── [After Transaction]
├── 释放在途 stock_occupy_record
├── 操作日志
└── afterCommit() → MQ → ES 更新
```

> **核心并发安全**：`stock/stock_org` 用原子增量 SQL 保证高并发正确性；`stock_physical_batch_detail/stock_financial_batch_detail` 用乐观锁版本号防止并发覆盖；整条链路在同一个事务内保证原子性。

## 二、定位策略码 & 计价策略码

这两个策略码是出入库扣减链路的核心"指令"：**定位码**决定从哪个实物批次扣数量，**计价码**决定从哪个财务批次扣金额（成本）。两者在组装 FormBO 时硬编码写入，由 `StockItemCalcArgBO` 携带，贯穿整个 `executeInOutStandardProcess` 流水线。

### 2.1 定位策略码（StockPositionCodeEnum）

> **核心问题**：出库时，这笔货从"哪个实物批次桶"里扣？

#### 101 — USE_CURRENT_ITEM_BATCH（使用当前单据批次）

**适用场景**：几乎所有入库，以及反审核场景。

```text
采购入库 / 配送收货 / 其他入库 / 期初入库 / 盘盈入库
调整入库 / 期末调整 / 寄售入库 / 期初单 / 销售退货入库
```

**执行逻辑（StockPositionStrategy101Impl）**：
1. 有指定批次号：明细行上已经填了 `physicalBatchNum`，直接用单据上的批次创建/更新实物批次档案（`initStockPhysicalBatch`），再关联到该批次
2. 无指定批次号：以 `(goodsId + 生产日期)` 为 key，匹配已存在的批次档案，自动归到对应批次

**核心语义**：入库时新货进来，"按单据说了算"，单据上写了什么批次就放哪个批次桶。

---

#### 102 — USE_SOURCE_ITEM_BATCH（使用来源单据批次）

**适用场景**：有钩稽关系的入库，批次必须继承上游出库单。

```text
移库入库（从移库出库单继承批次）
调拨收货入库（从调拨出库单继承批次）
部门领料入库 / 部门退料入库
生产委外入库
```

**执行逻辑（StockPositionStrategy102Impl）**：
1. 先从 `extraBizRequest.dependencyItemSns` 读取依赖的来源单据号
2. 查询来源单据（如移库出库单）的明细，取其 `physicalBatchNum`
3. 以 `(goodsId + bizUnitId + 数量)` 为 key，将入库明细精确匹配到来源单据对应的批次上
4. 处理来源单据明细被"拆分"的情况（`uniqueId` 包含 `|` 分隔符时合并再分配）

**核心语义**：物品从 A 仓库移到 B 仓库，批次信息必须跟着走，A 仓库是什么批次，B 仓库就是什么批次，不能凭空产生新批次。

---

#### 103 — TAKE_STOCK_ENOUGH_BATCH_IN_ORDER（按顺序取结存足够的批次）

**适用场景**：几乎所有出库。

```text
配送发货 / 盘亏 / 报损 / 其他出库 / 菜品销售出库
外销客户出库 / 调拨出库 / 盘点出库 / 寄售出库
```

**执行逻辑（StockPositionStrategy103Impl）**：
1. 有指定批次：直接用明细行上的 `physicalBatchNum`，创建/匹配批次，直接扣
2. 无指定批次：调用 `suggestByOutAmountWithSigned`，按批次剩余量自动推荐分配方案（FEFO 先过期先出或 FIFO 先进先出），将出库量按比例分配到一个或多个批次上，直到出库量被满足（MUST_COMPLETED 模式）

**核心语义**：出库时不确定从哪个批次扣，系统自动"按顺序找够了为止"，并合并同一批次的多条分配结果（`mergeChangeDetails`）。

---

### 2.2 计价策略码（StockValuationCodeEnum）

> **核心问题**：出入库时，这笔货的**成本金额（stock_money）**怎么算？

#### 201 — USE_CURRENT_ITEM_PRICE（使用当前单据价格）

**适用场景**：入库单据自带价格，直接用单据上的价格做成本。

```text
期初入库、调整入库（TZRK）
期末成本调整入库/出库（CTRK/CTCK）
移库入库（继承移库出库的金额，不重算）
寄售入库（成本即单据价格）
```

**执行逻辑（StockValuationStrategy201Impl）**：直接从当前入库单明细的 `noTaxMoney/money` 字段读取，不查库存均价，也不做任何计算。

价源标记：`SPECIFIC_MANUALLY_USER_INPUT（110）` 或 `SPECIFIC_MANUALLY_SYSTEM_DETERMINE（130）`

---

#### 202 — USE_SOURCE_ITEM_PRICE（使用来源单据成本价）

**适用场景**：入库时成本直接继承上游出库单的 `stock_price/stock_money`。

```text
返货入库（FHRK，继承配送发货出库成本）
客户退货入库（KTRK，继承客户销售出库成本）
配送返货驳回入库（继承返货出库成本）
```

**执行逻辑（StockValuationStrategy202Impl）**：查询依赖的来源出库单，取其已计算好的 `stock_price × 入库数量`，得到入库成本金额。与 201 的区别是：201 用结算价，202 用来源出库的库存成本价。

---

#### 203 — USE_ORG_WIN_PRICE（使用机构盘盈价）

**适用场景**：无依赖来源、成本需要查库存均价来暂估的入库。

```text
盘盈入库（PYRK，无来源单）
盘盈入库（来自盘点单，使用库存均价）
检验收货入库 / 寄售盘盈入库
```

**执行逻辑（StockValuationStrategy203Impl）**：按 `InventoryPriorityEnum` 的优先级链查价：

1. 仓库/机构实时均价（库存均价 = `stock_money / stock_amount`）
2. 最近一次入库价
3. 建议采购价（物品档案）
4. 0（无价格兜底）

价源标记：`SYSTEM_ESTIMATE_WAREHOUSE_AVG（510）`、`LATELY_PUT_STOCK_PRICE（550）` 等

---

#### 205 — USE_CURRENT_ITEM_FINANCIAL_BATCH（使用当前单据财务批次）

**适用场景**：入库后财务批次已确定，直接使用，不走计价推荐流程。

```text
反审核场景（恢复被反审核前的财务批次状态）
虚拟入库（采购入库虚拟 CGRX）
```

**执行逻辑**：直接用单据上已记录的 `financialBatchNum` 对应的财务批次，读取已有成本，不重算。

---

#### 207 — DEDUCT_PROPORTIONALLY_IN_ORDER（按比例依次扣减）⭐ 最核心

**适用场景**：绝大多数出库操作。

```text
配送发货 / 盘亏 / 报损 / 其他出库 / 菜品销售出库
调拨出库 / 外销出库 / 盘点出库 / 移库出库 / 寄售出库
```

**执行逻辑（StockValuationStrategy207Impl）**：

1. 按计价方式（移动加权/FIFO）从财务批次列表取货
2. 从最旧的批次开始，按比例扣减金额：`outMoney = batchMoney × (outAmount / batchAmount)`
3. 批次余量不足时跨批次继续扣
4. 所有合法批次扣完后还不够 → 从默认批次（兜底均价）出
5. 配置了使用结算价 → 直接用 `settlementMoney` 作为成本

---

#### 208 — CALCULATE_PRICE_BASE_ON_MARGIN（基于余量计算价格）

**适用场景**：出库时成本需要"反算"，依赖已知入库批次的余量来推算单价。

```text
退货出库（THCK，采购退货）—— 需要从采购入库批次反推出库成本
返货出库（FHCK）
```

**执行逻辑**：查找依赖的入库单的财务批次，用批次的 `(beginMoney / beginAmount)` 作为单价，再乘以出库数量得出出库成本，而不是从当前库存余量计算。

---

## 三、设计模式：策略模式 + 注册表模式

### 3.1 策略模式（Strategy Pattern）— 核心

完整的三要素全部在代码里：

**① 策略接口（Strategy）**

```java
// 定位策略接口
public interface StockPositionStrategy {
List<StockPhysicalBatchChangeBO> position(StockPositionBizRequest param);
StockPositionCodeEnum positionCode();  // ← 每个策略声明自己的 Code
}
// 计价策略接口
public interface StockValuationStrategy {
List<StockFinancialBatchChangeBO> valuation(StockValuationBizRequest param);
StockValuationCodeEnum valuationCode();
}
```

**② 具体策略（Concrete Strategy）**

```java
@Service
public class StockPositionStrategy101Impl implements StockPositionStrategy {
public StockPositionCodeEnum positionCode() { return USE_CURRENT_ITEM_BATCH; }
public List<StockPhysicalBatchChangeBO> position(...) { /* 使用当前单据批次 */ }
}
@Service
public class StockPositionStrategy103Impl implements StockPositionStrategy {
public StockPositionCodeEnum positionCode() { return TAKE_STOCK_ENOUGH_BATCH_IN_ORDER; }
public List<StockPhysicalBatchChangeBO> position(...) { /* 按顺序找够批次 */ }
}
// 计价同理：201Impl / 207Impl / ...
```

**③ Context（上下文）持有策略并调用**

```java
// StockPositionExecutorImpl 就是 Context
public List<StockPhysicalBatchChangeBO> position(StockPositionBizRequest request) {
StockPositionStrategy strategy = stockPositionStrategyMap.get(request.getPositionCode());
return strategy.position(request);   // ← 委托给策略执行
}
```

### 3.2 注册表模式（Registry Pattern）— 策略的组织方式

这是对纯策略模式的一个重要增强：不用 `if/else` 或 `switch` 选策略，而是用 **Map 作为注册表**，`@PostConstruct` 初始化时自动建立 `Code → Strategy` 的映射。

```java
@Service
public class StockPositionExecutorImpl implements StockPositionExecutor {
// Spring 自动注入所有实现了 StockPositionStrategy 的 Bean（即 101/102/103 三个实现）
@Resource
private List<StockPositionStrategy> stockPositionStrategyList;
// 注册表：Code → Strategy 的 Map
private Map<StockPositionCodeEnum, StockPositionStrategy> stockPositionStrategyMap;
@PostConstruct
public void init() {
// 启动时自动构建注册表
stockPositionStrategyMap = stockPositionStrategyList.stream().collect(
Collectors.toMap(StockPositionStrategy::positionCode, Function.identity())
);
}
public List<StockPhysicalBatchChangeBO> position(StockPositionBizRequest request) {
StockPositionStrategy strategy = stockPositionStrategyMap.get(request.getPositionCode());
return strategy.position(request);  // O(1) 查找，无分支
}
}
```

计价执行器 `StockValuationExecutorImpl` 结构完全一致。

### 3.3 两个模式的分工

```text
策略模式   ← 解决"同一行为有多种实现"的问题
定义接口 + 多个实现类，调用方通过接口调用，不感知具体实现
注册表模式 ← 解决"如何找到正确策略"的问题
用 Map 代替 if/else，O(1) 查找，新增策略只需新增实现类和注册
```

两者组合后，新增一种定位或计价方式只需：
1. 新增一个实现类，加 `@Service` 注解
2. 在 `StockPositionCodeEnum` 或 `StockValuationCodeEnum` 里加一个枚举值
3. Spring 启动时自动注入到 List，`@PostConstruct` 自动注册到 Map

**不需要修改任何已有代码，完全满足开闭原则。**

### 3.4 总结

| 模式 | 体现位置 | 解决的问题 |
|---|---|---|
| 策略模式 | `StockPositionStrategy` 接口 + 101/102/103 三个实现类 | 不同单据类型的定位/计价行为差异 |
| 注册表模式 | `@PostConstruct` 构建的 `Map<Code, Strategy>` | O(1) 派发策略，消除 if/else，新增策略无需改旧代码 |

## 四、计价策略 207 深度讲解

### 4.1 整体结构：三段式降级扣减

`valuation()` 方法的主干逻辑是三段式降级，前一段扣完就结束，扣不完才进下一段：

```text
valuation()
│
├─ 前置判断：是否使用结算价出库？
│       YES → createAndAssignDefaultBatchUseSettlementMoney()  直接用结算金额
│       NO  ↓
│
├─【第一段】assignValidFinancialBatch()  从合法财务批次按顺序扣减
│
├─【第二段】assignFromLastBatch()        合法批次扣完，从最后一个批次兜底
│
└─【第三段】createAndAssignDefaultBatch() 还不够，创建"默认批次"用参考价出
```

### 4.2 财务批次的三种状态

每次出库前，先理解财务批次（`stock_financial_batch_detail`）的三种状态（`FinancialBatchValidTypeEnum`）：

```java
// 判断规则：
amount > 0  && money >= 0  → VALID  （正常批次，有货可出）
amount == 0 && money == 0  → EMPTY  （空批次，已扣完）
其他                        → INVALID（异常批次，如 amount<0 或 amount=0 但 money≠0）
```

| 状态 | 含义 | 能出货吗 |
|---|---|---|
| VALID | 有数量、有金额，正常 | ✅ 优先从这里扣 |
| EMPTY | 已扣完，量金均为0 | ❌ 跳过 |
| INVALID | 异常，如负库存发生过 | ❌ 第一段跳过，第二段兜底 |

### 4.3 第一段：assignValidFinancialBatch（从合法批次按比例扣）

这是最核心的路径，覆盖正常情况。

**批次的排列顺序**

批次按 `sort_value ASC` 排序，`sort_value` 字段编码了业务日期 + 入库单号，保证了先入先出（FIFO）的顺序语义。移动加权模式下，所有批次合并为一个默认批次，顺序无意义；FIFO 模式下，不同批次严格按 `sort_value` 顺序消耗。

**计价方式分支（移动加权 vs FIFO）**

```java
// 确认计价法
Integer valuationWay = baseProxyService.listConfigurationByNames(...).getValuationWay();
boolean isSpecificIdentification = ValuationWayEnum.FIFO.getId() == valuationWay;
```

`isSpecificIdentification` 贯穿整个方法，决定批次的"聚合粒度"：
- `false`（移动加权）：按 `(warehouseId, goodsId)` 聚合，不区分批次号
- `true`（FIFO/个别计价）：按 `(warehouseId, physicalBatchNum, goodsId)` 聚合，严格区分每个批次

**bizDate 分支（实时均价 vs 历史均价）**

```java
if (!isSpecificIdentification && avgStockPriceCalcMethod == AvgStockPriceCalcMethodEnum.BIZ_DATE) {
request.setBizDate(bizDate);          // 取业务日期的快照均价
request.setDefaultFlag(YES);          // 只查默认批次（移动加权下只有一个默认批次）
} else {
request.setValidType(VALID);          // 只查正常批次
}
```

| 配置 | 含义 | 对应价源标记 |
|---|---|---|
| REAL_TIME | 用出库时刻的实时均价 | `MOVING_AVG_METHOD_WAREHOUSE_AVG（710）` |
| BIZ_DATE | 用单据业务日期的历史均价 | `MOVING_AVG_METHOD_BIZ_DATE_WAREHOUSE_AVG（720）` |

**核心扣减公式（按比例）**

```java
// 场景一：当前批次余量 >= 本次出库量 → 按比例扣
if (batchAmount + outAmount >= 0) {  // outAmount 是负数
outMoney = APMCalculateUtil.calculateNewMoney(
batchAmount,   // 批次当前数量
batchMoney,    // 批次当前金额
outAmount      // 本次出库量（负数）
);
// 展开 = batchMoney × (outAmount / batchAmount)
// 即：出库均价 = batchMoney / batchAmount，出库金额 = 出库均价 × 出库量
}
// 场景二：当前批次余量 < 本次出库量 → 把这个批次清空，继续找下一个批次
else {
outAmount = -batchAmount;         // 全部清空
outMoney  = -batchMoney;          // 金额全部出走
}
```

**分页循环查批次**

批次可能很多，用 `OffsetAdjustSearchBO` 做带偏移的分页，每次查 300 条，直到所有出库量分配完毕：

```java
while (true) {
List<StockFinancialBatchDetailBO> batches = queryFinancialBatchDetail(req);
if (isEmpty(batches)) break;
for (remain : remainAssignAmount) {
// 找到对应批次 → 按比例扣
// 扣完这一行 → 从 pair2UniqueIds 移除
}
if (isAllCompleted(remainAssignAmount)) break;  // 全部扣完 → 退出
// 否则 → 调整 offset，继续查下一页
}
```

### 4.4 第二段：assignFromLastBatch（从最后一个批次兜底）

**触发条件**：合法批次（VALID）全部扣完还不够（如先出后入导致批次尚未建立）。

```java
// 查询最后一个批次（包含 INVALID 批次）
List<StockFinancialBatchDetailBO> financialBatches =
stockFinancialBatchReadService.queryLastFinancialBatchDetail(req);
// 情况A：最后一个批次是"默认批次"（default_flag=YES）
//        → 用异常价格参考：查库存均价/最近入库价
outMoney = calMoneyDefaultZero(outAmount, priceBO.getPrice());
// 价源：SYSTEM_ESTIMATE_WAREHOUSE_AVG(510) 或 LATELY_PUT_STOCK_PRICE(550)
// 情况B：最后一个批次是正常批次但余量不足
//        → 用该批次的 beginAmount/beginMoney 反算单价
outMoney = calculateNewMoneyWithDefault(
detail.getBeginAmount(), detail.getBeginMoney(),
outAmount, BigDecimal.ZERO
);
```

### 4.5 第三段：createAndAssignDefaultBatch（创建默认批次用参考价出）

**触发条件**：连最后一个批次都找不到（仓库从未有过入库记录，但允许负库存）。

```java
// 查询异常价格（优先级链：库存均价 → 最近入库价 → 建议采购价）
Map<Long, StockPriceBO> priceMap = batchGetInvalidBatchPrice(hqId, orgId, goodsIds, bizDate);
// 创建一个"空的"默认财务批次（金额=0，数量=0）
List<StockFinancialBatchBO> batchBOs =
stockFinancialBatchWriteService.initStockFinancialBatch(hqId, initReqs);
// 用参考价算出库金额
outMoney = calMoneyDefaultZero(outAmount, priceBO.getPrice());
// 价源：SYSTEM_ESTIMATE_WAREHOUSE_AVG(510) 等暂估价标记
```

### 4.6 前置特殊路径：使用结算价出库

```java
if (calcStockMoneyUseSettlementMoney) {
// 直接用上游传入的结算金额作为成本，跳过所有批次扣减
Map<String, MoneyAndNoTaxMoneyBO> uniqueId2SettlementMoney =
request.getExtraBizRequest().getUniqueId2SettlementMoney();
createAndAssignDefaultBatchUseSettlementMoney(..., uniqueId2SettlementMoney);
// 价源标记为 USE_SETTLEMENT_PRICE(910)
}
```

这条路径完全绕过财务批次，不查库存成本，直接用业务合同价（结算价）作为出库成本。

### 4.7 完整流程图

```text
valuation(request)
│
├─ 读取计价法：移动加权(AVG) 或 先进先出(FIFO)
├─ 初始化三个 Map：
│    remainAssignAmount   {uniqueId → 待扣量}
│    pair2UniqueIds       {(仓库,批次,物品) → Set<uniqueId>}
│    assignedChangeAM     {uniqueId → 扣减结果容器}
│
├─ [分支A] 结算价开关=ON
│         └─ 直接用 settlementMoney，创建默认批次，打 910 价源
│
└─ [分支B] 结算价开关=OFF（主路径）
│
├─【第一段】assignValidFinancialBatch
│         分页查 VALID 批次，ORDER BY sort_value ASC
│         对每个待出库行：
│           找到匹配批次 → outMoney = batchMoney × (out/batch)
│           批次不足     → 清空该批次，继续下一个
│           打价源：710（实时）或 720（bizDate）
│         全部扣完 → 结束
│
├─【第二段】assignFromLastBatch（仍有剩余量）
│         查最后一个批次（含 INVALID）
│           默认批次  → 用异常参考价 × 量，打 510/550 价源
│           正常批次  → 用 beginMoney/beginAmount 反算均价
│
└─【第三段】createAndAssignDefaultBatch（仍有剩余量）
创建空默认批次
查异常参考价（均价→最近入库→建议采购价）
用参考价 × 量，打 510/550 价源
```

### 4.8 三段触发语义总结

| 阶段 | 触发原因 | 对应业务场景 |
|---|---|---|
| 第一段 | 正常情况 | 库存有货，正常出库 |
| 第二段 | 合法批次余量不足 | 当期补录的历史出库，出库时批次还没建立（先出后入） |
| 第三段 | 连批次档案都没有 | 仓库开启负库存，从未入过货就开始出 |

## 五、库存快照（日结）的意义

### 5.1 为什么需要快照

库存系统的核心结存表（`stock/stock_org`）只存实时当前值，每次出入库操作后被原子更新。这意味着：
- 你只能查"现在有多少货"
- 无法回答"某个历史日期有多少货"

但业务上大量场景需要历史数据：
- **月结对账**需要"本月每天期末库存"
- **成本重算**需要"某个业务日期之前的均价"
- **盘点**需要"盘点日当天的账面库存"
- **财务**需要"上月期末库存金额"

快照（`stock_daily`）就是为了解决这个问题而存在的——把某一天的期末结存固化为一条历史记录。

### 5.2 快照的两个维度

| 维度 | 表 | 粒度 | 用途 |
|---|---|---|---|
| 物品维度 | `stock_daily`（goods） | (仓库, 物品, 日期) | 日常库存查询、月结、成本均价 |
| 批次维度 | `stock_daily`（batch） | (仓库, 物品, 批次, 日期) | 批次效期管理、FEFO 取价 |

### 5.3 快照的两条写入路径

**路径 A：主动生成（createStockDaily）**

触发时机：手动触发日结、Crane 定时任务每天跑、或补录历史数据后修复。

核心算法：

```text
① 读取实时结存（stock / stock_org 当前值）
② 查询"今天的期末" = sumBatchFlowAndCalStockDaily()
→ 从实时结存出发，减去今日的流水变动，得出今日期末
③ 逆推到目标日期 = calcTargetDaily()
→ 今日期末 ± [目标日期到今天] 的流水 = 目标日期期末
④ 保存快照记录
⑤ 幂等保护（防止写快照期间并发出入库）：
写之前记录 stock_change_item.max_id
写完后再查一次，如果 max_id 变了 → 清除刚写的快照 → 重试
```

**路径 B：随结存变更实时更新（updateFromStockChange）**

每次出入库审核后，`saveStockChange()` 完成后同步事务内调用：

```java
// 查询所有 bizDate >= 本次变更业务日期 的已有快照记录
List<StockDailyBO> oldStockDailyBOS = queryDBExistStockDaily(bizDateGET = 变更日期);
// 对每条快照：期末 += 本次变更量
newEndAmount = oldEndAmount + changeBO.getChangeStockAmount();
newEndMoney  = oldEndMoney  + changeBO.getChangeMoney();
// 批量更新
batchUpdateStockDaily(hqId, newStockDailies);
```

> **关键设计**：变更的是业务日期当天及之后所有已存在的快照。因为这笔货的历史记录从业务日期开始就要被影响，否则历史数据就不一致了。

### 5.4 快照的三大用途

**用途1：历史库存查询（StockAmEndReadService）**

```java
// 查询指定日期的库存
batchQueryWarehouseAmBOList(hqId, bizDate, ...)
// → 直接读 stock_daily 中 bizDate 当天的 end_amount / end_money
// → 如果没有快照（从未发生过变更） → 返回 0
```

**用途2：移动加权 BIZ_DATE 模式取价**

出库成本计算时，`AvgStockPriceCalcMethodEnum.BIZ_DATE` 模式下：

```java
// 取单据业务日期当时的库存均价，而非实时均价
getOrgAVGPriceWithDate(hqId, orgId, goodsIds, bizDate)
// → 从 stock_daily 读 bizDate 的 end_amount / end_money
// → 计算均价 = end_money / end_amount
```

这是防止补录历史单据导致成本混乱的关键。

**用途3：月结（成本重算/月度加权均价基础）**

```text
本月加权均价 = (期初金额 + 本月所有入库金额) / (期初数量 + 本月入库数量)
期初数量/金额 = 上月期末快照
```

## 六、防超卖机制

### 五层防护，由外到内

**第1层：在途预占（事前锁量）**

出库之前，通过在途规则在 `stock_occupy_record` 里写入预计出库量：

```text
可用量 = 现存量 - 锁库量 - 在途出库量 + 在途入库量
```

上游订单系统查可用量时，已经扣除了"已在途但未出库"的数量，从源头减少超卖概率。

---
**第2层：应用层负库存校验（validateForPhysicalChangeStockDetail）**

在同一事务内、实际写库存之前，Java 代码做兜底校验：

```java
// 出库后如果 afterAmount - lockAmount < 0 且 不允许负库存 → 抛异常 → 事务回滚
if (!allowNegative && isNegative(afterAmount - lockAmount)) {
throw new BizRuntimeException(ErrorCode.LACK_STOCK, goodsNames);
}
```

---
**第3层：乐观锁版本号（批次表）**

`stock_physical_batch_detail` 和 `stock_financial_batch_detail` 用版本号防并发覆盖：

```sql
UPDATE stock_physical_batch_detail
SET amount = #{newAmount}, version = version + 1
WHERE (id, version) IN (...)
-- affected_rows = 0 → 并发冲突 → 上层感知并重试
```

---
**第4层：原子增量 SQL（结存表）**

`stock` 和 `stock_org` 用数据库行级原子操作，天然防并发：

```sql
-- 不是 "先读后写"，而是直接原子增量
UPDATE stock SET amount = amount + #{delta}, money = money + #{deltaMoney}
WHERE hq_id = #{hqId} AND id IN (...)
ORDER BY id  -- 固定顺序防死锁
```

---
**第5层：业务封结存（Squirrel + Redis 分布式锁）**

- **成本重算期间**：写 Squirrel key 封结存，任何出入库请求进来先检查这个 key，有值则拒绝
- **盘点/多人盘点**：通过 `@DistributedLock` + Redis 分布式锁，整个盘点生命周期内锁住单据号

---

### 快照和防超卖的关联

两者有一处交集：快照写入时的并发保护。

```java
// createStockDaily 内部：
Long beforeMaxId = stockChangeReadService.queryMaxId(queryMaxIdBizRequest);
// ... 生成快照 ...
Long afterMaxId = stockChangeReadService.queryMaxId(queryMaxIdBizRequest);
if (!beforeMaxId.equals(afterMaxId)) {
// 写快照期间有出入库发生 → 快照数据可能不准 → 清除重试
clearDaily(hqId, orgId, dailyDate, totalTargets);
throw new BizRuntimeException(ErrorCode.GEN_STOCK_DAILY_OCCUR_STOCK_CHANGE);
}
```

通过比较 `stock_change_item` 的 `max id`，检测快照计算窗口内是否有并发写，确保快照数据的准确性。

### 防超卖机制总结

| 机制 | 针对场景 | 原理 |
|---|---|---|
| 在途预占 | 高并发订单场景 | 事前占位，减少可用量 |
| 应用层负库存校验 | 正常出库超量 | 事务内 Java 层检查 afterAmount |
| 乐观锁版本号 | 并发修改同一批次 | `WHERE (id,version)` 匹配行数=0 则回滚 |
| 原子增量 SQL | 高并发结存更新 | MySQL 行锁 + `amount + delta` 原子操作 |
| 业务封结存 | 重算/盘点特殊期间 | Redis key + 分布式锁全局阻断 |
| 快照并发保护 | 补录历史单导致快照错误 | max_id 前后对比，写快照期间如有变更则重试 |

## 七、实时库存查询 & 均价重算

### 7.1 查询实时库存的逻辑

**核心判断：今天 vs 历史**

所有库存查询入口（`getStockAmBos`、`listStockAmBos` 等）都有同一个分支：

```java
if (DateUtils.isToday(bizDate.getTime())) {
// 实时路径：直接查 stock 表
stocks = stockDao.getByGoodsIdsConditionWithOptimized(hqId, conditions);
} else {
// 历史路径：查 stock_daily 快照
stocks = getStockFromDaily(hqId, bizDate, queryBOS);
}
// bizDate=null 时默认取 new Date()（今天），走实时路径
```

**实时路径：直查 stock 表**

```text
stock 表（仓库维度）
amount          → 现存量（实时）
money           → 现存无税金额（实时）
money_with_tax  → 现存含税金额（实时）
lock_amount     → 锁库量（实时）
```

可出库量 & 可出库金额是在 Java 层计算，不存库：

```java
// outAbleAmount = amount - lockAmount（来自 stock 表字段）
outAbleAmount = amount.subtract(lockAmount);
// outAbleMoney 等比例换算
outAbleMoney = calculateNewMoney(amount, money, outAbleAmount);
// 即 outAbleMoney = money × (outAbleAmount / amount)
```

在途量（occupy）则单独由调用方叠加，核心结存表本身不存在途：

```java
可用量（业务语义）= outAbleAmount + 在途入 - 在途出
// 在途 = 聚合 stock_occupy_record 的 sum(amount)
```

**历史路径：查快照 + 兜底**

```java
// 先查当前有结存的物品（实时表过滤，避免查不存在的快照）
List<StockAmBO> currentStocks = getExistStockAmBos(hqId, queryBOS);
// 再用历史快照覆盖 amount/money
List<Stock> historyStocks = getStockFromDaily(hqId, bizDate, filteredQueryBOS);
// 覆盖逻辑
if (historyStockAmBO != null) {
stockAmBO.setAmount(historyStockAmBO.getAmount());
stockAmBO.setMoney(historyStockAmBO.getMoney());
} else {
// 查询日期早于第一条快照 → 量和金额返回 0
stockAmBO.setAmount(AMOUNT_ZERO);
stockAmBO.setMoney(MONEY_ZERO);
}
```

> **设计意图**：以实时表的结构为基础（判断该物品是否存在），用快照数据覆盖历史时刻的量和金额。不存在快照的日期，说明那时候还没有库存，返回 0。

---

### 7.2 补录历史日期库存时，均价如何保持正确

系统采用"**异步自动成本重算**"机制来保证均价一致性，而不是实时修正。

**问题的本质**

假设当前日期是 5月28日，现在在5月3日补录一笔入库 20个 @ 8元：

```text
原来：
5月1日  采购入库 100个 @ 10元 → 均价 = 10元
5月5日  出库 50个  @ 10元     → 均价 = 10元
5月10日 采购入库 50个 @ 12元  → 均价 = (500+600)/150 = 11元
补录影响：
5月3日均价应变为 (1000+160)/120 = 9.67元
5月5日出库的成本应改为 9.67×50 = 483.5元（原来是500元）
后续每一天的均价都要级联重算...
```

**触发机制：DTS → CostRecalHandler**

每次结存变更（包括补录）都会写入 `stock_change_item` 表，DTS 监听这张表的变更，投递到 `CostRecalHandler`。

`CostRecalHandler.recvMessage()` 做三个关键判断：

```java
if (isMoneyOrAmountChanged(details)              // ① 有实际数量/金额变化
&& isBeforeCurrentTime(bizDate)              // ② 业务日期 < 今天（是历史补录）
&& isBeforeNewestBizDate(stockChangeItem)) { // ③ 有比它更晚的已审核单据（才有级联影响）
sendAutoCostRecalMessage(hqId, orgId, stockChangeItem);
}
```

同时排除以下不需要重算的场景：
- 重算本身产生的变更（防无限循环）
- 全盘生成的调整入库单

**延迟合并机制**

发出的 `AutoCostRecalMessage` 包含：

```json
{
"hqId": 12345,
"orgId": 67890,
"fromDate": 1746288000000
}
```

消费端不是立即执行重算，而是注册一个延迟任务，延迟时间由 Lion 参数 `AUTO_COST_RECAL_SCOPE` 配置（两种模式）：
- **模式1**：固定 N 分钟后执行
- **模式2**：固定每天某时刻执行

关键：**任务合并**。如果同一个机构在延迟期间又来了一条补录，系统不会创建新任务，而是合并到已有任务中，把 `fromDate` 取更早的那个：

```java
// 已有任务 fromDate = 5月7日，新补录 fromDate = 5月3日 → 更新 fromDate = 5月3日
costRecalTaskContext.setFromDate(
bizDate.before(costRecalTaskContext.getFromDate()) ? bizDate : costRecalTaskContext.getFromDate()
);
```

这样多笔补录只跑一次重算，从最早的补录日期开始。

**重算执行：从补录日期一路重算到今天**

任务被唤醒后，`CostReCalService` 从 `fromDate` 到 `toDate` 对该机构的所有单据按正确顺序重新执行一遍计价：

```text
① COPY 阶段：把待重算范围内的数据复制到"回放表"
② ARRANGE 阶段：按 bizDate + 单据类型优先级排序
③ 逐单重算：
- 重新走 StockValuationStrategy（207或其他）
- 重新算出正确的 stock_money
- 用 AbstractStockInOutCostUpdateService.batchUpdateStockInOutCost 回写
④ 更新结存表：stock.money 和 stock.amount 同步修正
⑤ 触发快照修复：updateFromStockChange 更新所有受影响日期的快照
```

> 由于 `stock.money` 在重算后被修正，实时查询均价（`calPriceDefaultZero(hqId, amount, money)`）会自动反映新值。不需要额外操作，因为均价本来就不持久化，每次都是 `money / amount` 现算。

**完整流程图**

```text
补录5月3日入库单 → 审核 → changeStock() 写 stock_change_item
│
↓ DTS 监听
CostRecalHandler.recvMessage()
│
三个条件都满足？
│ YES
↓
sendAutoCostRecalMessage(fromDate=5月3日)
│
↓ Mafka 消费
注册延迟重算任务（N分钟后 / 每天某时刻）
│
期间有其他补录？
YES → 合并 fromDate（取最早）
│
↓ 任务到时执行
CostReCalService.doReCalFromDate(5月3日 → 今天)
│
① 对5月3日之后所有单据重新计价
② 回写 stock_in/out_item_detail.stock_money
③ 更新 stock.money（实时均价随之修正）
④ 更新 stock_daily（历史快照随之修正）
```

**关键取舍**

| 取舍 | 选择 | 理由 |
|---|---|---|
| 实时重算 vs 延迟重算 | 延迟 | 多笔补录合并成一次重算，避免频繁全量重算 |
| 补录期间均价是否准确 | 不准确（重算完成前是暂估价） | 补录后到重算完成前存在窗口期，业务接受暂时不准确 |
