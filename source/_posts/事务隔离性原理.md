# 事务隔离性的原理

隔离性（Isolation）是 ACID 中的 **I**，核心问题是：**多个事务同时读写同一数据时，如何让它们互不干扰？**

## 一、并发写 — 必须串行化

两个事务**不能同时写同一行**，否则数据会损坏。这是通过 **锁** 来保证的。

### 行级锁（Row Lock）

```
事务 T1: UPDATE account SET balance = balance - 100 WHERE id = 1;
         ↓ 对 id=1 这行加 X 锁（排他锁）

事务 T2: UPDATE account SET balance = balance - 50  WHERE id = 1;
         ↓ 也要对 id=1 加 X 锁 → 阻塞等待 T1 释放

T1 提交 → 释放 X 锁 → T2 获得锁 → 继续执行
```

**关键**：写锁在事务提交后才释放（两阶段锁协议），这是隔离性的基础保证。

## 二、并发的核心矛盾：写 vs 读

| 场景 | 冲突程度 | 需要什么 |
|------|---------|---------|
| 写 vs 写 | 必须互斥 | 锁（上面讲了） |
| 写 vs 读 | **不必互斥，但需要协调** | 多版本并发控制（MVCC） |

## 三、MVCC — 现代数据库的核心机制

MVCC（Multi-Version Concurrency Control）是解决"读不阻塞写、写不阻塞读"的关键。

**核心思想**：不直接覆盖数据，而是**保留多个版本**。

### 工作方式

```
表的每一行在 InnoDB 中实际存储：
┌──────────┬──────────┬──────────┬─────────────┬─────────────┐
│   id     │ balance  │ trx_id   │ roll_ptr    │ db_row_id   │
├──────────┼──────────┼──────────┼─────────────┼─────────────┤
│   1      │   100    │  trx_99  │ → Undo Log  │ (主键)      │
└──────────┴──────────┴──────────┴─────────────┴─────────────┘

trx_id: 最后一次修改此行的事务 ID
roll_ptr: 指向 Undo Log 中旧版本的指针（版本链）
```

### 一个完整的并发例子

```
初始状态: A 余额 = 1000 (trx_id=50)

T1 开始 (trx_id=101)，读 A:
  → 看到 trx_id=50 ≤ 101，且 T1 启动时 50 已提交
  → 读到 1000 ✓

T2 开始 (trx_id=102)，UPDATE A = A - 100:
  → 创建新版本: A=900 (trx_id=102)
  → Undo Log 记录: 旧值 1000 

T1 再次读 A (可重复读级别):
  → 看到 trx_id=102 > 101（比自己新，且 T2 可能未提交）
  → 沿 roll_ptr 追溯 Undo Log 版本链
  → 找到 trx_id=50 的版本 → 读到 1000 ✓ (快照一致)
```

### 版本链追溯

```
当前行 → roll_ptr → Undo Log[trx_102, balance=900] → Undo Log[trx_50, balance=1000]
                        ↑ 新版本（T2 改的）              ↑ 旧版本（T1 的快照）
                        
T1 的快照时间点在这两个版本之间 → 读到 1000
```

## 四、ReadView — 版本可见性判断

每个事务在首次读取时生成一个 **ReadView**（读视图），包含三个关键信息：

| 字段 | 含义 |
|------|------|
| `m_ids` | 当前活跃（未提交）的事务 ID 集合 |
| `min_trx_id` | m_ids 中的最小值 |
| `max_trx_id` | 下一个要分配的事务 ID |

**判定规则**：

```
trx_id < min_trx_id  → ✅ 可见（已提交的旧版本）
trx_id > max_trx_id  → ❌ 不可见（未来的版本）
trx_id ∈ m_ids       → ❌ 不可见（活跃事务还没提交）
trx_id ∈ [min_trx_id, max_trx_id] 且不在 m_ids 中 → ✅ 可见（已提交）
```

## 五、隔离级别的实现差异

SQL 标准定义了四种隔离级别，它们在实现上有本质区别：

| 隔离级别 | ReadView 生成 | 解决的问题 | 实现要点 |
|---------|--------------|-----------|---------|
| **读未提交** (RU) | 不用 ReadView | 几乎无 | 直接读当前最新值，不管是否提交 |
| **读已提交** (RC) | **每次 SELECT 都生成新 ReadView** | 脏读 | 每次查询看到最新已提交快照 |
| **可重复读** (RR) | **事务开始时生成，整个事务用同一个** | 脏读 + 不可重复读 | 间隙锁防止幻读（InnoDB 独有） |
| **串行化** (S) | 全部串行执行 | 全部 | 读加共享锁，写加排他锁，彻底串行 |

### 一个例子说明 RC vs RR

```
T1: SELECT balance FROM account WHERE id=1;  -- 第1次读
T2: UPDATE account SET balance=900 WHERE id=1; COMMIT;
T1: SELECT balance FROM account WHERE id=1;  -- 第2次读

RC 下: 第1次=1000, 第2次=900  ← 两次看到不同值，但都是干净的
RR 下: 第1次=1000, 第2次=1000  ← 同一个 ReadView，看到一致的快照
```

## 六、锁 + MVCC 的协作

InnoDB 做 `SELECT ... FOR UPDATE` 或 `UPDATE` 时：

```
1. 获取目标行的 X 锁（写锁）        ← 锁机制阻止并发写
2. 不看 Undo Log，读当前最新版本     ← 当前读（Current Read）
3. 修改数据，写 Undo Log             ← MVCC 保留旧版本给其他读事务
4. 提交释放锁                        ← 锁释放
```

而普通 `SELECT`：

```
1. 不加锁                            ← 不阻塞任何人
2. 通过 ReadView 判断版本可见性       ← 快照读（Snapshot Read）
3. 沿 Undo Log 追溯旧版本            ← MVCC 保证一致性
```

## 七、幻读与间隙锁（InnoDB 的额外创新）

标准 SQL 的 RR 级别无法防止**幻读**（范围查询中，其他事务插入新行导致结果集变化）。InnoDB 在 RR 级别通过**间隙锁（Gap Lock）**额外解决了这个问题：

```
T1: SELECT * FROM account WHERE id BETWEEN 1 AND 10 FOR UPDATE;
    → 对 id=1,2,...,10 加行锁
    → 对 (1,2), (2,3), ..., (9,10) 这些间隙加 Gap Lock

T2: INSERT INTO account VALUES (5, ...);  → 被间隙锁阻塞！
T2: INSERT INTO account VALUES (11, ...); → 可以，不在间隙范围内
```

## 八、总结 · 核心原理链条

**隔离性是通过三层机制协作实现的**：

| 层 | 机制 | 解决什么问题 |
|---|------|------------|
| **锁（Lock）** | 行级排他锁、间隙锁、意向锁 | 并发写互斥、幻读 |
| **MVCC** | Undo Log 版本链 + ReadView | 读不阻塞写、快照一致性 |
| **隔离级别** | ReadView 生成策略不同 | 脏读、不可重复读、幻读 |

**一句话总结**：锁保证写着之间不打架；MVCC 通过保留历史版本 + ReadView 判定可见性，保证读者看到一致的数据快照而不阻塞写者；隔离级别的区别本质上就是"ReadView 什么时候创建"以及"要不要加间隙锁"这两个策略的差异。
