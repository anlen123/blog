2. 分析 SQL — EXPLAIN

关键字段解读

字段 含义 关注点
id 执行顺序 数字越大越先执行
select_type 查询类型 SIMPLE / PRIMARY / SUBQUERY / DERIVED / UNION
type 访问类型（从优到差） system > const > eq_ref > ref > range > index > ALL
possible_keys 可能使用的索引 候选索引
key 实际使用的索引 NULL = 没走索引
key_len 使用索引的长度 判断联合索引用了几列

Extra 关键信息

值 含义
Using index ✅ 覆盖索引，无需回表
Using index condition ✅ 使用了索引下推（ICP）
Using where MySQL 服务器层过滤

3. 索引优化（最高优先级，收益最大）

3.1 索引类型

索引类型 特点 适用场景
B+Tree（默认） 有序，支持范围查询、排序、分组 大部分场景
Hash 等值查询极快，不支持范围 Memory 引擎、等值查询
Full-Text 全文搜索 文本内容搜索

3.2 最左前缀原则（高频考点）

联合索引 (a, b, c) 的生效情况：

WHERE 条件 是否走索引 说明
a=1 ✅ 使用 a
a=1 AND b=2 ✅ 使用 a,b
a=1 AND b=2 AND c=3 ✅ 使用全部
a=1 AND c=3 ✅ a 生效，c 不生效 只用到 a
b=2 ❌ 跳过 a，不满足最左前缀
c=3 ❌ 跳过 a,b，不满足最左前缀
a=1 AND b>2 AND c=3 a,b 生效，c 不生效 范围查询中断后续列匹配

核心结论：从最左列开始匹配，遇到范围查询（>、<、between、like）则中断。

3.4 覆盖索引

查询的所有列都在索引中，不需要回表，EXPLAIN Extra 显示 Using index。

3.5 索引下推（ICP — Index Condition Pushdown）

MySQL 5.6+ 特性。将 WHERE 中能由索引处理的部分下推到存储引擎层过滤，减少回表次数。

3.6 索引设计原则

  • 区分度高的列优先（如 user_id，而非 gender）
  • WHERE / JOIN / ORDER BY / GROUP BY 列建索引
  • 避免过多索引（影响写入性能）
  • 尽量使用短索引（前缀索引）
  • 更新频繁的列慎重建索引

4. SQL 语句优化

更多 SQL 优化技巧

  • 批量插入 优于逐条插入
  • EXISTS vs IN：外表大用 EXISTS，外表小用 IN
  • 小表驱动大表（JOIN 时用小表作为驱动表）
  • JOIN 字段建索引，避免超过 3 个表的 JOIN
  • 避免在循环中执行 SQL，改用批量操作

5. 表结构 / Schema 优化

5.1 字段类型选择

原则 说明
尽可能小 年龄用 TINYINT 不用 INT
尽可能简单 优先用内建类型而非字符串
避免 NULL 尽量 NOT NULL + 默认值（NULL 使索引统计更复杂）
定长类型更快 CHAR 比 VARCHAR 快（当长度固定时）

  • 第三范式（3NF）：减少数据冗余，但查询需多次 JOIN
  • 反范式化：适当冗余，减少 JOIN，以空间换时间
  • 实际场景：混合使用，读多写少的表适当反范式化

5.4 分库分表

  • 垂直拆分：按业务模块拆库 / 按列拆表（冷热数据分离）
  • 水平拆分：按行拆分（user_id 取模 / 按时间范围）

6.2 InnoDB vs MyISAM（经典面试题）

对比项 InnoDB MyISAM
事务 ✅ 支持 ❌ 不支持
行级锁 ✅ ❌ 只有表级锁

6.3 InnoDB 关键特性

B+Tree 索引结构

  • 聚簇索引：主键索引的叶子节点存储完整数据行
  • 二级索引：叶子节点只存索引列 + 主键值，需要回表
  • 页大小默认 16KB
  • 非叶子节点只存索引不存数据 → 单页能存更多键 → 树更矮 → IO 更少
  • 叶子节点形成有序双向链表 → 天生支持范围查询和排序

核心组件

组件 作用
Buffer Pool 缓存数据页和索引页，建议设为物理内存 50%~80%，LRU 淘汰
Change Buffer 缓存二级索引修改，减少磁盘 IO，适合写多读少
Doublewrite Buffer 防止页损坏，保证数据可靠性
Redo Log 物理日志，崩溃恢复，保证持久性（WAL 机制）
Undo Log 逻辑日志，事务回滚 + MVCC 版本链

7. 事务与锁

7.1 事务 ACID

特性 含义 实现机制
原子性 (Atomicity) 要么全做，要么全不做 Undo Log
一致性 (Consistency) 事务前后数据满足约束 其他三者共同保证
隔离性 (Isolation) 并发事务互不干扰 锁 + MVCC
持久性 (Durability) 提交后永久保存 Redo Log

7.2 隔离级别

级别 脏读 不可重复读 幻读 实现机制
READ UNCOMMITTED ✅ ✅ ✅ 几乎不用
READ COMMITTED ❌ ✅ ✅ 每次查询生成新 ReadView
REPEATABLE READ（默认） ❌ ❌ ✅（部分解决） 事务开始时生成 ReadView
SERIALIZABLE ❌ ❌ ❌ 所有读加共享锁

7.3 MVCC（多版本并发控制）

核心概念：

  • 隐藏列：DB_TRX_ID（事务ID）、DB_ROLL_PTR（回滚指针）、DB_ROW_ID
  • ReadView：判断版本可见性的快照
  • Undo Log：维护历史版本链
隔离级别 ReadView 创建时机
RR（可重复读） 事务开始时创建，整个事务用同一个
RC（读已提交） 每次查询都重新创建

7.4 锁机制

按粒度：

锁类型 说明
表锁 (Table Lock) 锁整张表
行锁 (Record Lock) 锁单行记录
间隙锁 (Gap Lock) 锁索引间隙，RR 级别下防幻读
临键锁 (Next-Key Lock) = Record Lock + Gap Lock

按模式：

  • 共享锁（S Lock）：SELECT ... LOCK IN SHARE MODE
  • 排他锁（X Lock）：SELECT ... FOR UPDATE

死锁：

  • 原因：多个事务相互等待对方释放锁
  • 解决：InnoDB 自动检测并回滚一个事务；应用层应减少事务时间，按相同顺序访问资源

12. 常见面试题速答

Q1: 为什么用 B+Tree 不用 B-Tree 或 Hash？

B+Tree 非叶子节点只存索引不存数据 → 单页存更多键 → 树更矮 → IO 更少；叶子节点形成有序双向链表 → 天生支持范围查询和排序。Hash 不支持范围查询且存在哈希冲突。

Q2: 什么情况下索引会失效？

函数操作、隐式类型转换、左模糊 LIKE、联合索引不满足最左前缀、OR 条件不全有索引、优化器认为全表扫描更快。

Q3: 如何优化深分页？

游标分页（WHERE id > last_id LIMIT N）或延迟关联（子查询只取主键 ID 走覆盖索引，再 JOIN 回表取全量数据）。

Q4: MySQL 隐式类型转换规则？

字符串和数字比较时，字符串转数字。若字符串列（如 phone varchar）和数字比较，会把 phone 值转数字 → 索引失效。

Q5: 怎么查看是否走了索引？

EXPLAIN SELECT ...，看 key 是否为 NULL，看 type 是否为 ALL。

Q6: count(*) vs count(1) vs count(col) 的区别？

count(*) = count(1)：统计所有行（含 NULL）。count(col)：统计该列不为 NULL 的行。InnoDB 下 count(*) 会选最小的二级索引统计；MyISAM 下 count(*) 是 O(1)。

Q7: 联合索引 (a,b,c)，WHERE a=1 AND c=3 走索引吗？

a 走索引，c 不走。因为跳过了 b，不满足最左前缀的连续匹配。key_len 可以验证只用了 a 列的长度。

Q8: InnoDB RR 级别下如何解决幻读？

通过 Next-Key Lock（行锁 + 间隙锁）锁定记录之间的间隙，防止其他事务插入新数据。但 MVCC 的快照读仍可能看到幻行，需要 SELECT ... FOR UPDATE 当前读来彻底避免。

优化优先级总结

优先级 手段 说明
1️⃣ 索引优化 收益最大，首先做
2️⃣ SQL 语句改写 消除全表扫描、回表
3️⃣ 表结构设计 字段类型、分区
4️⃣ 配置参数调整 Buffer Pool 等
5️⃣ 架构升级 读写分离、分库分表（成本最高）

💡 黄金法则：先用 EXPLAIN 找出慢的原因，再针对性优化，而不是盲目加索引或改配置。

✅ 优点 ⚠️ 缺点

附录B：EXPLAIN filtered 字段详解

基本含义

filtered 是一个百分比（0~100），表示 WHERE 条件过滤后预计保留的行数占 rows 的百分比。

示例

  • rows=1000：索引扫描预估 1000 行（user_id=100 的记录）
  • filtered=10.00：经过 status=1 过滤后，预计只保留 100 行
  • 浪费了 900 次 IO

filtered 值高低的含义

filtered 值 含义
100% WHERE 条件全部由索引完成，最理想 ✅
~50% 索引扫描的行有一半被过滤，还算 OK
< 10% 大部分被 WHERE 丢弃，效率低 ⚠️
接近 0% 严重浪费，需要优化 ❌

优化示例

filtered 在 JOIN 中更关键

  • 驱动表 filtered 越低 → JOIN 次数越多 → 性能越差
  • MySQL 优化器根据 rows × (filtered/100) 选择驱动表

注意事项

  • filtered 是估算值，依赖统计信息，数据分布极不均匀时可能不准
  • 大量增删改后需更新统计信息：ANALYZE TABLE orders;
  • 优化目标：让 rows × (filtered/100) 尽可能小

总结

MySQL 优化的核心思路：SQL 语句 → 索引 → 表结构 → 配置参数 → 架构设计，逐层递进，成本依次升高。

  • 🔥 最核心能力：会看 EXPLAIN，会判断索引是否生效
  • 📝 最高频考点：最左前缀原则、索引失效场景、B+Tree 原理、MVCC、事务隔离级别
  • 🛠️ 最有价值实战：慢查询排查流程、深分页优化、覆盖索引设计

建议把 EXPLAIN 的 type 等级和 Extra 关键值烂熟于心，这是面试中最容易拉开差距的知识点。
