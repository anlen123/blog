限流设计与实现

发表于2024-03-05|更新于2026-07-01|架构
|浏览量:

一般开发开放平台做限流，本质上是在“流量控制 + 公平分配 + 资源保护 + 商业配额”之间找平衡。
如果是开放给第三方调用的 API 平台，通常不会只做一个“每秒几次”的简单限流，而是会做一套分层、分维度、可配置、可观测的限流体系。

一、先说结论：开放平台限流一般怎么做

通常会按下面这套思路落地：

  1. 限流维度设计
  • 按 appKey / clientId
  • 按 租户 / 商户 / 企业
  • 按 用户
  • 按 IP
  • 按 API接口
  • 按 环境（测试、生产）
  • 按 资源类型（读接口、写接口、回调接口）
  1. 限流指标设计
  • QPS：每秒多少次
  • QPM / QPH：每分钟/每小时多少次
  • Daily Quota：每日调用总量
  • Concurrency：并发请求数
  • Bandwidth / Payload：流量或包体大小限制
  1. 分层限流
  • 网关层限流
  • 应用层限流
  • 下游资源层限流（DB、缓存、第三方依赖）
  • 特殊接口单独限流
  1. 算法选择
  • 工程里最常见：令牌桶
  • 精确统计常见：滑动窗口
  • 削峰更明显：漏桶
  • 简单粗暴但误差大：固定窗口
  1. 技术实现
  • 单机：本地内存计数器
  • 分布式：Redis + Lua 原子限流
  • 更大规模：网关/服务网格/专用限流组件
  1. 超限后的处理
  • 返回 429 Too Many Requests
  • 降级返回缓存/默认值
  • 关键客户保底，普通客户排队或拒绝
  • 响应头返回剩余额度、重试时间

二、开放平台为什么要做“多层限流”

开放平台和普通内部系统不一样，原因主要有 4 个：

1. 保护核心服务

第三方接入后，调用行为不可控。
如果不做限流，一个客户端 bug、脚本轮询、重试风暴，就可能把你的核心接口打穿。

2. 保障公平性

不能让一个大客户把所有流量吃光。
所以通常要做：

  • 平台总限流
  • 租户级限流
  • 应用级限流
  • 接口级限流

3. 配合商业策略

开放平台往往有套餐：

  • 免费版：10 QPS，每日 1 万次
  • 标准版：50 QPS，每日 50 万次
  • 企业版：200 QPS，支持突发流量

所以限流不只是技术问题，也是一种产品能力/计费能力。

4. 防止异常和攻击

虽然不是纯安全系统，但限流天然有安全属性：

  • 防刷
  • 防接口遍历
  • 防暴力重试
  • 防恶意回调

三、一般会从哪些维度限流

这是最核心的设计点。

1. 按 appKey / clientId 限流

最常见。
适合开放平台，因为接入方通常都有自己的身份标识。

例如：

  • appA：100 QPS
  • appB：20 QPS

这是最基础的一层。

2. 按 API 接口限流

不同接口价值和成本不同，不能一个规则打天下。

例如：

  • /order/query：100 QPS
  • /order/create：20 QPS
  • /settlement/export：2 QPS

因为：

  • 查询类通常便宜
  • 写操作通常更贵
  • 导出类最重，必须严控

3. 按租户 / 商户 / 企业限流

有些平台一个企业下面会有多个 appKey。
如果只按 appKey 限流，用户可以开很多应用绕过限制。

所以经常要加一层：

  • 企业总额度：500 QPS
  • 每个 appKey 子额度：100 QPS

这样才不会被“拆账号”绕过。

4. 按用户 / 账号限流

适用于用户态接口，比如：

  • 登录
  • 发验证码
  • 查询个人数据
  • 发起审批

例如：

  • 同一用户 1 分钟最多发 5 次验证码
  • 同一用户 1 秒最多请求 10 次资料接口

5. 按 IP 限流

一般用于兜底和防攻击，不建议只靠 IP，因为 NAT 下很多人可能共用一个出口 IP。

典型做法：

  • appKey 是主维度
  • IP 作为异常风控辅助维度

比如：

  • 同一 appKey 下某个 IP 突然激增，额外打压

6. 按并发数限流

很多平台只管 QPS，不管并发，这是不够的。
如果一个请求很慢，高并发也会把线程池、连接池打满。

所以常见再加：

  • 每个 appKey 最多并发 50
  • 某个重接口最多并发 5

这类限流特别适合：

  • 导出
  • 上传
  • 回调
  • 复杂查询

7. 按日配额/月配额限流

这是开放平台很典型的商业规则。

比如：

  • 免费版每天 1000 次
  • 企业版每月 100 万次

这种一般不走毫秒级限流，而是走配额系统：

  • 调用前校验剩余额度
  • 调用后扣减
  • 到账期自动刷新

四、常见限流算法怎么选

1. 固定窗口

比如“每分钟最多 100 次”。

优点

  • 简单
  • 实现成本低

缺点

  • 窗口边界会突刺
    例如 00:59 打 100 次，01:00 又打 100 次，瞬时可能 200 次

适合

  • 简单后台管理接口
  • 不要求很精确的场景

2. 滑动窗口

统计最近 60 秒内的请求数，而不是按自然分钟切分。

优点

  • 比固定窗口更平滑
  • 更公平

缺点

  • 实现和存储成本更高

适合

  • 对精度要求高的开放 API

3. 漏桶

请求先进入桶，按固定速率流出。

优点

  • 输出速率平滑
  • 削峰明显

缺点

  • 突发能力差
  • 用户体验可能不如令牌桶

适合

  • 下游特别脆弱、要求稳定出流的场景

4. 令牌桶

系统按固定速率生成令牌，请求拿到令牌才能通过。

优点

  • 同时支持平均速率控制 + 短时突发
  • 工程上最实用

缺点

  • 需要合理设置桶容量和发放速率

适合

  • 大多数开放平台 API

一般建议

如果你问“开放平台一般怎么做”，答案通常是：

网关层主用令牌桶，配额层补充日/月额度，重点接口再加并发限制。

五、一般架构上怎么落

开放平台通常不是只在代码里 if count > n，而是分层处理。

1. 网关层限流

这是第一道防线，最常见。

常放在：

  • Nginx/OpenResty
  • Kong/APISIX
  • Spring Cloud Gateway
  • Envoy/Istio
  • 公司内部 API Gateway

网关层适合做

  • appKey 级限流
  • IP 级限流
  • API 路径级限流
  • 黑白名单
  • 统一 429 返回

好处

  • 拦截早，保护后端
  • 规则统一管理
  • 不用每个服务重复造轮子

2. 应用层限流

网关挡不住所有问题，应用层还要有第二道。

应用层适合做

  • 某个业务接口自己的特殊规则
  • 某个用户/订单/资源维度的细粒度限制
  • 下游依赖保护
  • 并发隔离

例如：

  • 某商户每天最多导出 3 次
  • 某订单号 10 秒内只允许重复提交 1 次

这些通常只有业务服务自己最清楚。

3. 下游资源层限流

有些平台 API 背后是贵资源：

  • 数据库
  • 搜索引擎
  • 第三方供应商接口
  • 消息发送能力

所以还会做：

  • DB 连接池限流
  • 某类 SQL 并发限制
  • 第三方接口调用预算控制

不然即使入口没超限，也可能把后面打挂。

六、分布式系统里一般怎么实现

方案 1：本地内存限流

比如 Guava RateLimiter、Sentinel 单机规则。

优点

  • 快
  • 简单

缺点

  • 多实例不准
  • 横向扩容后总量失真

适合

  • 单机服务
  • 辅助保护
  • 本地兜底

方案 2：Redis + Lua

这是很常见的分布式方案。

做法

  • 用 Redis 存计数器/令牌状态
  • 用 Lua 保证原子扣减
  • key 设计成：rate_limit:{appKey}:{api}:{window}

优点

  • 分布式一致性较好
  • 性能高
  • 规则灵活

缺点

  • Redis 成为关键依赖
  • 热 key 要处理

很多平台实际上就是这个方案

方案 3：网关自带限流能力

比如：

  • Kong rate limiting
  • APISIX limit-req / limit-count
  • Envoy local/global rate limit

优点

  • 成熟稳定
  • 易统一治理

缺点

  • 复杂业务规则不一定够灵活

适合

  • 通用开放平台入口

方案 4：本地预热 + 中央配额

高性能场景里常见。

思路类似：

  • 中央配额系统统一下发额度
  • 每个节点本地缓存一部分令牌
  • 本地快速放行
  • 用完再续租

这样能减少每次都打 Redis 的开销。

七、规则一般怎么设计才合理

1. 分级规则，而不是单一规则

例如：

  • 平台总入口：10000 QPS
  • 每个租户：500 QPS
  • 每个 appKey：100 QPS
  • /create 接口：20 QPS
  • /export 接口：2 并发

这样叫层级限流。

2. 区分读写接口

常见原则：

  • 读接口：额度高一些
  • 写接口：额度低一些
  • 幂等写接口：可适当放宽
  • 非幂等核心写：严格限制

3. 支持突发流量

第三方系统经常是批量任务、整点任务、定时补偿。
如果只限制平均速率，用户体验会很差。

所以一般会设：

  • 平均速率：50 QPS
  • 桶容量：100 或 200

让它有有限突发能力。

4. 给重点客户保底

实际业务里经常有：

  • 普通客户
  • VIP 客户
  • 战略客户

同样一个接口，额度可能不同。
这也是为什么规则配置中心很重要。

八、超限之后怎么返回

这部分很容易被忽略，但对接入方体验很关键。

最基础

返回 HTTP 429 Too Many Requests

同时建议返回：

  • 错误码
  • 错误信息
  • 建议重试时间

例如：

更规范一点

响应头里加：

  • X-RateLimit-Limit
  • X-RateLimit-Remaining
  • X-RateLimit-Reset
  • Retry-After

这样第三方更容易做自适应退避。

更成熟的做法

按业务区分处理：

  • 普通查询接口：直接 429
  • 非核心接口：返回缓存数据
  • 回调接口：接受请求但异步排队
  • 导出接口：提示稍后重试或转异步任务

九、开放平台限流通常还会配哪些能力

1. 配置中心

限流规则一定要可动态调整，不能写死在代码里。

通常会配置：

  • 限流对象
  • 接口
  • 阈值
  • 时间窗口
  • 是否启用
  • 白名单
  • 灰度范围
  • 生效环境

2. 监控告警

至少监控这些指标：

  • 总请求数
  • 放行数
  • 限流数
  • 限流比例
  • 各 appKey 限流 TopN
  • 各 API 限流 TopN
  • Redis 限流耗时/失败率

3. 审计与运营能力

开放平台经常会遇到客户问：

  • 为什么我今天被限了？
  • 我还剩多少额度？
  • 能不能临时扩容？

所以通常还会有：

  • 配额查询页
  • 调用报表
  • 超限日志
  • 临时提额能力
  • 套餐变更后自动生效

4. 白名单与豁免

比如：

  • 内部回归测试环境不限制
  • 特定合作方临时放开
  • 紧急故障期间旁路部分限流

但要慎用，白名单很容易失控。

十、一个比较典型的落地方案

如果你让我给“普通开放平台”设计一版，通常会这样做：

第一层：网关限流

维度：

  • appKey + API
  • IP 兜底

规则：

  • 默认每 appKey 每 API 50 QPS
  • 写接口 10 QPS
  • 导出类接口 2 QPS
  • IP 超阈值额外拦截

算法：

  • 令牌桶

实现：

  • 网关插件 + Redis/Lua

第二层：业务限流

维度：

  • 租户
  • 用户
  • 资源ID
  • 并发数

规则：

  • 单租户总并发 100
  • 单用户提交类操作 1 秒最多 3 次
  • 单订单 10 秒内只允许一次非幂等提交

实现：

  • 应用服务内存 + Redis 组合

第三层：配额系统

规则：

  • 免费版：每天 1 万次
  • 标准版：每天 10 万次
  • 企业版：每天 100 万次

实现：

  • 配额中心
  • 调用计量
  • 账期刷新
  • 运营控制台可提额

第四层：资源保护

规则：

  • 某重 SQL 接口并发 <= 5
  • 某第三方依赖调用速率 <= 20 QPS
  • 异步任务队列长度超阈值时拒绝新增任务

十一、几个实战建议

1. 不要只按 IP 限流

开放平台更应该按 appKey/tenant/API 为主，IP 只是辅助。

2. 不要只做网关层

很多业务规则只有应用层知道，网关只能挡住通用流量。

3. 不要只做 QPS

并发限制、日配额、异步削峰同样重要。

4. 限流要和幂等、重试策略一起设计

否则接入方被 429 后疯狂重试，反而更糟。
建议文档里明确：

  • 重试退避策略
  • 最大重试次数
  • 幂等 key 规范

5. 预留“临时提额”能力

大促、活动、客户上线前联调，经常需要临时扩容。

6. 要区分“保护系统”和“伤害客户体验”

限流不是越严格越好，目标是：

  • 系统不被打垮
  • 客户能预期行为
  • 商业规则能执行

十二、如果是 Java / Spring 体系，常见实现方式

如果你是 Java 开放平台，常见组合是：

  • 网关层：Spring Cloud Gateway / APISIX / Kong
  • 服务层：Sentinel / Resilience4j / 自研 AOP 限流
  • 分布式计数：Redis + Lua
  • 配置中心：Apollo / Nacos / ZooKeeper / 自研配置平台
  • 监控：Prometheus + Grafana / 公司监控平台
  • 运营能力：后台控制台管理配额、白名单、提额

十三、最简化的一句话架构

可以把它理解成：

网关做通用限流，服务做业务限流，配额中心做套餐控制，监控系统做可观测，运营后台做动态调参。

总结

一般开发开放平台做限流，不是单点限制 QPS，而是做一套分层、分维度、可配置的体系：

  • 维度：appKey、租户、用户、IP、API、并发、日配额
  • 层次：网关层 + 应用层 + 下游资源层
  • 算法：通常优先令牌桶，必要时配滑动窗口/并发控制
  • 实现：常见是网关 + Redis/Lua + 配额中心 + 监控告警
  • 目标：既保护系统，又保证公平，还能承载商业套餐和客户运营

这张图的核心思想

1. 网关做第一层

负责：

  • appKey 级限流
  • API 级限流
  • IP 级兜底
  • 统一返回 429

这是最前置保护。

2. 规则中心做动态配置

负责存：

  • 哪个客户多少 QPS
  • 哪个 API 什么限制
  • 哪个环境是否启用
  • 是否临时提额
  • 是否白名单

这是治理能力。

3. 配额中心做总量控制

负责：

  • 每天最多多少次
  • 每月最多多少次
  • 套餐额度
  • 剩余额度查询

这是商业能力。

4. 应用层做业务级保护

负责：

  • 同一用户重复提交限制
  • 同一订单防重
  • 导出接口并发限制
  • 某资源操作频率限制

这是业务精细控制。

5. 资源层做真正的兜底保护

负责：

  • DB 连接池不被打爆
  • 下游第三方额度不被刷光
  • 异步任务堆积时主动拒绝

这是防系统雪崩。

二、Redis + Lua 限流设计示例

这是最常见的工程方案之一。

1. 为什么要 Redis + Lua

因为分布式环境下：

  • 服务有多个实例
  • 请求会打到不同节点
  • 本地内存计数不准

所以需要一个共享状态存储。
Redis 适合做这个事情，而 Lua 可以保证：

  • 读取当前计数
  • 判断是否超限
  • 增加计数
  • 设置过期时间

这些操作原子执行。

2. 最基础的固定窗口限流设计

key 设计

比如对 appKey + API + 秒级窗口 限流：

rate_limit:{appKey}:{api}:{yyyyMMddHHmmss}

例如：

rate_limit:appA:/order/query:20260609153021

Lua 脚本逻辑

伪代码如下：

local key = KEYS[1]
local limit = tonumber(ARGV[1])
local expireSeconds = tonumber(ARGV[2])

local current = redis.call(“GET”, key)

if current and tonumber(current) >= limit then
return 0
end

current = redis.call(“INCR”, key)

if tonumber(current) == 1 then
redis.call(“EXPIRE”, key, expireSeconds)
end

return 1

返回含义

  • 1：允许通过
  • 0：超限拒绝

3. 滑动窗口设计思路

固定窗口简单，但边界突刺明显。
如果要更精确，一般会用：

  • ZSET 存请求时间戳
  • 每次请求先删除窗口外的数据
  • 统计窗口内数量
  • 若未超限则写入当前时间戳

key 设计

rate_limit_sw:{appKey}:{api}

Lua 思路伪代码

local key = KEYS[1]
local now = tonumber(ARGV[1])
local windowMillis = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])

redis.call(“ZREMRANGEBYSCORE”, key, 0, now - windowMillis)

local count = redis.call(“ZCARD”, key)
if count >= limit then
return 0
end

redis.call(“ZADD”, key, now, tostring(now))
redis.call(“PEXPIRE”, key, windowMillis)

return 1

优点

  • 更精确
  • 用户体验更平滑

缺点

  • Redis 开销比固定窗口大
  • 高频场景要注意内存和热 key

4. 令牌桶设计思路

如果你想支持：

  • 平均速率控制
  • 同时允许短时突发

那就更适合令牌桶。

令牌桶关键参数

  • rate：令牌生成速率，比如 50/s
  • capacity：桶容量，比如 100
  • tokens：当前剩余令牌数
  • last_refill_time：上次补充时间

Redis 存储结构

可以用 hash：

rate_limit_tb:{appKey}:{api}

字段：

  • tokens
  • last_time

Lua 核心思路

  1. 取出上次时间和当前令牌数
  2. 根据时间差补充新令牌
  3. 如果补充后令牌 >= 1，则扣减并放行
  4. 否则拒绝

伪代码

local key = KEYS[1]
local rate = tonumber(ARGV[1]) – 每秒生成多少令牌
local capacity = tonumber(ARGV[2]) – 桶容量
local now = tonumber(ARGV[3]) – 当前毫秒时间

local data = redis.call(“HMGET”, key, “tokens”, “last_time”)
local tokens = tonumber(data[1])
local lastTime = tonumber(data[2])

if tokens == nil then
tokens = capacity
lastTime = now
end

local delta = math.max(0, now - lastTime)
local refill = delta * rate / 1000
tokens = math.min(capacity, tokens + refill)

local allowed = 0
if tokens >= 1 then
tokens = tokens - 1
allowed = 1
end

redis.call(“HMSET”, key, “tokens”, tokens, “last_time”, now)
redis.call(“EXPIRE”, key, 3600)

return allowed

5. 实际生产建议

建议一：通用接口优先令牌桶

因为开放平台第三方常有“批量同步”“整点任务”，纯固定窗口体验差。

建议二：导出/重接口加并发限制

QPS 小不代表资源消耗小。

建议三：再叠加日配额系统

令牌桶解决速率，配额解决总量。

五、面试回答版

下面给你一个适合面试直接讲的版本。

1. 短版回答

开放平台做限流，一般会从多个维度和多个层次来做。
维度上通常会按 appKey、租户、用户、IP、API 来限，指标上不光看 QPS，还会看并发数和日配额。
架构上一般分为：

  • 网关层做通用限流
  • 应用层做业务级限流
  • 配额中心做日/月调用量控制
  • 资源层保护数据库和下游依赖

算法上大多数会优先选择令牌桶，因为它既能控制平均速率，也能支持短时突发；对精度要求更高时会用滑动窗口；对重接口还会额外加并发限制。
在分布式场景里，常见实现是 Redis + Lua 保证原子性，再配合配置中心动态调整规则，最后通过监控告警和报表支撑运营提额、白名单和问题排查。

2. 稍长版回答

如果让我设计一个开放平台的限流体系，我会从四个方面考虑：

第一，限流维度

至少按 appKey + API 做基础限流，因为开放平台是面向第三方接入的；同时还会加上 租户级 限流，防止客户通过多个 appKey 绕过限制。对于登录、验证码、重复提交等场景，还会加 用户级 限流；IP 更多是作为防刷和风控辅助维度。

第二，限流层次

第一层在 API Gateway，做通用流量控制和统一拦截；第二层在业务服务内部，做资源级、用户级和幂等相关限制；第三层在资源侧，对数据库、缓存、第三方接口做并发和调用预算保护；如果平台有商业套餐，还会单独做配额中心管理日/月总量。

第三，算法选择

对于大多数开放 API，我会选令牌桶，因为它对突发流量更友好；如果某些接口要求更平滑和精确，可以用滑动窗口；重接口如导出、复杂查询，则会叠加并发限制，而不是只看 QPS。

第四，工程实现

分布式场景下一般用 Redis + Lua 做限流判断，保证原子性；规则从配置中心动态下发；限流命中后返回 429，并带上 Retry-After 和剩余额度等信息；同时要做好监控，包括限流次数、命中规则、被限 appKey TopN、接口 TopN，方便后续运营和排障。

六、如果你要做项目，我建议的“最小可用版本”

如果你现在真要开始做，我建议先别上太复杂的体系，先做 MVP：

第一阶段：先能用

  • 网关层按 appKey + API 做令牌桶限流
  • Redis + Lua 实现
  • 超限返回 429
  • 监控限流次数

第二阶段：补业务能力

  • 增加租户级限流
  • 增加导出/写接口并发限制
  • 增加白名单和临时提额

第三阶段：补商业能力

  • 日配额 / 月配额
  • 套餐差异化
  • 控制台查看剩余额度
  • 超限报表
